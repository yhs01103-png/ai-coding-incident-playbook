# 여러 프로세스가 같은 JSON/파일 레지스트리를 쓸 때 — 원자적 쓰기만으론 안 된다

## 문제

GUI/CLI/MCP서버/백그라운드 워치독처럼 서로 다른 프로세스 여러 개가 같은
설정/레지스트리 파일(JSON 등) 하나를 읽고 쓸 수 있을 때, "임시파일에 쓰고
`os.replace()`로 교체"하는 원자적 쓰기만 해두면 안전하다고 착각하기 쉽다.
원자적 쓰기는 "쓰다가 중간에 깨진 파일이 남는" 문제만 막지, "A가 읽은
뒤 B가 먼저 저장하고, A가 그걸 모른 채 자기 스냅샷으로 마저 저장해서
B의 변경을 통째로 덮어쓰는" 손실갱신(lost update)은 전혀 못 막는다 —
쓰기 자체는 매번 원자적으로 "성공"하기 때문에 에러도 안 나고 조용히
사라진다.

## 원인

read-modify-write(읽고 → 메모리에서 고치고 → 통째로 다시 씀) 패턴에서,
"쓰기 직전에 디스크가 여전히 내가 마지막으로 읽었던 그 상태인지"를
확인 안 하면 이 손실갱신이 구조적으로 발생한다. 특히 "필드 하나만
갱신"하는 헬퍼 함수(예: `save_core_path(entry)`처럼 어떤 하위 섹션
전체를 통째로 교체하는 함수)는 그 섹션 안의 리스트에 항목을 append하는
용도로도 쓰이는데, 이러면 "다른 프로세스가 그 사이 같은 섹션에 다른
항목을 추가했는지"를 안 보고 내 스냅샷 기준으로 섹션 전체를 덮어써서
방금 추가된 항목이 사라진다.

## 해법 — 두 축으로 나눠서 다르게 처리

**축 1 — 낙관적 동시성 제어(OCC)**: 프로세스가 파일을 읽을 때마다 그
시점의 전체 파일 해시(sha256 등)를 기억해두고, 쓰기 직전에 디스크의
현재 해시와 비교한다. 다르면(그 사이 누군가 저장했다는 뜻) 그냥
덮어쓰지 않고 막는다 — 파일 하나를 통째로 해시 비교하므로, 그 파일
안의 어느 섹션을 쓰든 전부 같은 매커니즘 하나로 보호된다(섹션마다
따로 락을 만들 필요 없음).

**축 2 — 충돌 시 동작을 "덮어쓰기냐 append냐"로 갈라라**:
- **사람이 편집 중인 배열을 통째로 교체하는 함수**(예: "루트 목록을
  이걸로 바꿔줘")는 충돌 나면 **그냥 멈추고 에러를 올린다** — 어느 쪽
  버전이 맞는지는 사람이 판단해야 하므로 자동으로 아무거나 선택하면
  안 된다("새로고침 후 다시 시도하세요"류 메시지).
- **append 전용 함수**(예: "이 항목 하나만 큐에 추가해줘")는 충돌 나도
  **최신 상태를 다시 읽어서 자동 재시도**해도 안전하다 — 내가 추가하려는
  항목과 다른 프로세스가 추가한 항목은 서로 무관해서 병합에 애매함이
  없다(단, 최대 재시도 횟수는 둬서 무한루프는 방지). "삭제 전용" 함수
  (예: "이 ID만 큐에서 지워줘")도 같은 이유로 재시도 안전.

판단 기준: "충돌했을 때 최신 상태를 다시 읽어서 내 변경을 그대로
재적용해도 두 변경이 자동으로 합쳐지는가?" — 그렇다면 재시도, 아니면
사람에게 멈추고 물어본다.

## 일반화

- 원자적 쓰기(temp+replace)와 동시성 제어(OCC/락)는 **서로 다른 문제를
  푼다** — 하나가 있다고 다른 하나가 공짜로 따라오지 않는다.
- 파일 전체 해시 하나로 여러 섹션(예: `roots`/`labeledFolders`/
  `corePath`)을 동시에 보호할 수 있다 — 섹션마다 별도 메커니즘을 새로
  발명할 필요 없이, 이미 있는 OCC 인프라에 그 섹션의 로드/저장 함수만
  참여시키면 된다.
- "이 헬퍼가 덮어쓰기인지 append인지"부터 먼저 분류하면, 충돌 시
  자동재시도(안전)와 사람에게 묻기(필요) 중 뭘 골라야 하는지가 거의
  자동으로 정해진다.
- 새 헬퍼 함수를 추가할 때 "지금 이 파일을 쓰는 프로세스가 정말 하나뿐인가"
  를 스스로 물어보는 습관이 안전하다 — "지금은 GUI 하나뿐"이라도, 같은
  파일에 쓰기용 API(MCP tool 등)가 나중에 하나만 더 생겨도 바로
  손실갱신 시나리오가 열린다. 다만 실제로 다중 프로세스가 이미 쓰고
  있는 게 확인된 경우(아래 실측 참고)에 우선 적용하고, 아직 단일
  프로세스만 쓰는 헬퍼까지 미리 다 OCC로 감싸는 건 과설계일 수 있다 —
  근거 없이 방어부터 깔지 말 것.

## 실측 사례

SSOT_Explorer(D-096, 2026-09-04) — `pendingActions`(GUI/CLI/MCP/워치독
4개 프로세스가 전부 쓸 수 있는 append 전용 큐)에 OCC를 걸되, 충돌 시
멈추는 대신 최신 상태를 다시 읽어 재시도하게 설계 — 무인 워치독이 매일
스케줄러로 도는데 사람의 GUI 저장과 우연히 겹쳐 그냥 에러로 멈추면 그날
찾은 발견사항이 로그도 없이 전부 사라지는 게 실제 위험 시나리오였음.
`roots`(사람이 편집)는 반대로 충돌 시 그냥 멈추는 쪽 유지.

SSOT_Explorer(D-112, 2026-09-08) — 코드 정밀분석 중 `corePath`(MCP
`/shortcut`·`/snippet`이 읽는 경로+명령/문구 등록)의 저장 함수가
D-096과 똑같은 구조(GUI 폼에서 append)인데도 OCC가 아예 빠져있는 걸
발견 — "developerMode 토글처럼 위험이 낮다"고 판단해 의도적으로 뺐던
결정이었는데, 실제로 두 프로세스가 같은 스냅샷에서 읽고 순서대로 쓰는
경쟁조건을 직접 재현해보니 먼저 등록한 항목이 조용히 사라지는 게
재현됐다. `pendingActions`와 동일한 OCC+재시도 패턴을 그대로 재사용해
승격 — 새 메커니즘을 발명하지 않고 이미 검증된 것과 같은 함수(파일
해시 추적 dict)에 새 로드/저장 함수만 참여시키는 방식이라 비용이
거의 없었다.

## 관련 문서와 구분

때" 열지 막을지를 다룬다 — 이 문서는 "쓰기가 성공은 했는데 순서가 꼬여서
내용이 사라지는" 문제라 다르다. `설정경로_환경변수_우선순위_폴백_패턴.md`
와도 다르다 — 그건 "경로를 어디서 찾는가"고, 이건 "같은 파일을 여러
프로세스가 쓸 때 서로를 어떻게 안 덮어쓰는가"다.
