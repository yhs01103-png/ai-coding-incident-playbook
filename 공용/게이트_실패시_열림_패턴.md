# 레이트리미터/게이트는 자기 자신의 실패를 fail-open으로 (범용)

호출 횟수 제한, 권한 체크, 어뷰징 방지 게이트 등 "이 요청을 통과시킬지
막을지"를 판단하는 모든 미들웨어/게이트 로직에 적용되는 원칙.

## 함정

레이트리미터가 "지금까지 몇 번 호출됐는지"를 확인하려고 DB(Firestore 등)를
조회하는데, **그 조회 자체가 실패하면(DB 순간 장애 등)** 무엇을 해야 할까?
아무 생각 없이 짜면 "확인 실패 = 안전하게 막자"는 직관으로 요청을 거부하게
되기 쉽다.

## 원칙 — 게이트 자신의 인프라 장애는 열림(허용) 쪽으로 넘어진다

**정상 기능이 미터링 인프라의 일시적 장애 때문에 막히는 것이, 어쩌다 한도를
살짝 넘는 것보다 나쁘다.** 카운트 조회가 실패하면(카운트가 한도를 넘었다는
게 확인돼서가 아니라, 확인 자체를 못 해서) 기본값은 **허용**으로 둔다:

```python
try:
    current_count = get_call_count_from_db(user_id)
except InfraError:
    log.warning("호출 카운트 조회 실패 — fail-open으로 허용")
    return True  # 막는 게 아니라 허용
if current_count >= DAILY_LIMIT:
    return False
return True
```

## 언제 반대로(fail-closed) 가야 하는가

이 원칙은 "과금/보안이 아니라 남용 방지용 소프트 리밋"일 때 적용한다.
반대로 **결제, 인증, 데이터 무결성**처럼 잘못 통과시켰을 때의 비용이 명확히
더 크면 fail-closed(장애 시 막음)가 맞다 — 예를 들어 "이 사용자가 유료
구독자인지" 확인이 실패했는데 그냥 통과시키면 매출 손실이 생긴다. **판단
기준**: 이 게이트를 잘못 통과시켰을 때의 비용 vs 정상 요청을 잘못 막았을
때의 비용을 비교해서, 후자가 더 크면 fail-open, 전자가 더 크면 fail-closed.
남용 방지/속도 제한류는 대개 전자(정상 사용자 차단 비용)가 더 크다.

**되돌릴 수 없는 외부 행동(메시지 전송·결제 실행 등)을 막는 게이트도 fail-closed다**
(Market_Agent_App 실측, 2026-10-09). 앱이 사용자 대신 다른 서비스에 메시지를 보내는 경우, 하루 한도·
전송 간격 게이트의 입력(오늘 보낸 수, 마지막 전송 시각)을 저장소에서 읽는다. 이 읽기가 실패했을 때
"0건/기록 없음"으로 취급해 통과시키면 한도를 확인하지 못한 채 보낸다 — 보낸 메시지는 되돌릴 수 없고
상대 서비스의 제재(스팸 판정, 계정 정지)로 이어질 수 있어 "잘못 통과시킨 비용"이 더 크다. 그래서
(1) 읽기 실패는 예외로 새게 두지 않고 잡아서 **전송을 막고**, (2) 막은 원인을 오류 로그에 남기며,
(3) 사용자에게 "기록을 읽지 못해 안전을 위해 보내지 않았다" 한 줄을 돌려준다. 읽기 함수를 주입식으로
받으면 이 실패 경로를 테스트에서 그대로 재현할 수 있다. 같은 맥락의 한계: 기록 저장소 자체가 지워지는
경우(앱 데이터 삭제, 손상 복구가 박스를 비움)는 읽기 실패가 아니라 "기록 없음"으로 보여 막을 수 없다 —
기록 소실 시 한도가 초기화된다는 점은 알고 두거나, 소실을 감지할 별도 표식이 필요하다.
