# 백엔드가 응답에 필드를 추가해도, 클라이언트가 실제로 읽고 있는지는 아무것도
# 강제하지 않는다 — 주기적으로 감사할 것 (범용)

클라이언트-서버로 나뉜 프로젝트에서, 서버 쪽 API 응답에 필드를 하나 추가하는
작업과 클라이언트 쪽이 그 필드를 실제로 파싱해서 쓰는 작업은 **완전히 분리된
두 커밋**이 되기 쉽다. 이 사이 시차가 생겨도 아무것도 안 깨지고 아무 경고도
안 뜬다는 게 이 함정의 핵심 — 다른 프로젝트에도 그대로 재현될 수 있는 구조적
문제라 범용으로 남긴다.

## 왜 조용히 묻히는가

- JSON을 느슨하게 파싱하는 클라이언트 코드(`json['new_field']`를 아예 안 쓰면
  그냥 무시되는 구조 — Dart의 `Map<String, dynamic>` 기반 `fromJson`, JS의
  구조분해 등)는 서버가 새 필드를 추가로 보내도 **에러를 내지 않는다**. 그냥
  그 값이 응답 어딘가에 도착했다가, 아무도 안 읽어서 버려질 뿐이다.
- 타입체커/린터도 이 틈을 못 잡는다 — "이 API 응답에 이 필드가 있는데 어느
  모델도 그걸 선언 안 했다"는 걸 감지하려면 서버 스키마와 클라이언트 모델을
  **양쪽 다 아는** 도구가 있어야 하는데, 대부분의 프로젝트엔 그런 계약 검증
  단계가 없다(OpenAPI 스키마 자동생성+클라이언트 코드젠 같은 걸 안 쓰는 한).
- 그래서 "서버는 이미 몇 릴리스 전부터 보내고 있었는데 클라이언트가 계속
  무시하고 있었다"는 게 기능 하나가 통째로 "구현 중"으로 잘못 표시된 채 며칠~
  몇 주씩 방치될 수 있다 — 실제로는 필드 하나 배선하면 끝나는 마무리 작업인데,
  아무도 "다 끝났는지 확인"을 안 해서 계속 미완료 목록에 남아있는 상태.

## 감사 방법

1. **API 응답을 만드는 쪽(서버) 코드에서 최근 추가된 필드를 먼저 특정**한다 —
   결정이력/커밋 로그에서 "응답에 필드 추가"류 항목을 찾거나, 그 엔드포인트의
   직렬화 코드(`return {..., "new_field": ...}`류)를 직접 읽는다.
2. **그 필드 이름으로 클라이언트 코드 전체를 grep**한다. 결과가 0건이면 확정
   — 그 필드는 서버가 보내는 순간부터 지금까지 클라이언트 어디서도 안 읽히고
   있었다는 뜻이다.
3. 이미 배선된 필드들과 **같은 자리**(같은 모델 클래스, 같은 UI 컴포넌트)를
   찾아서 그 옆에 나란히 추가한다 — 이미 검증된 파싱/표시 경로가 있으면 새
   작업이 아니라 "이미 있는 배선에 필드 하나 잇기" 수준으로 작아진다.
4. 파싱 테스트가 있는 프로젝트라면, 새 필드를 포함한 샘플 JSON으로 테스트
   케이스를 하나 추가해서 앞으로 같은 필드가 다시 조용히 빠지는 걸(리팩토링
   중 실수로 등) 방지한다.

## 이 문제를 구조적으로 줄이는 법 (선택, 비용 대비 판단 필요)

작은/중간 규모 프로젝트에서 OpenAPI 코드생성 같은 무거운 도구를 도입하는 건
과할 수 있다 — 대신 저비용으로 할 수 있는 것들:
- 서버 쪽 결정이력/커밋 메시지에 "API 응답 필드 추가"를 남길 때, 클라이언트
  담당 작업을 **같은 항목의 하위 TODO로 명시**해서 "서버 완료"와 "전체 완료"를
  섞어 표시하지 않는다(이번 실측 사례처럼 서버 D-번호 하나가 배선까지 다 끝난
  것처럼 보였는데 실제론 절반만 끝나 있었던 경우를 방지).
- 주기적으로(신규 기능 착수 전이나 코드 감사 시점에) 최근 N개 API 필드 추가
  항목을 골라 위 감사 방법을 한 번씩 돌려본다 — 특정 필드 하나를 찾아서 고치는
  것보다, "이런 게 또 있을 수 있다"는 걸 알고 정기적으로 스윕하는 습관이 더
  근본적인 대응이다.


## 실측 후속 (poker_app, 2026-09-19~21) — "클라이언트 배선"을 끝내도 서버 안쪽 소비 지점이 남는다 (3층)

감사 리포트(2026-09-17)가 "서버는 완성됐는데 클라이언트가 안 부르는 기능" 5건을 가장 큰 리스크로 꼽았고,
이틀 뒤 client 코드를 같은 방식(기능 식별자 grep)으로 재대조하니 4건이 해소돼 있었다 — 이 감사 방법은 재실행이
싸고 결과가 즉시 나오므로 **작업 시작 때마다 돌리는 습관**이 유효하다. 같은 세션에서 새 사례가 하나 더 나왔다:

- 서버가 제자 환생(ADR-142)을 로직·API까지 완성했고 클라이언트 호출부는 0건이었다(전형적 1·2층 분리). UI를
  붙인 뒤에도 **퍼크가 개방·표시만 되고 실전 효과가 없는 상태**였다 — 서버가 퍼크를 저장하고 AI 결정 함수에
  받을 인자(`perks`)까지 만들었지만, 실제 결정 호출부(라이브 대국/배경 시뮬레이션/토너먼트 어댑터)가 그 값을
  조회해 넘기지 않았다. 즉 완료 판정 층이 **세 개**다: ① 서버 API/로직 ② 클라이언트 호출·UI ③ 서버 내부에서
  그 값을 실제로 소비하는 코드가 그 값을 받는가.
- **③ 감사법**: 새 인자/데이터의 이름(`perks`)으로 서버 코드를 grep해 *정의*만 있고 *호출부 전달*이 없는지
  본다(`decide(` 호출 4곳 중 몇 곳이 그 인자를 넘기는가). 테스트는 결과 값이 아니라 **인자 전달 자체**를
  관찰하도록 함수를 기록용 서브클래스로 바꿔 끼워 검증하면 확률적 결과에 흔들리지 않는다.
- **표시만 되는 기능은 완료로 치지 않는다**: UI에 나오는 값이 실제 동작에 반영되는지가 판정 기준이다 — 새 UI를
  붙이는 순간 "이제 유저에게 약속한 효과가 실제로 있는가"를 한 번 더 묻는다.

## 반대 방향 — 서버가 필드 전송을 멈춘 뒤에도 클라이언트가 계속 읽는다 (RVS_App, 2026-11-11)

설계를 바꿔 서버가 응답 필드(예: 선택지의 `users`, 평가의 `shared`)를 더는 보내지 않게 했는데, 클라이언트의 모델·화면은 그 필드를 계속 파싱하고 그리는 코드가 남았다. 필드가 **옵션**이라 컴파일도 실행도 멀쩡하고, **시험의 가짜 응답이 옛 필드를 계속 실어 주니 시험도 통과**한다 — 죽은 코드가 "검증된 기능"처럼 보이는 상태다.

- **감사**: 서버에서 필드를 뺀 같은 커밋(또는 바로 다음)에 그 키 이름으로 클라이언트 모델·화면·시험 픽스처를 grep한다 — 읽는 코드, 그리는 코드, 그 값을 넣어 주는 시험 데이터가 **세 곳**이다.
- **같이 지운다**: 모델 필드·표시 코드·그 표시를 확인하는 시험·픽스처를 한 번에 지운다. 시험만 남기면 사라진 기능을 계속 보증하고, 표시 코드만 남기면 영영 안 뜨는 화면이 된다.
- **롤아웃 순서**: 이미 배포된 옛 클라이언트가 있으면 서버는 필드를 빼도 되고(옵션이라 옛 클라이언트는 그냥 안 그림), 새 클라이언트가 읽기를 지우는 쪽이 안전하다. 반대로 필수 필드를 빼면 옛 클라이언트가 깨진다.
