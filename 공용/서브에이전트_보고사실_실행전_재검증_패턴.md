# 서브에이전트가 보고한 "사실관계"도 실행 전에 직접 재검증한다 (범용)

`LLM_블라인드_서브에이전트_자기일관성_측정_패턴.md`와는 다른 축이다 — 그
문서는 "여러 번 생성한 결과가 서로 얼마나 일관되는가"를 다루고, 이 문서는
**서브에이전트 1회 보고 안의 개별 사실 주장 하나하나가 실제로 맞는지**를
다룬다. 서브에이전트(fork든 fresh Agent든)가 코드베이스를 조사해 "X는 Y
상태다"라고 보고하면, 그 보고를 실행 계획의 전제로 그대로 믿고 진행하기
쉽다 — 서브에이전트도 결국 같은 모델이 grep/Read 몇 번으로 결론 내린
것이라, 검색 누락이나 오독으로 사실과 다른 결론을 낼 수 있다.

## 문제

"조사만 하는" 서브에이전트의 결과 리포트는 보통 신뢰도가 높다고 가정하고
그 위에 바로 실행 계획을 얹는다. 그런데 리포트의 개별 항목(예: "이 파일은
어디서도 참조 안 됨", "이 함수는 아무도 안 씀")은 grep 패턴이 조금만
빗나가도(예: 실제 참조가 다른 표기법·다른 확장자·주석 안에 있는 경우) 틀린
채로 리포트에 남는다. 리포트 전체 톤이 확신에 차 있어도 개별 사실은 오류일
수 있다는 점이 리뷰어(사람이든 AI든)에게 잘 안 드러난다.

## 해법

- 서브에이전트 리포트의 항목 중 **그 위에 바로 코드 변경을 얹을 항목**만이라도,
  실행 직전에 자신이 직접 한 번 더 확인한다(예: "미사용"이라는 결론이면
  실행 직전 자신이 직접 grep 한 번 더 돌려서 확인) — 리포트 전체를 다시
  조사하란 뜻이 아니라, 그 결론을 근거로 실제 파일을 만들거나 지우는
  단계에서만 값싸게 한 번 더 확인.
- 특히 "미사용/죽은 코드/참조 없음"류의 **부정 명제**(무언가가 없다는 주장)는
  긍정 명제보다 검증 실패 확률이 높다 — grep 패턴 하나만 놓쳐도 "없다"는
  결론이 그냥 나와버리기 때문. 이런 항목을 실행 계획의 전제로 쓸 땐 재검증
  우선순위를 높게 둔다.
- 재검증에서 리포트가 틀렸다고 확인되면, 그 사실을 조용히 넘기지 말고 작업
  결과물(커밋 메시지, 결정이력)에 "리포트가 이 부분은 틀렸었다"로 명시 —
  같은 서브에이전트를 다음에도 신뢰할 근거(또는 못 할 근거)가 쌓인다.

## 실측 사례 (poker_app, ADR-121/125, 2026-09-14)

전체 UI 애니메이션/UX 전수조사를 fork 서브에이전트에 맡겼는데, 그 리포트가
"Lottie 애셋 4개(`trophy`/`chip_spin`/`spade_icon`/`cards_loader.json`)가
전부 미사용(grep 0건)"이라고 결론 냈다. 이후 실제로 그 4개를 소비하는 코드를
작성하려고 각각의 사용처를 직접 grep한 결과, `cards_loader.json`은
`splash_screen.dart`가 이미 오래전 커밋부터 쓰고 있었음이 드러났다(fork의
grep이 이 참조를 놓친 것으로 추정). 실제 미사용은 3개였다 — 실행 직전 재검증
덕에 "이미 쓰이고 있는 에셋을 새로 소비하는 코드를 중복 작성"하는 실수를
피했고, 결정이력 문서에도 "전수조사 리포트가 이 부분은 틀렸었다"고 명시
기록했다.
