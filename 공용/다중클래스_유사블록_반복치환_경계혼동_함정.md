# 한 파일에 클래스가 여러 개일 때 유사 블록을 반복 치환하면 괄호가 엉뚱한 클래스로 샌다 (범용)

중괄호/괄호로 블록을 구분하는 언어(Dart/JS/Java/C++ 등, 들여쓰기만으로
스코프를 정하는 Python은 이 함정에서 자유롭다)에서, **한 파일 안에 비슷하게
생긴 블록이 여러 클래스에 걸쳐 여러 번 등장**할 때(예: 여러 위젯 클래스가
각자 비슷한 구조의 콜백/빌더를 갖고 있는 UI 코드) 반복되는 편집 실수.

## 함정

같은 패턴(예: "GestureDetector로 감싸진 위젯을 InkWell로 교체")을 파일 안
여러 곳에 순서대로 적용하다 보면, 지금 편집 중인 블록이 **어느 클래스에
속하는지**를 놓치기 쉽다. 특히 두 블록이 코드 모양은 비슷한데 실제로는 서로
다른 클래스(예: `_ActionRowState`와 `_EVBreakdownState`)에 속해 있으면,
"열었으니 닫아야 할 괄호 개수"를 세다가 실수로 **다른 블록/다른 클래스의
끝부분에** 괄호를 추가하게 된다. 이 실수는 문법적으로는 종종 유효한 채로
남는다(괄호 개수 자체는 맞아떨어질 수 있음) — 컴파일러/린터가 즉시 정확한
위치를 짚어주지 않는 한, 원인이 수십~수백 줄 떨어진 곳에 있어 디버깅이
오래 걸린다.

## 해법

1. 한 파일에서 비슷한 블록을 여러 번 고칠 계획이면, 먼저 `grep -n "^class "`
   (또는 해당 언어의 클래스/함수 선언 패턴)로 **파일 안의 클래스/함수 경계를
   전부 나열**해두고, 지금 편집하는 줄 번호가 어느 경계 안에 있는지 항상
   확인한다.
2. 편집 하나를 끝낼 때마다(파일 전체를 다 고치고 나서 한 번에 검사하지 말고)
   그 파일 하나만 즉시 정적 분석/컴파일(`flutter analyze <파일>`,
   `tsc --noEmit <파일>` 등 파일 단위 지원 시)한다 — 실수가 있으면 다음
   블록으로 넘어가기 전에 바로 드러나서, 원인을 그 직전 편집 하나로 좁힐 수
   있다. 전체 프로젝트 분석은 그 다음(개별 파일들을 이미 검증한 뒤 최종
   확인용)으로 미룬다.
3. 실수를 발견했다면, "어느 클래스에 몇 개 열림/닫힘이 있어야 하는지"를 다시
   세는 대신 방금 편집한 두 블록의 diff를 나란히 보면서 어느 쪽에 괄호가
   잘못 갔는지부터 확인한다 — 대부분 "가장 최근에 편집한 두 블록 중 하나"에
   있다.

## 실측 사례 (poker_app, ADR-123, 2026-09-14)

`hand_review_screen.dart`에서 GestureDetector 2곳을 InkWell로 바꾸는 작업
중, 서로 다른 클래스(`_ActionRowState`의 행 전체 탭 영역, `_EVBreakdownState`
안의 "재생" 버튼)에 속한 블록을 같은 함수 안이라고 착각해 첫 번째 블록을
감싸며 추가한 닫는 괄호를 실제로는 파일 뒷부분의 `_EVBreakdownState` 클래스
끝에 잘못 추가했다. `flutter analyze`를 파일 단위로 즉시 돌리는 습관 덕에
전체 프로젝트 분석 전에 바로 컴파일 에러로 드러났고, `grep -n "^class "`로
클래스 경계를 재확인해 올바른 위치로 옮겨 수정했다.
