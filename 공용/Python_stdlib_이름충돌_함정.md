# 프로젝트 파일명이 Python stdlib 모듈명과 겹치면 인터프리터 부팅 자체가 깨질 수 있다 (범용)

Python 프로젝트에서 파일/모듈 이름을 지을 때 적용하는 짧은 체크리스트.

## 함정

`server/types.py`처럼, **stdlib에 이미 있는 모듈명**(`types`, `io`, `email`,
`calendar`, `queue`, `token` 등)과 같은 이름의 파일을 프로젝트 안에 만들면,
그 파일이 있는 디렉터리가 `sys.path` 앞쪽에 오는 실행 경로(프로젝트 루트에서
직접 실행 등)에서 **Python 3.10+ 인터프리터 자체의 부팅 과정**이 깨질 수
있다 — `enum`/`functools` 같은 내부 stdlib 모듈이 초기화 중에 `from types
import ...`를 실행하는데, 그게 stdlib의 진짜 `types`가 아니라 프로젝트의
`server/types.py`로 잘못 resolve되기 때문이다. 증상은 임포트 에러가 아니라
알아보기 힘든 초기화 단계 크래시로 나타나기 쉽다.

**경로 의존적이라 더 헷갈린다**: 어느 디렉터리에서 실행하느냐(`sys.path[0]`이
뭐가 되느냐)에 따라 재현되거나 안 되거나 한다 — "내 컴퓨터에선 되는데"의
전형적인 원인이 될 수 있다. `pytest`처럼 프로젝트 루트가 아닌 다른 위치에서
실행되는 도구에서는 재현이 안 될 수도 있어서, 실행 위치별로 따로 확인해야
한다.

## 해법

1. **가장 확실한 해법은 그냥 이름을 안 겹치게 짓는 것**(`server/types.py`
   → `server/schemas.py` 등) — 파일을 새로 만들 때 stdlib 모듈명과
   겹치는지 한 번 확인하는 습관이 가장 싸다.
2. 이미 만들어진 파일이라 이름을 바꾸기 부담스러우면(호출부가 많음 등),
   문제가 되는 지점에서만 `sys.path`를 일시적으로 조작해 진짜 stdlib을
   가져온 뒤 복원하는 방어 코드로 우회할 수 있다:
   ```python
   import sys
   _saved = sys.path[0]
   sys.path.pop(0)  # 프로젝트 경로를 잠깐 빼서
   import types as _real_types  # stdlib의 진짜 types를 가져옴
   sys.path.insert(0, _saved)  # 복원
   ```
   단, 이건 원본 이름 충돌은 그대로 둔 채 증상만 우회하는 것이라, 실행
   위치가 하나 더 늘어나거나 다른 도구가 추가되면 다시 재현될 수 있다는
   걸 인지하고 있어야 한다(가능하면 1번을 우선한다).
