# 동시 요청이 함께 인증 거절을 받을 때 — 복구(갱신·기기 가입)는 한 번, 세션 번호로 "이미 바뀐 세션"을 가린다 (범용)

앱 시작을 빠르게 하려고 요청 여러 개를 동시에 보내는(`Future.wait`, `Promise.all`) 순간, "401이면 토큰을 갱신하거나 새로 가입하고 다시 보낸다"는
요청 단위 복구 로직이 요청 수만큼 돈다. 토큰 갱신은 보통 한 번으로 묶어 두지만, **무계정 기기 가입 같은 다른 복구 경로는 빠지기 쉽다.**

## 1. 실측 (RVS_App 2026-10-31)

- 시작 요청 4개(프로필·사용량·동의·관계 목록)를 동시에 보내도록 바꾼 다음 날, 인증 켠 서버에서 첫 실행 → 4개가 함께 `login_required` → 각자 `/auth/device`
  → **같은 초에 계정 4개**. 3개는 버려진 계정이고, 서버의 IP당 시간당 가입 한도(10회)를 한 번에 4회 쓴다 — 테스터 3명만 같은 와이파이로 열어도 막힌다.
- 토큰 갱신(`/auth/refresh`)은 이미 공유 Future로 한 번만 하고 있었다. 기기 가입 경로만 그 장치가 없었다.
- 개발 서버는 개발용 무인증 스위치(추적 안 되는 파일)로 돌아 이 경로를 한 번도 지나지 않았다 — 인증 켠 사본으로 실기기를 돌려서야 보였다
  (`Flutter_실기기_adb_탭_스크린샷_자동검증_절차.md` "다른 세션이 작업 중일 때").

## 2. 고치는 법

1. **모든 복구 경로를 같은 방식으로 한 번만**: 진행 중인 복구 Future를 필드에 두고(`_recovering ??= _doRecover().whenComplete(() => _recovering = null)`),
   늦게 거절받은 요청은 새로 복구하지 않고 그 Future를 기다린 뒤 다시 보낸다. 갱신·가입·재로그인 판단이 한 함수 안에 있으면 그 함수 하나를 공유한다.
2. **세션 번호**: 세션이 바뀔 때마다 오르는 정수를 두고, 요청을 보내기 직전 값을 잡아 둔다. 거절이 왔을 때 번호가 이미 달라졌으면
   (그 사이 다른 요청이 갱신·가입을 끝냈다) 복구하지 말고 새 세션으로 한 번 더 보낸다. 공유 Future만으로는 "복구가 끝난 **뒤에** 도착한 옛 거절"을 못 막는다 — 그 요청은 새 복구를 시작한다.
3. **번호는 새 세션을 저장할 때만 올린다** ⚠️: 옛 토큰을 지울 때 올리면, 가입 요청이 아직 진행 중일 때 도착한 거절이 "이미 바뀌었다"로 보고
   **토큰 없이** 재시도해 또 거절받는다(RVS 첫 수정에서 실기기로 발견 — 동의·관계 목록이 401 두 번 뒤 실패). 지운 상태는 "바뀐 세션"이 아니라 "복구 중"이다.
4. **예외 — 다시 로그인해야 하는 사용자**(구글 연결 등 조용히 새 계정을 만들면 데이터가 사라진 것처럼 보이는 경우): 그 경로에서만 지울 때 번호를 올려,
   뒤늦은 거절이 "토큰 없음 → 기기 가입"으로 새지 않게 한다. 공유 Future가 던진 재로그인 예외는 기다리던 요청 모두에 같이 전달된다.
5. 다시 보내기는 한 번만(재귀 금지). 두 번째도 거절이면 그 응답을 그대로 올린다.

## 3. 시험 — 즉시 응답하는 가짜 서버로는 틈이 안 보인다

목(mock) HTTP가 바로 답하면 거절 4개가 복구 시작 전에 다 도착해 "가입 1번"은 통과하지만 3번의 틈은 못 잡는다. `Completer`로 응답 시점을 잡는다:
- 동시 4개가 함께 거절 → 가입 1번, 4개 모두 성공.
- **가입 응답을 붙잡아 둔 동안** 다른 요청의 거절을 풀어 준다 → 그 요청이 가입을 기다렸다가 새 세션으로 성공(번호를 지울 때 올리면 여기서 실패).
- 가입이 끝난 **뒤에** 옛 거절이 도착 → 가입 없이 재시도로 성공.
- 재로그인 대상 사용자의 동시 거절 → 아무도 가입하지 않고 모두 재로그인 예외.
각 시험이 수정 전 코드에서 실제로 실패하는지 한 번 돌려 본다(RVS: 앞의 둘이 각각 수정 전 코드에서 실패).

## 4. 함께 확인

- 서버 쪽: 기기 가입에 IP당 한도가 있으면 클라이언트 중복은 곧 한도 소진이다. 반대로 서버가 같은 기기의 중복 가입을 막아 주길 기대하지 말 것(기기 식별자가 없으면 구분 못 한다).
- 동시 전송을 넣는 변경(`Future.wait`)을 리뷰할 때 "이 요청들이 함께 401을 받으면?"을 체크리스트로 둔다 — 시작 화면뿐 아니라 탭 하나가 요청 여러 개를 동시에 보내는 곳도 같다.
