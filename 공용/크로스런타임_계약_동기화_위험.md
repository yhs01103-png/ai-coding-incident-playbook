# 서로 다른 런타임에 걸친 상수/계약은 동기화를 강제할 장치가 없다 (범용)

클라이언트(Dart/Flutter)와 서버(Python)처럼 **서로 다른 언어/런타임**이 같은
개념(임계값, 스키마, 툴 이름 등)을 각자 자기 쪽 코드에 따로 선언해야 하는 모든
프로젝트에서 반복 확인되는 구조적 한계. 최소 4개 독립 프로젝트(SSOT_Explorer의
MCP 툴 스키마, Hub_App_winter의 레이어 분리 방침 문서, JudgeCal의 표본 크기
임계값, poker_app의 보스전 액션/레이즈 범위 계약)에서 각자 발견돼 "이건 개별
버그가 아니라 크로스런타임 자체의 구조적 한계"로 확인됨(2026-08-19 종합,
2026-09-01 poker_app 사례 추가).

**실측 사례(poker_app, 2026-09-01, H-041/ADR-63~64)**: client(Dart,
`boss_llm_decision.dart`)와 server(Python, `boss_decision_logic.py`)가
"합법 액션 문자열 집합은 `{fold, call, raise}`, raise면 `min_raise`~
`max_raise` 범위 안"이라는 같은 검증 규칙을 양쪽에 각각 손으로 구현했다
— client 쪽은 게임 엔진의 `ActionType` enum(`fold`/`call`/`raise`)과
이름이 우연히 같아 지금은 안 어긋나지만, 엔진 쪽 enum 이름이 바뀌면
서버 쪽 `_VALID_ACTIONS`는 컴파일 타임에 아무 신호 없이 조용히
어긋난다. 완화책으로 결정 문서(ADR-63/64)에 "이 검증 규칙은 두 곳에
있다"를 명시적으로 남기고, 서버 쪽 검증을 관대하게(loose)가 아니라
엄격하게(strict) 짜서 — 어긋나면 "잘못된 값을 그대로 통과"가 아니라
"즉시 502로 실패 + 클라이언트 폴백"으로 안전하게 넘어가게 설계(아래
"완화책"과 별개로, 크로스런타임 계약이 어긋났을 때의 **실패 방향**도
같이 설계해두면 완전 동기화가 안 돼도 안전망이 남는다).

## 문제

같은 런타임 안에서는 상수/스키마를 한 곳에 선언하고 import해서 쓰면 되지만,
언어가 다르면(Python↔Dart 등) **코드를 공유할 방법이 없다** — 값을 양쪽에
각각 손으로 선언해야 한다. 한쪽만 바뀌면:
- 컴파일 타임에 안 걸림(둘 다 각자 문법적으로는 유효한 코드라서)
- 런타임에도 바로 안 걸림 — 실제로 그 값에 의존하는 경로가 실행될 때가
  돼서야("알 수 없는 값", 잘못된 판정 등) 어긋남이 드러난다

## 지금 수준에서 할 수 있는 것 — 완전 자동화는 안 되니 최소한이라도

- **결정 문서에 "이 값을 바꾸면 반드시 다른 쪽도 같이 바꿔야 한다"를 명시적으로
  남긴다** — 코드 주석뿐 아니라 설계 결정 로그에도, 값이 있는 두 파일 경로를
  서로 교차 언급해서(양방향) 한쪽만 보고 고치는 실수를 줄인다.
- **완전한 해결책은 스키마 단일 소스(JSON Schema 등)에서 양쪽 코드를 생성하는
  것**이지만, 이건 별도 빌드 파이프라인 투자가 필요해서 프로젝트 초기엔
  오버엔지니어링이다 — 크로스런타임으로 공유해야 하는 계약이 몇 개 안 될 땐
  "문서화된 수동 동기화"로 충분하고, 개수가 늘어나거나 실제로 어긋난 사고가
  한 번이라도 나면 그때 코드생성 파이프라인 도입을 검토한다.
- 최소한 **CI 린트로 이름 일치 정도는 확인**할 수 있다(값 전체를 생성하진
  못해도, "이 상수 이름이 두 파일 다 존재하는가" 정도의 존재 여부 체크는
  스크립트 몇 줄로 가능) — 완전 자동화가 부담스러우면 이 정도가 절충안.

## 새 크로스런타임 계약을 추가할 때 미리 할 일

새로 클라이언트+서버 양쪽에 같은 값/스키마가 필요해지면, 만들자마자 그
사실을 결정 문서에 "이 값은 두 곳에 있다"로 기록해둔다 — 나중에 "여기 있는
줄 몰랐다"는 사고를 막는 가장 싼 방법은 처음 만든 순간에 남겨두는 것뿐이다.


## 실측 후속 (poker_app, 2026-09-19) — 값의 성격에 따라 "복제"가 아니라 "원본 조회"를 택한다

같은 프로젝트 안에서 두 방식이 공존한다: **가격 견적**은 클라이언트가 서버 공식을 미러링하되 실제 청구는 서버
응답을 신뢰(어긋나도 표시만 잠깐 틀릴 뿐 돈은 서버 값), **확률 고지**(랜덤박스/카드팩 확률)는 미러링하지 않고
서버가 원본 표를 조회 API로 그대로 내려준다. 판단 기준은 **어긋났을 때의 비용**이다 — 견적은 화면 오차로 끝나지만
확률 고지는 실제 추첨과 한 글자라도 다르면 법적/신뢰 문제라, 복제본 자체를 만들지 않는 편이 "동기화를 강제하는
장치" 문제를 통째로 없앤다(고지 값이 추첨 값에서 파생 → 동기화할 대상이 없음). 새 크로스런타임 값을 만들 때
"어긋나면 비용이 큰가?"를 먼저 묻고, 크면 복제 대신 조회로 설계한다(네트워크가 필요해지는 대가는 감수).
