# 포크한 앱의 공유 파일 갈라짐 점검 — 한쪽을 고치면 다른 쪽도 고쳐야 하는지 알려 주는 장치

## 문제

앱 A를 복사해 앱 B를 만들면(포크) 같은 파일을 두 곳이 따로 들고 간다. 공유 모듈(호출 계측, LLM 호출 계층, 상태 라우터 등)은 한쪽에서 버그를 고치거나 안정화를 넣으면 **다른 쪽에도 같은 수정이 필요**한데, 그걸 알려 주는 장치가 없다. 실제로 JudgeCal에서 만든 취소·AI 연결 확인·응답 모델이 RVS에 한참 뒤에야 옮겨졌고, RVS에서 만든 하루 한도 429 차단기는 JudgeCal에 없는 채로 지내다 옮겼다. "이식했다"는 기억은 휘발되고, 포크 기준 커밋 기록조차 실제와 어긋나 있었다(함정: 개발_서비스_폴더_분리_운영_패턴 함정 29).

## 패턴

작은 스크립트 하나(`scripts/check_fork_drift.py`)가 세 가지만 한다.

1. **공유 파일 목록**(의도적으로 같은 모양을 유지해야 하는 서버 파일 8~10개)마다 두 앱의 **줄 차이 수**를 센다(CRLF/LF 무시, `difflib`).
2. **기준 파일**(`fork_drift_baseline.json`)에 마지막으로 검토했을 때의 *상대 앱 커밋 해시*와 파일별 차이 수를 저장한다.
3. 실행하면 (a) 상대 앱에서 **기준 이후 그 파일들을 건드린 커밋 목록**(`git log <기준>..HEAD -- 파일들`)과 (b) 차이 수가 기준과 달라진 파일을 보여 주고, 하나라도 있으면 종료 코드 1이다. 검토하고 필요한 수정을 옮긴(또는 안 옮기기로 한) 뒤 `--update-baseline`으로 기준을 갱신한다. **기준 갱신은 사람(또는 사람이 시킨 에이전트)이 검토한 뒤에만** 하고 자동으로 하지 않는다.

의도적으로 다른 부분(한쪽만 있는 한도 환불, 서로 다른 작업 이름 등)은 처음 기준에 이미 들어 있어 경고가 되지 않는다 — "다름"이 아니라 "다름이 **변했을 때**"만 알린다. 그래서 오탐 없이 계속 켜 둘 수 있다.

## 하지 말 것

- **공용 패키지로 뽑기부터 하지 않는다.** 두 앱의 배포·의존성이 달라 공유 패키지가 오히려 결합을 만든다. 파일 수가 적고 갈라지는 방향이 한쪽 우세한 동안은 점검 스크립트가 훨씬 싸다. 갈라짐 경고가 자주 울리면 그때 공용화를 검토한다.
- 목록에 **크게 갈라진 파일**(예: 한도·계정 로직)은 넣지 않는다. 처음부터 차이가 수백 줄이면 변화가 신호가 되지 않는다. 한쪽 변경이 다른 쪽에 의미가 있는 파일만 고른다.
- 기준 해시를 *포크 시점*으로 두지 않는다 — 마지막 **검토 시점**이다.
- **공유 파일 안의 상대 앱 이름(로거 이름·ContextVar 이름 등)을 "잔재 정리"로 바꾸지 않는다.** 차이 0줄이던 파일에 의미 없는 차이가 생겨 이후 진짜 변경이 묻힌다. 이름 정리는 공유 목록 밖 파일(클라이언트 설정 등)에서만 하고, 공유 파일은 "포크 유산이라 둔다"고 설계 문서에 적는다(RVS_App 2026-10-30 — 클라이언트 `JUDGECAL_*` 정의 이름은 `RVS_*` 우선 + 폴백으로 바꾸고, 서버 `judgecal.*` 로거는 `fork_drift_baseline` 대상이라 유지).

## 체크리스트

- [ ] 포크 직후 공유 파일 목록과 기준(상대 앱 HEAD, 파일별 차이 수)을 저장했는가
- [ ] 한쪽의 공유 파일을 고친 날 스크립트를 돌렸는가(커밋 전 훅으로 걸지 않아도 된다)
- [ ] 한쪽에만 있는 개선을 *옮길지 말지*를 설계 문서에 적었는가(예: 해설 캐시는 입력이 매번 달라지는 게임에는 효과가 작아 안 옮김)
- [ ] 기준을 갱신하기 전에 옮길 것을 다 옮겼는가
