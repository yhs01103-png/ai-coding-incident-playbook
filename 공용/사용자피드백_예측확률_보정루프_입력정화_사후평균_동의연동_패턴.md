# 사용자 피드백으로 예측 확률을 보정하는 루프 — 입력 정화부터, 사후 평균은 읽을 때, 동의와 안내를 일치 (범용)

예측(결과 후보 + 확률)을 내는 앱이 "실제로 어땠나요"를 받아 확률을 점점 맞추고 싶을 때. 보정 공식보다 **입력이 먼저 망가져 있는 경우가 많다** —
원 사례는 RVS_App(역산 시뮬레이터, 2026-10-31). 프로젝트 무관하게 적용 가능. §7은 이 보정을 사용자 사이로 넓힐 때(공유 풀, 2026-11-11).

## 1. 입력부터 정화한다 (보정 공식보다 먼저)

- **기본값 있는 질문은 데이터를 오염시킨다.** "예측한 대로 행동했나요" 스위치가 기본 켜짐이면, 안 건드린 사용자는 원래대로 했어도 전부 "그대로 했음"으로 쌓인다.
  → 기본값 없는 선택(바꿔 본 대로 / 원래대로 / 다른 걸)으로, 안 고르면 저장하지 않는다. "원래대로"도 버리지 말고 따로 둔다(원래 행동 보정의 재료).
- **적중은 사람이 고른다.** 실제 결과 글을 키워드·임베딩으로 예측과 자동 대조하면 그 판정이 곧 학습 라벨이 된다 — 틀린 판정이 그대로 보정에 들어간다.
  → "예측 N개 + 예측에 없던 결과" 중 사용자가 직접 고르게 하고, 자동 판정은 **"추천" 표시만**(미리 선택해 두면 그냥 넘겨 자동 판정과 같아진다).
- **선택지는 서버가 저장해 둔 그 예측에서만.** 화면마다 후보를 넘겨받으면 경로마다 달라질 수 있다 — 조회 응답에 후보를 싣고, 저장 때 서버가 고른 순위를 그 세션의 후보 수로 검사한다.
- **출처를 기록한다**(`user`/`keyword`)와 자동 추천 순위도 같이 저장 — 옛 자동 판정 기록은 지우지 말고 `unverified`로 분리, 추천이 사용자 선택과 얼마나 맞는지(일치율)도 잴 수 있다.
- 이건 `JudgeCal_Athe/확률적_결과_기반_자기편향_순환_함정.md`의 "신호는 사용자 입력이어야 한다"를 라벨 쪽에 적용한 것이기도 하다.

## 2. 보정은 사후 평균, 원본은 그대로 두고 읽을 때 덧씌운다

- 결과가 여럿이면 디리클레(베타의 다중 버전) 사후 평균: **보정 확률_i = (원래 확률_i × k + 실제로 된 수_i) ÷ (k + 기록 수)**.
  k = 원래 확률을 기록 몇 건만큼 믿을지(예 20 — 기록 20건이면 원래와 실제가 반반). 기록이 최소 건수(예 5) 미만이면 원래 그대로.
  "예측에 없던 결과"는 기록 수에만 들어가 전부를 깎고, 합 100으로 다시 나눈다(최대잔여법).
- **원본(시드 파일·DB)은 안 바꾼다.** 후보를 돌려주는 한 곳에서만 덧씌운다 — 끄기는 상수 하나, 되돌리기는 커밋 되돌리기. 파일을 직접 고쳐 커밋하는 방식은
  원본을 쓰는 다른 작업(자동 콘텐츠 채우기 등)과 충돌하고, 배포 서버의 실사용 집계를 반영하기 어렵다.
- **결과 순서·개수를 유지한다** — 저장된 후보의 n번째가 원본의 n번째여야 다음 집계가 같은 칸을 센다(정렬은 보여 줄 때만).
- k·최소 건수는 운영 한도(요금제 숫자)가 아니라 엔진 조정값이다(`개발_서비스_폴더_분리_운영_패턴.md`의 "엔진·안정화 로직은 제약이 아니다").

## 3. 집계 표를 따로 두지 말고 매번 기록에서 센다 (표본이 작은 동안)

- 별도 카운터 표는 "다시 기록하면 두 번 셈", "동의 철회 시 빼기", "기록 삭제 시 빼기"를 전부 따로 처리해야 한다.
  기록 + 예측 노드 + 동의 표를 조인해 조회 때 세면 셋 다 공짜로 맞는다. 느려지면 그때 인덱스나 캐시를 둔다(측정 뒤).

## 4. 다른 사용자 기록을 쓰는 순간, 동의와 안내를 동작과 일치시킨다

- 집계만 쓴다 해도 "남의 기록으로 내 확률이 바뀐다" — 기존 학습 동의 설정이 있으면 **동의한 사용자의 기록만** 재료로.
- 실측 함정: 동의 설정을 먼저 만들어 두면 안내가 "지금은 아무 곳에도 쓰이지 않고 허락 여부만 저장돼요"로 남아 있다가, 실제로 쓰기 시작한 커밋에서
  **안내와 API 플래그(`in_use: false`)를 같이 안 바꾸면 거짓 안내가 된다**(RVS는 보정 커밋이 먼저 푸시되고 다음 작업에서 발견). 동의를 실제로 쓰는 커밋에
  안내 문구·플래그·테스트를 같이 넣는다. 옛 문구로 받은 동의를 새 용도에 써도 되는지도 확인(배포 전이면 해당 없음).

## 5. 보정 곡선은 "참고용"을 그대로 보여 준다

- "몇 %라고 본 결과가 실제로 몇 % 일어났나"를 구간별로 — 결과가 적은 구간(예 10개 미만)·기록이 적을 때(예 30건 미만)는 숫자와 함께 "아직 N건이라 참고용".
  표본이 적은데 숫자만 보여 주면 우연을 성과로 착각하게 하고, 그대로 밝히는 게 신뢰를 만든다.
- 운영자용(전체 집계)과 사용자용(내 기록)은 **같은 계산 함수 하나**를 쓰고 재료만 다르게.

## 5-1. 운영자 지표 — 곡선 옆에 무엇을 같이 두나 (RVS 2026-10-31, 개발자 콘솔)

- **Brier에 "예측에 없던 결과" 칸을 넣는다**: 후보 확률 합이 100%로 정규화돼 있으면 실제 결과가 후보 밖일 때 후보 칸만 보면 오차가 작게 나온다. 확률 0인 칸 하나를 더해 그 경우를 1로 친다.
- **절대값 대신 기준선 대비**(skill = 1 − Brier ÷ 같은 기록에 후보 확률을 모두 같게 준 Brier): 후보 수가 기록마다 달라 Brier 절대값끼리는 비교가 안 된다. 양수면 "확률을 붙인 의미가 있다".
- **로그 손실은 바닥을 둔다**(없던 결과 = 1%): 0을 넣으면 한 건이 평균을 무한대로 만든다.
- **구간 비율엔 윌슨 95% 구간**: 칸마다 후보 수가 작아 정규 근사는 0~1 밖으로 나간다.
- **결과 출처별로 나눈다**(사례 매칭 / AI 생성): AI가 만든 사례와 실제로 관찰된 사례를 같은 무게로 믿지 않으려면 먼저 둘의 실제 적중이 다른지 본다. 사례마다 "실제 결과로 검증된 횟수·한 번도 안 맞은 사례·마지막 검증 시각"만 세고 사례 문장·id는 내보내지 않는다.
- **오차 원인은 사용자가, 1위가 빗나갔을 때만**: "어디서 빗나갔나요" 선택지(상황 판단 / 행동 효과 / 상대 반응 / 바깥 변수 / 예측에 없던 일)를 1위가 맞지 않은 기록에만 묻고 고르지 않아도 저장되게 한다. 서버는 같은 조건이 아니면 버린다(나중에 1위로 고쳐 기록하면 지워짐). AI 추정은 기록마다 호출 비용이 들고 원인을 지어낼 수 있다.
- 모두 순수 함수 하나(조회와 분리)로 두고, 재료가 0건이어도 null·빈 칸으로 그려지게 시험한다 — 배포 전에는 대부분 0건이다.

## 6. 먼저 데이터 속도를 잰다

- 보정의 재료는 "예측대로 행동했고 직접 고른" 기록뿐이다. 사용자가 예측한 행동을 실제로 하는 비율이 낮으면 표본이 거의 안 쌓인다 —
  기록 대비 그 비율(scored / not_followed)을 콘솔에 먼저 띄우고, k·최소 건수는 그 속도를 보고 정한다. 데이터 0건일 때 넣은 보정은 "최소 건수 미만이면 원본"이라 동작이 안 바뀌어 안전하다.

## 7. 사용자 사이로 넓힐 때 — 복사해 올리지 말고 동의한 사용자의 기록에서 매주 계산한다 (RVS 2026-11-11)

"여러 사용자가 같은 방향으로 쌓은 결과를 모두가 참조하는 풀로 올리고 싶다"는 요구에서, 처음엔 실제 결과를 기록할 때 일반화한 글을 공유 표에 복사해 올리고 탈퇴 직전에도 옮기는 방식을 만들었다가(여러 커밋) **같은 날 전부 걷어냈다.** 이유와 대안:

- **복사의 문제 셋**: ① 내 기록과 같은 정보가 두 곳에 있어 동의 철회·계정 삭제마다 "연결 끊기"·삭제 훅이 따로 필요하다 ② 공유 표에 사용자가 쓴 글이 남는다(규칙으로만 일반화한 글 — 지역명·별명·직장 얘기는 규칙이 못 지운다) ③ 사용자마다 문장이 달라 "같은 상황·같은 결과"를 묶는 기준을 글 단위로 따로 만들어야 한다. 3절("집계 표를 따로 두지 말고 매번 기록에서 센다")을 사용자 간으로 넓히면 이 셋이 같이 사라진다.
- **파생 방식**: 공유 풀은 별도로 올리는 곳이 아니라 **동의한 사용자의 세션(실제 결과 기록)에서 주기적으로 계산한 통계**다. 표본 한 건 = 실제 결과를 적은 세션 중 *예측한 행동을 그대로 했고* 목표 역산이 아닌 것. 라벨 = 실제 결과가 예측 후보 중 몇 번째인지(후보에 없으면 "일치 아님") + 그때 AI가 낸 순위별 확률. 사용자 식별은 솔트 해시뿐이고 상한 계산에만 쓰며 글은 담지 않는다.
  - **철회 = 다음 계산부터 빠짐, 계정 삭제 = 세션이 지워져 흔적 없음** — 철회·삭제 처리 코드가 필요 없다.
  - **동의 시점이 아니라 동의 여부로 판단하면 동의 전에 적은 기록도 포함된다.** 구현을 끝내고 문서를 쓰다 발견했다 — 문구에 "허락하기 전에 이미 적은 것도 포함"을 명시한다(안 하면 사용자는 "앞으로 적는 것만 쓰이겠지"라고 읽는다).
- **승격은 표본 수로, 도배 상한을 같이 둔다**: 묶음 하나의 센 표본이 N건 이상이면 승격(RVS는 20). 한 사용자가 한 묶음에서 센 건수를 k로 제한하면(RVS 2) **서로 다른 사용자 수 하한이 N÷k(10명)로 자동 보장**돼 따로 하한 규칙이 필요 없다. 하루 기여 상한(5)도 같은 곳에서 건다.
- **묶음 이름표를 글 없이 유지한다**: 주마다 그리디로 다시 묶으면 묶음이 흔들려 "같은 묶음의 일반 문장 재사용"이 깨진다. 글이나 대표 문장을 저장하지 않고, **센 표본의 세션 id 해시 집합**을 저장해 새 묶음과 절반 이상 겹치면 같은 묶음, 아니면 대표 임베딩의 코사인으로 본다. 임베딩 호출이 안 되는 환경(키 없음)에서도 동작한다.
- **사람이 읽는 문장은 승격 때 묶음당 한 번만 만든다**: 사용자별로 일반화하면 AI 호출이 사용량에 비례하고 사용자별 일반화 글이 남는다. 묶음이 승격될 때 그 묶음의 글 몇 개를 AI에 주고 일반 문장 하나를 받아 규칙 검사(숫자·연락처 제거·길이)를 거치고, 못 만들면 **노출하지 않고 다음 주에 다시** 한다. 표본이 2배가 되면 한 번 갱신. 개발자 부담 호출은 전용 신원의 하루 한도가 그대로 상한이다.
- **노출은 자동 + 이력**: 승인 큐 대신 승격·갱신·해제를 이력 표에 남겨 문제가 생겼을 때 찾는 용도로 쓴다(관리 부담보다 추적 가능성을 택한 결정). 20건 아래로 내려가면(철회) 승격이 풀리고 그것도 이력에 남는다.
- **보여 주는 방식**: "비슷한 N건 중 1위 예측이 맞은 비율 X% · AI가 낸 확률 Y%"를 나란히 — 5절 보정 곡선을 묶음 단위로 옮긴 것이다. 마음에 안 들면 호출 1회로 AI가 매칭 정보와 내 프로필을 합쳐 다시 계산(기존 AI 보강 경로 재사용). 통계는 결과 **세트로 세지 않고 근거로만** 쓴다 — 세트로 세면 같은 증거를 두 번 센다.
- **킬 스위치는 읽기까지 닫는다**: 첫 구현은 서버 스위치가 올리는 쪽(기여)만 막아서 이미 승격된 데이터는 스위치를 꺼도 계속 보였다(설계 검토에서 발견). 스위치 하나가 쓰기·계산 배치·읽기·동의 화면을 모두 닫는지 시험한다.
- **동의 문구는 쓰이는 것을 그대로 말한다**: 기존의 "건수만 쓰는" 학습 동의(4절)와 달리 상황·행동 글이 AI 일반화의 입력으로 쓰이므로 별도 스위치·별도 문구가 필요하다. 서버 스위치가 꺼져 있는 동안은 화면에서 숨긴다(안 열린 기능을 동의받지 않는다).
- **교차 사용자 읽기 SQL은 저장소 계층에**: 공유 풀 로직 모듈이 세션·동의 표를 직접 조인하면 계층 감사에서 걸린다(RVS 11-11 감사에서 실제로 잡혀 고침) — 저장소 메서드가 재료를 돌려주고 로직은 변환(순위·해시·상한)만 한다.

## 체크리스트

- [ ] 적중 라벨을 사람이 고르고, 자동 판정은 추천 표시만인가
- [ ] 선택지가 서버 저장값에서만 오고 서버가 범위를 검사하는가
