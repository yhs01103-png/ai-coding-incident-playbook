# 데이터 이전 검증 — "값이 원본 어딘가에 있다"는 확인은 한 글자 값도 통과시킨다 + 원본 삭제 전 양방향 대조 (범용)

평문 파일의 값을 새 저장소(암호화 저장소, DB 등)로 옮기고 **원본을 지우는** 작업에서, 검증이 약하면 손상된 이전을
"전부 일치"로 보고하고 원본까지 지워 되돌릴 수 없게 된다. 실측에서 이전 직후 "14개 모두 원본과 일치"라고 보고했는데
3개가 한 글자로 저장돼 있었고, 원본 삭제 직전의 대조에서 **이전 도중 사용자가 원본에 새로 적은 값 2개**까지 발견됐다.

## 함정 1 — 부분문자열 존재 확인(`Contains`)은 짧은 값을 전부 통과시킨다

```powershell
$ok = $allSourceText.Contains($migratedValue)      # ← "원본 어딘가에 이 문자열이 있다"
```

이전된 값이 **한 글자**(`백`)여도, 원본 텍스트 전체에 그 글자가 어딘가 있으니 `True`다. 파싱 버그로 값이 잘리거나 비어도
(`''.Contains` 계열은 항상 참) 이 검증은 못 잡는다.
- 해결 ①: **길이 하한 + 전체 일치**를 같이 본다 — 값이 기대 형식의 최소 길이 이상인지, 원본의 "라벨 뒤 부분 전체"와 같은지.
  원본 줄에서 구분자(`:`/`=`) 뒤를 잘라 후보 집합을 만들고 `HashSet.Contains(전체 값)`으로 **완전 일치**만 인정한다.
- 해결 ②: 값을 출력하지 않는 대신 **길이를 표로 출력**하고 사람이 상식으로 훑는다(압축 비번 11자, 키 44자, 이메일 18자 …
  한 자리 숫자가 보이면 즉시 이상). 길이 표는 한 글자 버그를 가장 싸게 드러낸다.
- 해결 ③: 한 줄짜리·빈 값 같은 **경계 입력을 테스트 데이터에 일부러** 넣는다(원인이었던 PowerShell 단일 요소 배열 풀림은
  `PowerShell_5_1_조용히_틀리는_함정_모음.md` 함정 1).

## 함정 2 — 정방향 대조만으로는 "원본에 있지만 옮기지 않은 값"을 못 찾는다

정방향(새 저장소의 값 → 원본에 있는가)이 전부 일치해도, **원본에 있는데 파서가 놓친 항목**은 영영 모른다. 원본을 지우면 그 항목이
사라진다.
- 역방향: 원본에서 "비밀처럼 보이는 토큰"(길이 ≥ 8, 숫자 포함, 영숫자+기호만, 도메인·IP·공개키·날짜 제외)을 뽑아 새 저장소의
  값/메모 어디에도 없는 것을 센다. **값은 출력하지 않고 `파일:줄번호 (길이)`만** 낸다.
- 의심 건은 값 대신 **모양**(글자→`a`, 숫자→`9`, 한글→`가`, 기호는 그대로)과 라벨로 정체를 가린다 — 모양 `가가가가 가가 = aaaa9999!%(`
  만 봐도 "라벨이 붙은 새 비번 줄"임을 알 수 있다.
- 라벨과 값이 붙은 토큰(`KEY=값`)은 `=` 뒤만 대조해 오탐을 줄인다. 오탐은 허용하되 **누락 의심은 0이 될 때까지** 사람이 본다.

## 함정 3 — 원본은 읽은 뒤에도 바뀐다 (사용자가 같은 파일을 계속 편집 중일 수 있다)

이전 스크립트를 짠 시점의 스냅샷과 삭제 시점의 원본이 다를 수 있다. 실측: 첫 읽기 이후 사용자가 두 파일에 "바꿀 예정 비번" 줄을
추가했고(수정 시각으로 확인), 역방향 대조가 없었다면 삭제와 함께 사라졌다.
- 삭제 직전 **마지막으로 대조를 돌리고**, 그 대조 시점의 `LastWriteTime`을 기록해 두었다가 **삭제 순간에 다시 비교**한다 — 하나라도
  다르면 전부 보류.
  ```powershell
  if ((Get-Item $f).LastWriteTime.ToString('MM-dd HH:mm') -ne $expected[$f]) { 보류 }
  ```
- 같은 폴더에 **내가 만들지 않은 파일**(0바이트 메모 등)이 있으면 열지도 지우지도 않는다.

## 순서 — 원본을 지우기까지

1. 원본 → 중간 형식(JSON 등)으로 **옮긴 뒤**, 새 저장소와 중간 형식을 **사용자가 직접 실행하는 읽기 전용 대조 스크립트**로 비교한다
   (마스터 비밀번호가 필요한 단계는 에이전트가 대신 못 한다 — 스크립트만 주고 결과를 받는다. 스크립트는 값을 출력하지 않고 `일치/불일치`만).
2. 원본 ↔ 중간 형식을 **양방향 대조**한다(위 함정 1·2).
3. 사용자의 **명시적 삭제 승인** + 수정 시각 가드(함정 3) 통과 시에만 삭제한다. 삭제 후에도 중간 형식 사본이 남아 있으니, 그 평문 사본은
   새 저장소 가져오기·백업(USB) 뒤에 별도로 지운다.
4. 어떤 단계에서든 "전부 일치" 보고는 **어떤 검증으로 일치를 봤는지**(길이 하한? 완전 일치? 양방향?)와 함께 한다 — 약한 검증으로
   한 "일치" 보고는 사용자가 원본 삭제를 결정하는 근거가 되므로 가장 위험하다.
