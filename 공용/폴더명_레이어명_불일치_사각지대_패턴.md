# 폴더/파일 이름이 레이어를 흉내내도 실제 의존 방향은 안 지켜질 수 있다 (범용)

`레이어_분리_방침.md`(Plug_In_Global)류의 원칙을 적용하는 프로젝트가 폴더명을
레이어명과 맞추기 시작하면(`hooks/`=UX, `services/`=API호출, `pipeline.js`=
파이프라인, `contracts/`=계약 등) "이름이 곧 구조 보증"이라고 착각하기 쉽다.
실제로는 이름과 실제 import 관계가 어긋난 채로 방치되는 사각지대가 있다.

**실측 사례(poker_app 세션, 2026-09-14)**: `Local_APP\AI연동 자동실행
허브 엔진_레거시_롤백용`(workout/diet/skin/stretch 멀티앱 허브 — 이
knowledge base의 다른 문서가 인용하는 `Hub_App`/`Hub_APP_Sever`와 같은
계열의 스냅샷으로 추정) 프론트엔드를 열어 실제 import문을 grep으로
대조한 결과 —
- `apps/workout/hooks/useWorkoutSync.js`(폴더명상 UX)가 `apps/workout/
  pipeline.js`(파이프라인)를 거치지 않고 `shared/services/hubApiService.js`
  (API호출 레이어)를 **직접 import**.
- `apps/workout/pipeline.js` 자신도 실제로는 페이지 컴포넌트를 재수출하는
  수준이라, 방침이 말하는 "경로+API호출+DB+로직+계약을 재조립하는
  오케스트레이션" 역할과는 거리가 있었음.
- `apps/workout/components/WorkoutHubTab.jsx`(폴더명상 UI)가 `shared/
  contracts/policy.js`(계약)를 직접 import — 계약은 "참조만" 원칙 자체는
  안 어겼지만, UI가 계약을 직접 참조하는 경로 자체가 방침의 통신 방향
  단방향 원칙과 결이 다름.

폴더 이름 자체는 처음엔 의도대로 지어졌을 가능성이 높다 — 개발이 진행되며
지켜지지 않게 된 것으로 보이고, 이걸 잡아낼 별도 장치(lint, 감사)가 없어서
아무도 눈치채지 못한 채 누적된 사례로 추정된다.

**반대 방향 사례(RVS_App, 2026-11-01)** — 이름만 보고 감사하면 위반을 **잘못 세기도** 한다.
Flutter 클라이언트 `lib/path/`에 경로 상수(`app_paths`)와 함께 기기 파일 저장소(`mode_store`·`draft_store` —
안내를 봤는지·모드·입력 임시 저장을 파일로 읽고 씀)가 들어 있었다. 감사는 폴더 이름대로 이걸 "경로 레이어"로 보고
`mode_store → logic/app_mode` import를 "경로는 아무것도 부르지 않는다" 위반으로 세 번 연속 기록했다. 실제 책임으로 보면
저장소는 **DB(영속) 레이어**라 모델 타입을 참조하는 게 정상 — 오분류였다. 대신 진짜 위반은 따로 있었다: 화면(UX) 4개가
그 저장소를 직접 받아 쓰고 있었다(파이프라인 경유 원칙 위반, 6건). 해결은 저장소 틀을 logic으로 옮기는 게 아니라
(로직은 처리 단위라 저장소 틀의 자리가 아님 — 처음 낸 안을 방침과 대조하다 철회) 파이프라인에 얇은 감싸개
(`DevicePrefs`)를 두고 화면은 그것만 받게 한 것. 저장소 생성은 전역설정(`main`) 한 곳이라 테스트는 거의 안 바뀌었다.

교훈: 감사 표의 행을 셀 때 "이 파일이 실제로 무엇을 하는가"를 먼저 적고 나서 방향 규칙을 대본다 — 이름에서 레이어를 정하면
없는 위반을 세고(오분류), 있는 위반의 원인을 엉뚱한 데서 고치려 든다(틀을 logic으로 옮기는 안).

## 문제

- 폴더명이 레이어처럼 보이면 리뷰어/AI 에이전트 모두 "이름이 맞으니 구조도
  맞겠지"라고 안심하고 실제 import 그래프를 재확인하지 않게 된다.
- 코드 리뷰만으로는 놓치기 쉽다 — 한 파일의 import 몇 줄만 보고 "저 레이어를
  건드리네"라고 즉시 알아채는 사람은 드물고, 위반이 하나씩 조용히 쌓인다.
- `레이어_분리_방침.md`가 "폴더명은 1:1로 안 맞아도 된다"고 명시한 것의
  반대쪽 함정이다 — 그 문서는 "이름이 달라도 책임만 맞으면 된다"만
  다루고, "이름을 맞췄다고 책임까지 자동 보장되진 않는다"는 이번에
  새로 확인된 축.

## 완화책

- **기계적 검증 장치**를 둔다 — JS는 import 경계 lint(예: `eslint-plugin-
  boundaries`, dependency-cruiser), Python은 import-linter류로 "이 폴더는
  저 폴더만 import 가능"을 강제. 처음부터 못 두면 최소한 존재는 인지해둔다.
- 장치가 없는 프로젝트는 **주기적 레이어 감사 체크리스트에 "이름-실제 방향
  일치 여부" 항목을 넣는다** — `앱_정밀_분석_프롬프트.md`(Plug_In_Global)
  0-3단계 레이어 감사 표의 10번째 행이 이 항목을 명문화한 실제 사례.
- 감사 결과는 1회성 리포트로 흘려보내지 말고 프로젝트 자체 설계도 폴더에
  누적 로그로 남긴다 — 다음 감사 때 "지난번보다 나아졌는지" 비교 근거가
  없으면 같은 위반이 반복돼도 아무도 모른다(`설계도_이중계층_프로토콜.md`
  §13 로깅 규칙 참고).
- 새로 폴더를 레이어명으로 지을 때, "이 이름이 약속하는 호출 방향"을 그
  폴더 최상단 주석/README에 한 줄로 명시해두면 나중에 감사할 때 "원래
  의도"와 "실제 상태"를 바로 대조할 수 있다.
