# 서버가 거절하는 새 규칙의 롤아웃 — 앱 먼저, 플래그는 시즌 경계, 튜닝값은 저장 금지 (범용)

게임·콘텐츠 서버가 "이 행동은 이제 안 된다"처럼 **새 거절 규칙**을 플래그로 켜는 모든 배포에 적용되는 운영 원칙.
(보스전 규칙형 기믹을 실사용자 앞에 내놓는 지침을 쓰다 나온 것 — 규칙 자체는 프로젝트 전용이지만 순서·저장 원칙은 어디서나 같다.)

## 1. 앱을 먼저 배포하고, 규칙 플래그는 그 뒤에 켠다

- 서버가 응답에 **필드를 새로 내리는 것**은 모르는 클라이언트가 무시하면 끝이라 안전하다.
- 그러나 **서버가 행동을 거절하는 새 규칙**은 모르는 클라이언트에게 "버튼은 눌리는데 오류(409 등)가 나는 앱"으로 보인다.
- 그래서 순서는 ① 새 필드를 이해하고 버튼을 막아 주는 앱 배포 → ② 사용자들이 업데이트할 시간 → ③ 규칙 플래그 ON.
  (서버만 먼저 켜면 옛 앱 사용자는 조용한 오류 폭탄을 맞는다.)

## 2. 누적형 랭킹이 있는 콘텐츠는 플래그를 시즌 경계에서만 바꾼다

- 판 단위로 모드가 고정되면 진행 중인 판은 안전하다(시작 때 모드로 끝까지 간다).
- 문제는 **시즌 누적 값**(누적 피해, 점수)이다. 시즌 중간에 규칙을 켜거나 끄면 같은 시즌의 앞 판과 뒤 판 난이도가 달라 순위가 불공정해진다.
- 켜고 끄는 시점은 시즌 리셋 직후. 부득이하게 시즌 중에 바꿨다면 그 시즌 순위 보상을 수동 점검한다. 같은 플래그를 쓰는 다른 경로(자동 NPC 대전 등)도 같이 바뀐다는 점을 체크리스트에 넣는다.
- 켜기 전 체크: DB 스냅샷, 진행 중 세션이 없는 시간대.

## 3. 튜닝 값은 코드 상수로, 저장하는 건 "진행 결과"뿐

- 배정표·수치·구간 경계 같은 튜닝 값을 DB에 저장하는 순간 그 값이 마이그레이션 대상이 된다. 코드 상수면 바꿔도 마이그레이션이 없다.
- 저장해야 하는 건 플레이어/회사의 **진행 결과**(체력 누적, 랜덤으로 굴린 구성처럼 재굴림하면 안 되는 것)뿐이다.

## 4. 저장되는 식별자는 이름을 바꾸지 않는다

- 저장된 구성에는 id 문자열이 들어간다(효과 id, 카드 id 등). id를 바꾸거나 지우면 저장본이 가리킬 곳이 없어지고, 모르는 id를 무시하는 코드라면 깨지진 않지만 **있던 효과가 조용히 사라진다**.
- 이름을 바꿔야 하면 별칭 표(옛 id → 새 id)를 둔다. 의미(수치)만 바꾸는 건 자유다.
- 풀에서 항목을 뺄 때는 이미 붙은 효과를 지울지 둘지 정책을 먼저 정한다(기본: 그대로 둔다).
