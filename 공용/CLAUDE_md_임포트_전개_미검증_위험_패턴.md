# CLAUDE.md `@경로` 임포트 전개 미검증 위험 패턴

트리거(상황): 사용자 레벨 `~/.claude/CLAUDE.md`(또는 프로젝트 CLAUDE.md)에서
`@경로` 문법으로 다른 규칙 문서를 참조하고 "이건 항상 로드된다"고 가정해 그
하위 문서에만 실제 규칙 본문(참조조건 표, 트리거 규칙 등)을 두고 있을 때 —
그 하위 규칙이 세션에서 실제로 적용됐는지 의심되거나, 여러 세션에 걸쳐 같은
정책 위반이 반복되는데 원인을 코드가 아니라 "규칙이 안 읽혔을 가능성"에서
찾아야 할 때.

## 무엇이 실제로 발견됐는가

`@경로` import는 "세션 시작 시 그 자리에 내용을 그대로 펼쳐 넣는 공식 문법"
이라고 문서화돼 있지만(예: 이 사용자의 `~/.claude/CLAUDE.md` 머리말), 실제
세션의 시스템 리마인더를 열어보면 `@C:\...\파일명.md` 줄이 **문자열 그대로**
남아있고 대상 파일 내용으로 안 펼쳐진 사례가 관측됐다(JudgeCal_Athe 세션,
2026-09-05). 그 하위 문서(이 사례에서는 프로젝트 전역 작업규칙 마스터본)가
가리키는 여러 개의 하위 참조조건 규칙(다른 문서를 언제 열지 정하는 규칙들)이
그 세션 내내 컨텍스트에 전혀 없었다는 뜻 — 사용자가 우연히 그 규칙의 존재를
물어봐서 직접 파일을 열어 확인한 뒤에야 뒤늦게 반영됐다.

## 왜 위험한가

- 에러가 안 뜬다 — import가 안 펼쳐져도 세션은 정상적으로 진행되고, 그
  세션이 마스터본의 규칙을 하나도 안 지키고 있다는 신호가 사용자에게도
  AI에게도 안 보인다.
- "상시 로드"라는 문서상 주장과 실제 동작이 갈리는 걸 확인할 방법이
  세션 시작 시점의 시스템 리마인더를 직접 열어 `@`로 시작하는 줄이 문자열
  그대로 남아있는지 육안으로 대조하는 것뿐 — 자동 알림이 없다.
- 체인이 길수록(마스터본 → 참조조건 규칙 여러 개 → 각 참조조건이 또 가리키는
  실제 프로토콜 문서) 실패가 한 지점에서 전체 체인을 조용히 끊는다.

## 완화책

1. **"상시 로드"를 안전장치로 신뢰하지 않는다** — 중요한 참조조건 규칙(언제
   어느 문서를 열지 정하는 규칙)이 의심스러우면, "이미 로드됐을 것"이라고
   가정하지 말고 그 자리에서 직접 Read로 열어 확인하는 걸 기본 습관으로
   삼는다. 상시 로드는 있으면 편한 최적화일 뿐, 있다고 보장되는 안전장치가
   아니다.
2. **재현성으로 구분한다** — 이 문제가 매 세션 재현되는지, 이번 한 번만인지
   구분 없이 "가끔 그렇다"로 단정하지 않는다. 다음 세션에서 같은 방식으로
   시스템 리마인더를 열어 재확인하고, 반복되면 구조적 결함(빈도 상시)으로,
   1회만 재현되면 관측 부족(빈도 미상)으로 기록을 갱신한다.
3. **체인을 짧게 유지한다** — 마스터본이 가리키는 각 하위 참조조건 규칙
   문서 자체도 또 다른 문서를 가리키는 깊은 체인을 만들지 않는다(이 사용자의
   기존 규칙 — "C-3/C-4 절에는 '언제 여는지'만 남기고 본문은 중복 기재하지
   않는다"). 체인이 얕을수록 한 지점의 임포트 실패가 덜 광범위하게 퍼진다.
4. **불일치 발견 시 보고** — 도구/제품 자체의 버그일 가능성이 있으므로
   재현 정보(파일 경로, 세션 시작 시스템 리마인더의 관측 내용)를 남겨 추적
   가능하게 한다.
5. **(2026-09-06, 실제 적용·검증됨) `@import` 대신 SessionStart 훅으로
   배달한다** — 프로즈(`@import`)는 실패해도 신호가 안 남지만, 훅은 외부
   프로세스가 실제로 실행되는 것이라 신뢰성 등급 자체가 다르다. 이 사용자
   워크스페이스엔 이미 매 세션 확실히 발동하는 SessionStart 훅(SSOT
   레지스트리 드리프트 감지용, `ssot_session_context.py`)이 있었고, 그
   출력이 이 세션 내내 한 번도 안 빠지고 나온 걸 직접 확인했다 — 그래서
   마스터본(`클로드_코드_답변_전역규칙.md`)도 같은 방식으로 배달하는 훅
   (`~/.claude/hooks/global_rules_context.py`)을 신설해 `@import`를
   완전히 우회했다. 단, 처음엔 cwd 무관하게 매 세션 무조건 그 파일 전문
   (~7,600자)을 주입하다가 "이 워크스페이스와 무관한 프로젝트에서도 매번
   이 비용이 붙는다"는 지적을 받아, `ssot_session_context.py`가 이미
   쓰던 것과 동일한 cwd-매치 로직(`_is_or_under`, 레지스트리의 `roots[]`
   경로 하위 여부 확인)을 그대로 복제해 **등록된 SSOT 루트(하위 폴더
   포함) 세션에서만** 주입하도록 스코프를 좁혔다 — 매치/비매치 양쪽 다
   실제로 pipe-test해 확인(매치 시 정상 주입, 비매치 시 출력 0바이트).
   교훈: "훅으로 신뢰성을 확보"와 "그 훅을 아무 데나 무조건 발동시키지
   않기"는 별개 결정이다 — 신뢰성 문제를 해결하자마자 이번엔 "매번 발동
   비용" 문제가 새로 생기므로, 조건부 게이팅(레지스트리 매치 등 이미
   가벼운 신호가 있으면 그걸 재사용)을 같이 넣어야 실질적으로 쓸 만하다.
6. **(2026-09-06, 일반화) 이 문제는 `@import`에만 한정되지 않는다** —
   README → CLAUDE.md → 상위 워크스페이스 인덱스로 이어지는 파일 체인,
   그리고 마스터본 안의 "이 상황엔 이 문서를 열어라"류 참조조건 규칙
   (예: 이 사용자 워크스페이스의 C-1~C-5)도 전부 같은 신뢰성 등급이다 —
   전부 "AI가 그 문서를 실제로 읽고 알아서 따라야" 작동하는 프로즈
   기반이라, `@import`와 동일한 방식으로 조용히 안 지켜질 수 있다(아직
   이쪽은 실측 사례가 없어 [추정]). 신뢰성이 특히 중요한 소수의 규칙만
   골라 이 완화책 5번처럼 훅으로 전환하는 걸 검토할 가치가 있고, 모든
   참조조건을 훅으로 바꾸는 건 과함(대부분은 프로즈로 충분히 작동해왔고,
   신뢰성 문제가 실측되지도 않았다).

비고: 순수 범용(특정 프로젝트 코드와 무관, `@경로` import 기능 자체의 신뢰성
문제이자 프로즈 기반 참조조건 규칙 전반의 신뢰성 등급 문제) — JudgeCal_Athe
세션에서 1회 관측 후 완화책 5번을 실제로 적용·검증 완료. 원인 자체의 재현
빈도(항상/가끔/이번만)는 아직 미상이나, 훅 기반 완화책은 이미 검증된 해법으로
남긴다.
