# 사용자가 "나중에 결과를 적어야" 가치가 쌓이는 앱 — 로컬 예약 알림으로 후속 확인, 기본은 켬, 효과는 기록률로 잰다 (범용)

예측·계획·약속처럼 **나중에 실제 결과를 기록해야** 정확도나 데이터가 쌓이는 앱은 기록을 사용자의 기억에만 맡기면 결과 기록이 거의 쌓이지 않는다. 서버 푸시 없이 기기 로컬 예약 알림으로 "며칠 뒤 어떻게 됐나요?"를 묻고, 그 효과를 서버 쪽 지표로 잰다. RVS_App(2026-10-23)에서 Lazzy(Jarvis)의 로컬 알림 구현을 줄여 옮기며 정리했다.

## 1. 로컬 예약 알림만으로 충분한 경우

- 알림 시각이 "지금 + N일" 정도로 느슨하고 서버 이벤트에 달려 있지 않다 → `flutter_local_notifications`의 `zonedSchedule`. 서버 푸시(FCM)·백그라운드 폴링은 가져오지 않는다(비용 0, 앱이 꺼져 있어도 예약 시각에 온다).
- 예약은 **절대 시각**을 `tz.TZDateTime.from(DateTime, tz.local)`로 변환해 넘기면 기기 시간대 패키지가 없어도 순간이 맞다.
- 하루 단위 알림이면 `inexactAllowWhileIdle`로 충분해 "정확한 알람" 권한(`SCHEDULE_EXACT_ALARM`)을 요구하지 않는다. 대신 Android 13+ `POST_NOTIFICATIONS`, 재부팅 후 복원용 `RECEIVE_BOOT_COMPLETED`와 `ScheduledNotificationReceiver`/`BootReceiver`를 매니페스트에 넣고, 플러그인이 요구하는 `coreLibraryDesugaring`을 켠다. 의존성 `timezone` 버전은 플러그인 쪽 요구(예: ^0.11)에 맞춘다 — 다른 앱의 고정 버전을 그대로 옮기면 해결 실패.
- 한계: 기기를 바꾸면 예약이 사라진다. Windows는 앱이 꺼져 있으면 안 올 수 있고 취소가 제한된다.

## 2. 설계 규칙

- **고정 문구**: 알림 본문에 사용자가 쓴 상황·내용을 넣지 않는다(잠금 화면 노출). 누르면 열릴 대상은 payload(`종류:세션 id`)로만 넘긴다.
- **알림 id는 세션 id에서 결정적으로**(해시) 만든다 — 예약 목록을 따로 저장하지 않아도 나중에 같은 id로 취소할 수 있다.
- **구현을 인터페이스 뒤에 둔다**: 기본 `NoReminders`(아무것도 안 함), 기기 구현은 `main()`에서만 끼운다. 테스트는 가짜(예약·취소 기록, 탭 스트림)를 끼운다. 기기 구현을 `main()`에서만 import하면 위젯 테스트가 플러그인을 로드하지 않는다.
- **설정은 기존 설정 스키마의 한 섹션으로**(RVS는 프로필 스키마 `reminders`: 끔/1·3·7일 뒤 + 시각). 스키마·폼·검증이 다른 섹션과 같은 경로로 나온다. 단, 기기 전용 값이므로 **AI 프롬프트에서 빼고**, 채팅 AI가 바꾸지 못하게 한다(섹션 플래그로 구조 힌트·값 변경 경로 둘 다 막는다).
- 알림을 눌러 앱이 **새로 켜진 경우**도 처리한다(`getNotificationAppLaunchDetails` → 첫 로드 뒤 한 번 꺼내 쓰기). 이미 기록돼 있으면 기록된 내용이 보이게 해서 취소 실패(Windows)를 흡수한다.
- 결과를 기록하는 모든 경로에서 예약을 취소한다(기록 화면이 여러 곳에서 열리면 호출 지점이 한 곳인 저장 함수에 건다).
- **물어볼 거리가 없는 결과에는 예약하지 않는다**(RVS 2026-10-31 실기기): AI가 결과를 못 만들어 자리표시 후보만 돌아온 역산에도 "3일 뒤 어떻게 됐나요?"가 예약되고 타임라인에 정상 카드로 남았다. 예약 판단을 "응답이 200인가"가 아니라 "보여 줄 결과가 있는가"(예: `hasNoResult`)에 걸고, 서버도 같은 판정(`is_fallback`)으로 타임라인 기록을 건너뛴다 — 앱만 막으면 다른 클라이언트·옛 앱에서 같은 카드가 생긴다.

## 3. 기본은 "켬", 끄는 건 "끔"만

기록이 서비스의 원료라면 기본을 켠다. 구현은 **"끔"만 끄고 나머지(미설정·모르는 값)는 기본값**으로 해석한다 — 미설정이 꺼짐이면 아무도 켜지 않는다. 첫 예약 때 OS 권한 창이 뜨는 것은 감수하고, 거부하면 예약만 건너뛰고 본 기능은 그대로 둔다. 안내(첫 실행 한 장)에 알림 이유와 끄는 위치를 적는다.

## 4. 효과 측정 — 알림이 기록을 늘리는가

- 기기가 예약하면 서버에 **"N일 뒤 알림 예약"을 표시**한다(서버 시계로 알림 시각 계산 — 기기 시간대와 무관). 표시 호출이 실패해도 알림 자체는 동작한다.
- 집계: (알림 시각이 지난 역산 중 결과를 적은 비율) vs (알림 없이 N일 넘게 지난 역산 중 같은 비율). 둘을 나란히 본다.
- 주의: 기본을 켠 뒤에는 "알림 없음" 표본이 줄어든다(켜기 전 기록이 비교 대상). 한 사람 안의 수치는 건수가 적을 때 우연이므로 전체 합계(개발자 콘솔)로 판단한다. 알림 시각이 지나지 않은 건은 분모에 넣지 않는다.
- **미확인 관리**(RVS 2026-10-31): 기록률만으로는 "아직 기다리는 중"과 "포기된 것"이 섞인다. 알림 시각이 지났는데 기록이 없는 건을 지난 기간(7일 안 / 30일 안 / 만료)으로 나눠 센다 — 만료 기준은 예측 기간과 맞춘다(그 뒤에 적은 결과는 같은 기간의 예측과 비교할 수 없다).
