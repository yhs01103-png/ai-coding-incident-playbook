# 개발 폴더 / 서비스용 폴더 분리 운영 패턴

2026-10-19 신설(같은 날 "제약 모음 + git 밖 스위치"·라벨 규칙·방식 비교 추가). 2026-10-20: 승격 검증 엔진·앱 분리·폴더 라벨·실무 비교 절 추가(맨 끝). 2026-10-21: JudgeCal_Athe 적용 사례 3(맨 끝)과 "엔진·안정화 로직은 제약이 아니다" 구분 추가. 한 프로젝트를 "개발 중 코드로 하는 테스트"와 "실제 서비스 코드로 보고 하는 테스트"로 나눠야 할 때, 폴더 두 개와 스크립트 하나로 분리하는 방법. 원 사례는 JudgeCal_Athe(Flutter 클라이언트 + FastAPI 서버, Railway 배포)이고, 본문 명령은 프로젝트에 종속되지 않게 썼다.

## 언제 쓰나

- 개발 중인 코드가 실제 서비스(GitHub -> 배포 서버)에 섞여 나가면 안 되는데, 서비스와 같은 코드로 점검도 해야 할 때
- 완성된 커밋만 골라 서비스 쪽으로 보내고 싶을 때
- 개발 쪽에서는 실수로라도 GitHub에 푸시되지 않게 하고 싶을 때

## 구조

```
<상위폴더>\
  <프로젝트>\          서비스용 = 원본. git remote: GitHub(origin 등) + dev(fetch 전용). 브랜치 main.
  <프로젝트>_개발\     개발용 = 복사본. git remote 없음. 브랜치 dev.
```

| | 개발용 | 서비스용 |
|---|---|---|
| 폴더 | `<프로젝트>_개발\` | `<프로젝트>\` (기존 원본) |
| 브랜치 | `dev` | `main` (GitHub `main` 추적) |
| remote | 없음 | GitHub, 개발 폴더(`dev`, 푸시 URL 차단) |
| `.env` / `data\` / `venv\` | 자기 것 | 자기 것 |
| 서버 포트 | 8801 | 8800 |
| 실행 | 같은 `start.ps1`(포트는 `.env`에서 읽음) | 같은 `start.ps1` |

흐름: 개발 폴더에서 커밋 -> `promote.ps1`이 서비스용 폴더로 같은 커밋을 cherry-pick -> 서비스용 폴더에서 점검 -> 서비스용 폴더에서 푸시 -> GitHub -> 배포.

**원본을 서비스용으로 두는 이유**: 원본 경로에는 이미 레지스트리, 예약 작업, 설정 파일, venv, 빌드 캐시가 묶여 있다. 원본 이름을 바꾸거나 옮기면 이것들을 전부 고쳐야 한다. 이름이 새로 생기는 쪽을 복사본(개발용)으로 하면 기존 의존이 하나도 안 깨진다.

## 배치 변형 B — 프로젝트 폴더 안에 `개발\`과 `서비스\`

```
<상위폴더>\<프로젝트>\      컨테이너(저장소 아님)
    개발\                  개발용 clone (remote 없음, 브랜치 dev)
    서비스\                서비스용 (GitHub 추적, 브랜치 main)
```

두 환경이 한 폴더 안에 모이고 이름이 대칭이라 보기 좋다. 구조와 흐름(promote, remote 정책, 포트 분리)은 위와 같다.

| | 형제 배치(기본, 위) | 변형 B(컨테이너) |
|---|---|---|
| 새 프로젝트 | 가능 | **가장 쉽다**(비용 0, 아래 "처음부터 만들 때") |
| 기존 프로젝트 전환 | 원본을 그대로 서비스용으로 쓴다. 경로 의존이 안 깨진다 | 원본 폴더를 `서비스\`로 옮겨야 해서 경로 의존을 전부 고쳐야 한다 |
| 개발 폴더 이름 | `<프로젝트>_개발` | `개발` |

**처음부터 만들 때**

```
mkdir <프로젝트> ; cd <프로젝트>
git clone <GitHub URL> 서비스
git clone 서비스 개발
cd 개발 ; git remote remove origin ; git branch -m main dev
```

그다음 "만드는 절차"의 복사 항목(`.env` 포트, `data\`, 로컬 전용 문서, venv 재생성)만 하면 된다. `promote.ps1`의 서비스용 폴더 기본값만 한 줄 바꾼다.

```powershell
[string]$ServiceRoot = (Join-Path (Split-Path -Parent $PSScriptRoot) "서비스")
```

**기존 프로젝트를 변형 B로 전환할 때**

기존 폴더에는 경로에 묶인 것이 많아 비용이 크다. 효과는 폴더 정리뿐이라, 기존 프로젝트는 형제 배치를 유지하고 새 프로젝트에서 변형 B를 쓰는 것을 권한다. 그래도 전환한다면:

1. **이동 제약**: Windows에서는 폴더를 작업 디렉터리로 쓰는 프로세스(에디터, 에이전트 세션, 서버, 터미널)가 하나라도 있으면 이름 변경·이동이 실패한다. 전부 닫고, 상위 폴더에서 연 셸에서 수행한다. 에이전트 세션 안에서는 자기 작업 폴더를 옮길 수 없다.
2. 순서: `<프로젝트>` -> `<프로젝트>_tmp`로 이름 변경 -> 새 `<프로젝트>\` 생성 -> `<프로젝트>_tmp`를 `<프로젝트>\서비스`로 이동 -> `git clone 서비스 개발` 후 remote 제거, 브랜치 `dev`, 복사 항목 반영.
3. **경로 의존을 전수 수정**(옮기기 전에 목록부터 만든다):
   - 작업 스케줄러 등 예약 작업의 실행 경로
   - 에이전트/에디터 로컬 설정에 박힌 절대경로(허용 명령 목록 등)
   - 인덱스·레지스트리·문서에 적힌 폴더 경로(본문 서술, 프롬프트 문자열 포함)
   - venv(절대경로를 품고 있어 재생성), 빌드 캐시(`flutter clean` 등)
   - 에이전트의 프로젝트별 메모리는 폴더 경로 기준이라 새 경로로 옮겨지지 않는다
   - OneDrive 같은 동기화 폴더면 대량 이동이 동기화 부하와 충돌을 만든다
4. `promote.ps1`의 서비스용 폴더 기본값을 위 한 줄로 바꾼다.
5. **서비스용 저장소의 `dev` remote 주소를 새 개발 폴더로 갱신**한다: `git -C 서비스 remote set-url dev <새 개발 폴더 경로>`. 안 하면 promote의 fetch가 실패한다.
6. "검증 체크리스트"를 처음부터 다시 돌린다.

## 만드는 절차

```
cd <상위폴더>
git clone <프로젝트> <프로젝트>_개발        # 로컬 경로로 clone, 원본이 origin이 된다
cd <프로젝트>_개발
git remote remove origin                    # 푸시 대상 자체를 없앤다
git branch -m main dev
```

git 추적 안 되는 실행 파일을 원본에서 복사한다.

| 복사 | 비고 |
|---|---|
| `.env` | 포트 항목만 개발용 값으로 바꾼다(`API_PORT=8801`). 토큰·키는 같아도 된다 |
| `data\` | 개발 데이터의 출발점. 크기가 작을 때만 |
| `.gitignore`로 제외한 로컬 전용 문서(설계도, 결정이력 등) | clone에 따라오지 않는다. 복사하고 이후엔 개발 폴더가 최신본 |
| 에디터·에이전트 로컬 설정 중 필요한 것 | 예: 훅 폴더 |
| `venv\` | 복사하지 않는다. venv는 절대경로를 품고 있어 새로 만든다 |

복사하지 않는 것: 수 GB급 빌드 산출물, 자체 `.git`을 가진 하위 저장소, 빌드 캐시(`build\`, `node_modules\`). 개발 폴더에서 새로 만들면 된다.

```
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

## promote.ps1 (개발 -> 서비스용 이동 스크립트, 이것 하나면 된다)

개발 폴더에 두고 개발 폴더에서 실행한다. 서비스용 폴더 위치는 "자기 폴더 이름에서 `_개발`을 뺀 형제 폴더"로 자동 계산한다.

```powershell
param(
    [Parameter(Mandatory = $true)][string]$Revs,   # 커밋 또는 시작..끝 범위
    [switch]$Push,
    [string]$ServiceRoot = (Join-Path (Split-Path -Parent $PSScriptRoot) ((Split-Path -Leaf $PSScriptRoot) -replace "_개발$", ""))
)
$ErrorActionPreference = "Stop"
$DevRoot = $PSScriptRoot

if (-not (Test-Path (Join-Path $ServiceRoot ".git"))) { Write-Host "[ERROR] 서비스용 폴더 없음: $ServiceRoot"; exit 1 }

# 서비스용 저장소가 개발 커밋을 가져올 수 있게 fetch 전용 remote "dev"를 둔다(푸시 URL은 막는다)
if ((git -C $ServiceRoot remote) -notcontains "dev") {
    git -C $ServiceRoot remote add dev $DevRoot
    git -C $ServiceRoot remote set-url --push dev DISABLED
}
git -C $ServiceRoot fetch -q dev
if ($LASTEXITCODE -ne 0) { exit 1 }

if ($Revs -match "\.\.") { $commits = git -C $DevRoot rev-list --reverse $Revs } else { $commits = git -C $DevRoot rev-list --no-walk $Revs }
if (-not $commits) { Write-Host "[ERROR] 커밋을 찾지 못함: $Revs"; exit 1 }

foreach ($c in $commits) {
    Write-Host "[promote] $($c.Substring(0,7)) $(git -C $DevRoot log -1 --format=%s $c)"
    git -C $ServiceRoot cherry-pick -x $c   # -x: 메시지 끝에 원래 개발 커밋 해시를 남겨 출처를 추적한다
    if ($LASTEXITCODE -ne 0) { Write-Host "[ERROR] 충돌. $ServiceRoot 에서 해결 후 git cherry-pick --continue (또는 --abort)"; exit 1 }
}

if ($Push) {
    $remote = git -C $ServiceRoot remote | Where-Object { $_ -ne "dev" } | Select-Object -First 1
    $ErrorActionPreference = 'Continue'   # push 진행 메시지(stderr)를 PS 5.1이 오류로 바꾸지 않게 — 아래 함정 17
    git -C $ServiceRoot push $remote main 2>&1 | ForEach-Object { "$_" }
    $code = $LASTEXITCODE
    $ErrorActionPreference = 'Stop'
    if ($code -ne 0) { Write-Host "[ERROR] 푸시 실패"; exit 1 }
}
```

저장 시 UTF-8 **BOM 포함**으로 저장한다(아래 함정 2).

## 포트를 `.env`에서 읽는 시작 스크립트

두 폴더가 같은 `start.ps1`을 쓰되 포트만 `.env`로 갈린다.

```powershell
$port = 8800
$portLine = Select-String -Path (Join-Path $root ".env") -Pattern "^API_PORT=(\d+)" | Select-Object -First 1
if ($portLine) { $port = [int]$portLine.Matches[0].Groups[1].Value }
$env:<클라이언트_API_주소_환경변수> = "http://127.0.0.1:$port"
```

## 함정 (원 사례에서 실제로 겪은 것)

1. **git worktree로 분리하면 푸시를 못 끊는다.** worktree는 같은 `.git`을 공유해서 remote 설정도 같이 보인다. 개발 쪽 푸시를 막으려면 pre-push 훅이 필요한데, 훅은 git에 포함되지 않는 로컬 파일이라 clone 때마다 다시 만들어야 한다. GitHub에 브랜치를 2개 두는 안도 불필요해진다. 별도 clone + 개발 쪽 remote 제거가 가장 단순하고 확실하다("No configured push destination").
2. **BOM 없는 UTF-8 `.ps1`의 한글은 Windows PowerShell 5.1에서 깨진다.** 스크립트 메시지가 `?`로 나온다. BOM을 붙인다(기존 `.ps1`이 BOM으로 시작하는지 확인하면 된다).
3. **`$ErrorActionPreference = "Stop"` 아래에서 없는 remote를 `git remote get-url dev 2>$null`로 조회하면 PS 5.1이 오류로 중단한다.** stderr가 오류 레코드로 바뀌기 때문이다. 조회 대신 `git remote` 목록에 이름이 있는지 `-notcontains`로 확인한다.
4. **이미 옮긴 커밋을 다시 cherry-pick하면 빈 커밋 상태로 멈춘다**("You are currently cherry-picking"). `git cherry-pick --skip`으로 건너뛴다. 스크립트 테스트 때 같은 커밋으로 두 번 돌리지 않는다.
5. **cherry-pick은 서비스 쪽에서 새 해시를 만든다.** 개발 폴더와 서비스용 폴더의 같은 변경이 다른 커밋 해시를 가진다. 접두사 구간(처음부터 어느 지점까지 전부)을 옮길 때만 `git merge --ff-only`로 해시를 같게 유지할 수 있다.
6. **`.gitignore` 제외 폴더는 clone에 따라오지 않는다.** 설계 문서처럼 로컬 전용이지만 계속 갱신하는 것은 복사 시점 이후 한쪽(개발)을 최신본으로 정하고, 다른 쪽(서비스용)은 오래된 사본이 된다는 걸 문서에 적어 둔다.
7. **DB 파일은 git으로 가지 않는다.** 푸시로 배포 서버의 DB가 바뀌지 않는다. 두 로컬 폴더의 DB도 서로 별개다. 배포 서버 DB는 그쪽 볼륨에 별도 절차로 올려야 한다.
8. **GitHub 푸시는 외부에 보이는 동작이다.** `-Push`는 사용자가 명시했을 때만 쓴다. 기본은 서비스용 폴더에 옮기는 데서 멈추고 점검 후 그 폴더에서 푸시한다.
9. **Flutter 명령(`analyze`, `test`)이 생성 파일을 바꿔 놓는다**(예: `windows/flutter/generated_plugin*`). 커밋하지 않는다. 서비스용 폴더에 이런 변경이 남아 있어도 cherry-pick은 겹치지 않는 한 진행된다.

10. **promote 뒤 두 폴더를 `diff`로 비교하면 줄바꿈 때문에 "다르다"고 나온다.** `core.autocrlf=true`인 Windows에서 git이 서비스용 폴더에는 CRLF로 다시 쓰기 때문이다. 내용 비교는 `diff -rq --strip-trailing-cr`로 한다.
11. **로컬 전용으로 제외해 둔 문서(설계도·결정이력)를 git 추적으로 바꿀 때**:
    - 두 폴더가 같은 문서를 갖게 하려면 추적이 가장 단순하다(promote가 그대로 옮긴다).
    - 먼저 **GitHub 저장소가 비공개인지** 확인한다. 인증 없이 `curl https://api.github.com/repos/<소유자>/<저장소>`가 404면 비공개(또는 없음)다. 공개면 올리지 않는다.
    - 올리기 전에 문서에 비밀값 패턴(API 키, 토큰, 개인키)이 없는지 스캔한다.
    - `.gitignore`의 제외 줄 자리에 "언제, 왜 추적하는지, 공개 전환 전에 다시 제외할 것"을 주석으로 남긴다.
    - 문서 종류에 따라 커밋 정책을 정해 둔 규칙이 있으면(예: 결정이력은 커밋, 코드로 재생성되는 스냅샷은 제외 권장) 먼저 확인한다.
12. **세션이 폴더 역할을 알게 한다.** 에이전트 세션은 폴더 경로로 프로젝트를 구분하므로, 어느 폴더가 개발용이고 어느 폴더가 서비스용인지 README 맨 앞에 "작업 폴더" 섹션으로 적는다. README는 promote로 양쪽 폴더에 같이 간다.

## 개발/서비스를 "다르게 동작"시키기 — 제약 모음 + git 밖 스위치 (2026-10-19 추가)

폴더를 나눈 목적이 "개발 폴더는 제약 없이 화면을 테스트하고, 서비스용은 실제 사용자 제약을 건 상태"라면, 코드를 두 갈래로 키우지 말고
**제약만 한곳에 모은 뒤 폴더마다 다른 것은 git 밖 스위치 파일 하나**로 줄인다. 그래야 promote(커밋 이동)가 계속 충돌 없이 돈다.

### 구조

```
<서버>/constraints/
  rules.<ext>     실제 제약 — 하루 한도·광고 요구·레이트리밋·시즌 상한·잠금 해제 조건 …(기존 코드에서 추출)
  noop.<ext>      rules와 같은 이름의 "아무것도 안 막는" 구현
  __init__.<ext>  오케스트레이션 — 스위치 파일이 있으면 그것을, 없으면 rules를 쓴다. 기능 코드는 여기만 import한다
  _active.<ext>   스위치(한 줄, git 밖) — 개발 폴더에만 둔다: noop을 쓰라
<클라이언트>/…/constraints/   같은 모양(rules / noop / active)
```

- **두 폴더에 똑같이 있는 것**: rules, noop, 오케스트레이션, 기능 코드 안의 호출 한 줄. 평소 커밋으로 개발 → 서비스로 옮겨진다.
- **폴더마다 다른 것**: 스위치 파일 하나. `.gitignore`에 넣어 커밋 자체가 생기지 않게 한다 — promote로 넘어갈 수도, 충돌할 수도 없다.
- **기본값은 제약이 걸린 쪽(rules)**: 스위치 파일이 없으면 rules. 서비스용 폴더와 배포 서버(GitHub에서 받아 배포 — 스위치 파일이 없다)는 자동으로 제약이
  걸리고, 파일을 지우거나 잊어도 안전한 쪽으로 넘어간다. 배포 가드가 있으면 "배포 환경인데 noop이 연결됨"이면 시작을 거부하는 줄을 하나 더 둔다.
- **이름 짝 보장 테스트**: "rules와 noop이 같은 공개 이름을 모두 갖는다"를 테스트로 건다. noop에 짝을 빠뜨리면 개발 폴더만 import 오류가 나는 사고를 막는다.
- **호출부는 한 줄**: 기능 코드 사이에 제약 로직을 섞지 않는다(`constraints.check_daily_limit(...)` 한 줄). 개발 커밋이 제약 코드 근처를 건드릴 일이 없어
  cherry-pick 충돌이 거의 사라진다.
- **새 제약을 추가할 때**: 개발 폴더에서 rules에 실제 구현, noop에 빈 구현, 기능 코드에 호출 한 줄 → 평소처럼 커밋·promote → 서비스용은 이미 rules를
  보고 있어 바로 걸린다. 스위치·라벨은 건드리지 않는다.

### 무엇을 "제약"으로 모으나

| 모은다(개발에서 끄고 싶은 운영 제약) | 모으지 않는다(게임·업무 규칙) |
|---|---|
| 하루 횟수 한도, 광고 시청 요구, 레이트리밋, 시즌·주기 상한, 잠긴 콘텐츠·진행 게이트, 실시간 대기(자동 판정 타이머 등), 결제 스토어 의존 | 잔액 부족, 이미 소유, 정원 초과처럼 데이터 무결성을 지키는 규칙 — 끄면 데이터가 깨진다. 개발 중엔 대신 "치트"(잔액 넣기 등) 도구로 우회한다 |

판단 기준: **"이 검사가 없어도 데이터는 맞는가?"** — 맞으면 운영 제약(모은다), 깨지면 규칙(남긴다).

**엔진·안정화 로직은 제약이 아니다(2026-10-21, JudgeCal 사용자 지적)**: AI 호출의 폴백 모델·시간 배정·요청 마감·계측·연결 확인처럼 "개발에서 끌 이유가 없고 두 폴더가 같게 동작해야 하는" 일반 코드는
`constraints/`에 넣지 않는다. 넣으면 개발 폴더에서만 꺼져 서비스용과 다른 동작을 검증하게 된다. 개발 폴더에서 구현·커밋해 promote로 양쪽에 똑같이 보내고, 값(시간 상한 등)만 환경변수로 조절한다.
구분이 헷갈리면 "사용자가 개발 중에 이 기능을 끄고 화면을 테스트하고 싶은가?" — 그렇다면 제약, 아니면 일반 코드.

### 커밋 라벨 — 서비스용 직접 커밋만 `[service]`

- 개발 폴더 커밋에는 라벨을 달지 않는다. 서비스용에 있는 커밋은 "개발에서 옴" 아니면 "서비스용에서 직접"뿐이라, 직접 커밋만 표시하면 구분된다.
- 개발에서 온 커밋의 출처는 promote의 `git cherry-pick -x`가 메시지 끝에 `(cherry picked from commit <개발 해시>)`로 자동으로 남긴다.
- 서비스용 폴더에 commit-msg 훅을 두어 `[service]` 없는 직접 커밋을 거부한다(아래). 훅은 git이 옮겨 주지 않는 로컬 파일이라 서비스용 clone마다 다시 만든다.
  cherry-pick은 commit-msg 훅을 거치지 않으므로 promote는 막히지 않는다.

```sh
#!/bin/sh
# 서비스용 폴더 .git/hooks/commit-msg — 직접 커밋은 [service] 라벨 필수(개발에서 옮긴 커밋은 cherry-pick이라 이 훅을 안 거친다)
head -1 "$1" | grep -q '^\[service\]' || { echo "서비스용 폴더 직접 커밋은 제목을 [service]로 시작하세요"; exit 1; }
```

**왜 개발 쪽 라벨(`[dev]`)이 필요 없나**: 라벨을 "promote에서 뺄 커밋" 표시로 쓰면, 스위치를 git에 넣어 둔 경우 개발 폴더의 "noop 연결" 커밋도 평범한
`[dev]` 커밋과 구별되지 않아 그대로 넘어가 서비스용 스위치를 **조용히 noop으로 덮는다**(충돌로 멈추지도 않아 더 위험하다). 빼야 할 커밋을 라벨로 고르지 말고,
빼야 할 것 자체를 git 밖으로 보내는 것이 근본 해결이다.

### 세 방식 비교 — 어떤 걸 고르나

| 기준 | A. 코드 하나 + 설정 스위치(환경변수) | B. 폴더 분리 + 제약 모음 + git 밖 스위치(이 절) | C. 한 폴더 + 브랜치 둘 |
|---|---|---|---|
| 차이를 두는 곳 | 설정값 | 스위치 파일 하나 | 브랜치별 커밋 |
| 서비스 코드에 개발용 분기 | 섞임(가드로 막음) | noop 구현이 섞이지만 연결 안 됨 | 안 섞임 |
| 충돌 | 거의 없음 | 거의 없음(호출부 한 줄 원칙) | 제약 근처를 고치면 남 |
| 개발 코드가 원격에 올라감 | promote한 것만 | 절대 안 올라감(원격 없음) | 개발 브랜치 푸시 시 올라감(실수 가능) |
| 개발·서비스 동시 실행 | 가능 | 가능(포트·DB 분리) | 어려움(브랜치 전환) |
| 오갈 때 비용 | 없음 | 없음 | 브랜치 전환·재빌드 |
| 클라우드/원격 세션 | 서비스 코드만 | 서비스 코드만 | 개발 브랜치도 봄 |

- 개발 코드를 원격에 절대 올리지 않으면서 두 환경을 동시에 돌려 비교하려면 **B**.
- 폴더를 늘리고 싶지 않고 충돌 없는 단일 코드가 최우선이면 **A**.
- 원격 세션(클라우드)이 개발 코드도 봐야 하면 **C** — 대신 실수 푸시·브랜치 전환 비용을 감수한다.

## 검증 체크리스트

- [ ] 개발 폴더에서 `git remote` 출력이 비어 있고 `git push`가 "No configured push destination"으로 실패한다
- [ ] 서비스용 폴더에서 `git remote -v`에 GitHub과 `dev`(push는 DISABLED)가 있다
- [ ] 개발 `.env`의 포트가 서비스용과 다르다. 두 서버를 동시에 띄워 둘 다 `/health`가 응답한다
- [ ] 개발 폴더에서 더미 커밋 1개를 만들고 `.\promote.ps1 <해시>`로 서비스용 폴더에 같은 변경이 생긴다
- [ ] 서비스용 폴더에서만 푸시가 된다(처음 1회는 사용자 확인 후)

**첫 푸시 전 점검**

- [ ] 올라갈 커밋 목록 확인: `git log <원격>/main..main --oneline`
- [ ] 올라갈 변경에서 비밀값 패턴 스캔(추가된 줄만): `git diff <원격>/main..main | grep "^+"`에 API 키·토큰·개인키 패턴
- [ ] `.env`, `*.db`가 추적되지 않는다: `git ls-files | grep -E "\.env$|\.db$"`가 비어 있다
- [ ] 저장소가 비공개다(설계 문서를 추적하는 경우 필수)
- [ ] 서비스용 폴더의 작업 트리에 도구가 만든 변경(생성 파일 등)이 남아 있지 않다

## 한계

- 개발이 서비스보다 오래 앞서가면 cherry-pick 충돌이 늘어난다. 자주, 작게 옮긴다.
- 두 폴더가 같은 프로젝트인데 디스크 사본이 둘이라 용량이 두 배다(대형 산출물은 복사하지 않는 이유).
- 에이전트 세션의 프로젝트별 메모리·설정은 폴더 경로 기준이라 개발 폴더는 새 프로젝트로 인식된다. 필요한 메모리는 따로 옮겨야 한다.

추가 함정(이 사례에서 실제로 겪음):

13. **PowerShell 5.1은 `param()` 기본값을 계산할 때 `$PSScriptRoot`가 비어 있다**(`-File`로 실행) — `Split-Path -Parent $PSScriptRoot`가
    "빈 문자열" 오류로 멈춘다. 기본값은 비워 두고 본문에서 `$PSScriptRoot`(없으면 `$MyInvocation.MyCommand.Path`)로 계산한다.
14. **이미 옮긴 커밋을 다시 cherry-pick하면, 뒤 커밋이 같은 파일을 또 바꾼 경우 빈 커밋이 아니라 add/add 충돌로 멈춘다** — 함정 4의 `--skip`만으로는
    부족하다. 옮기기 전에 서비스용 폴더에서 `git cherry <서비스 브랜치> dev/<개발 브랜치>`로 내용(patch-id) 기준 "이미 옮김(-)" 목록을 만들어 건너뛴다.
15. **같은 셸에서 두 폴더의 서버를 번갈아 켜면 `.env`에서 읽은 환경변수(`API_PORT`)가 남아 다른 폴더 서버가 엉뚱한 포트로 뜬다** — 시작 스크립트가
    `.env`를 읽기 전에 그 변수를 먼저 지운다.
16. **클라우드 세션 협업(원격 브랜치 푸시)과 함께 쓰면** 클라우드는 GitHub에 있는 서비스용 코드만 본다 — 클라우드 브랜치를 서비스용에 받은 뒤 개발 폴더에도
    같은 커밋을 당겨 와야 두 폴더가 안 갈라진다.
17. **PS 5.1 + `$ErrorActionPreference='Stop'`에서 `git push`는 성공해도 실패로 끝난다** — git이 "To https://..." 진행 메시지를 stderr로 내고,
    PS 5.1은 그걸 NativeCommandError로 바꿔 스크립트를 멈춘다(exit 1, 실제로는 GitHub에 올라감). push 줄만 `Continue`로 두고 `2>&1 | ForEach-Object { "$_" }`,
    판정은 `$LASTEXITCODE`로. 이런 일이 생기면 `git fetch` 뒤 `git status -sb`로 실제 반영 여부부터 확인한다.

운영 기록(2026-10-20, 분리 뒤 첫 기능 사이클): 기능 커밋 2개를 개발 폴더에서 라벨 없이 커밋 → `promote.ps1 <첫 커밋>..<끝 커밋> -Push` 한 번으로
서비스용 master에 옮기고 GitHub까지. promote 전에 `git check-ignore -v server/app/constraints/_active.py`로 스위치가 git 밖인지 확인 — 개발 폴더는
noop으로 돌고, 옮겨진 커밋에는 스위치가 없으니 서비스용·Railway는 rules만 본다. 서비스용에서 직접 고칠 일이 생기면 그때만 `[service]` 라벨.

## 승격 검증 엔진 · 앱 분리 · 폴더 라벨 (2026-10-20 추가, poker_app 적용)

위 절차가 "옮기기"였다면 이 절은 "옮겨도 되는지 확인하고, 통과한 것만 푸시"와 "폰에 개발앱·서비스앱을 같이 설치"를 더한 것이다.

### 스크립트 구성 — 연결점 2개 + 엔진 1개 + 푸시 1개

| 위치 | 파일 | 역할 |
|---|---|---|
| 개발 연결점 | `promote.ps1` | 엔진 Plan 호출 → cherry-pick → 서비스 연결점 호출. 검증 로직은 갖지 않는다 |
| 서비스 연결점 | `service_gate.ps1` | 서비스용 폴더에서 직접 실행하는 입구. 엔진 Verify를 부를 뿐 |
| 엔진 (서비스 위치, 1개) | `gate_engine.ps1` | 모든 검증이 여기 한 곳 |
| 푸시 (서비스 위치) | `push_verified.ps1` | 표식을 받아 푸시만. 강제 푸시 없음 |

- **엔진을 서비스 위치에 두는 이유**: ① 서비스용에서 직접 한 커밋만 있는 사이클이 개발 폴더 없이 돌아야 한다. ② 검증기가 검증 대상과 같이 바뀌지 않는다(개발 폴더에서
  막 고친 엔진으로 자기 자신을 통과시키는 일을 막는다). 스크립트는 git에 올라가 두 폴더에 같은 복사본이 있으므로(정합성 검사 대상) 어느 쪽을 실행해도 내용은 같다.
  단 서비스용에 엔진이 아직 없는 처음 한 번은 promote가 개발 폴더 복사본으로 Plan을 돌린다.
- **Plan(옮기기 전)**: 옮길 개발 커밋이 폴더별 파일(스위치·`.env`·키스토어·DB·로컬 전용 도구)을 건드리지 않는가 / 서비스용에 푸시 대기 중인 `[service]` 커밋과 같은 파일을
  건드리지 않는가(겹치면 옮기다 충돌하고 정합성 비교에서 가려진다) / 제약 짝 테스트. 어긋나면 아무것도 옮기지 않는다.
- **Verify(옮긴 뒤 또는 서비스 전용 커밋만 있을 때)**: 푸시 대기 커밋(`origin/<브랜치>..<브랜치>`)을 분류 — 승격(메시지에 `cherry picked from commit`) / 서비스 전용(제목 `[service]`) /
  그 외는 거부. 서비스용에 제약 스위치 파일·`dev` 라벨이 없는가, 승격 커밋은 출처 개발 커밋과 내용이 같은가(서비스 전용 커밋이 건드린 파일만 예외),
  서비스 전용 커밋은 허용 경로 목록(`service_only_paths.txt`, 비어 있으면 전부 거부 — 이 파일 자체도 개발 폴더에서만 바뀐다)만 건드렸는가, 제약 짝 테스트(서비스용 = 운영 제약 모드).
  통과하면 `.git\promote_verified`에 브랜치 해시를 기록. `push_verified.ps1`은 표식이 있고 해시가 지금 브랜치와 같을 때만 푸시한다(검증 뒤 커밋이 생기면 거부).
- 푸시는 `-Push`를 줄 때만(밖으로 나가는 동작). 서비스 전용 커밋만 있으면 서비스용에서 `service_gate.ps1 -Push` 한 번.
- 엔진이 보는 것은 **넘어올 때의 관문**이다. 제약 동작 자체는 전체 테스트와 서비스 서버 실물 확인(`/client-constraints` 등)의 몫.

### 개발앱 / 서비스앱 분리 (Android)

- 앱 ID 뒤에 `.dev`(+ `versionNameSuffix`)와 별도 라벨을 붙이면 같은 서명으로도 한 폰에 둘 다 설치된다. 서명과 앱 ID가 같으면 한 번에 하나만 깔리고 로컬 저장소도 하나라
  개발 서버에서 쌓은 진행이 서비스 서버 검증에 섞인다 — 제약 검증이 목적이면 분리한다. 대가: 소셜 로그인(구글 등)의 앱 자격이 패키지명+서명 기준이라 `.dev` 패키지를 따로 등록해야 개발앱에서 된다(게스트 로그인은 무관).
- 서버는 앱 ID와 무관하게 **빌드한 폴더의 포트**(`server\.env`)로 정해진다. 서버가 다르면 DB도 다르고, 같은 서버여도 기기 ID가 설치마다 랜덤이라 앱이 다르면 계정도 다르다.
- 무엇이 개발앱인지는 폴더 이름이 아니라 **폴더 안의 라벨 파일**(git 밖, 내용 `dev`|`service`)이 정한다. 폴더마다 처음 한 번 `label_folder.ps1 -As dev|service`.
  빌드 스크립트는 라벨 없는 폴더의 빌드를 거부하고 `-Which dev|service`로 라벨 폴더를 찾아 빌드한다. gradle도 같은 파일을 직접 읽는다(파일이 없으면 서비스앱 = CI용 기본값,
  환경변수가 우선). 폴더 이름이 바뀌어도 라벨은 따라가고, 새로 clone하면 다시 붙인다(스위치 파일과 같은 성격).

### 새로 겪은 함정 (18~20)

18. **PowerShell 함수 안의 파이프 출력은 반환값에 섞인다.** `& $cmd | ... | Select-Object` 뒤 `return $LASTEXITCODE`를 하면 반환값이 `[출력 줄..., 코드]` 배열이 되어
    `$code -ne 0`이 항상 참 — 테스트가 통과해도 실패로 판정된다. 출력은 `Write-Host`로, 반환은 `[int]` 하나로.
19. **`git cherry-pick`/promote 범위 `A..B`는 A를 제외한다.** `HEAD~1..HEAD`는 마지막 한 개뿐이라, 앞 커밋을 건너뛰고 뒤 커밋만 옮기다 충돌한다. 중단된 cherry-pick은
    `git -C <서비스용> cherry-pick --abort`로 원래 상태로 되돌린 뒤 `<직전에 옮긴 커밋>..HEAD`로 다시. 마지막 한 개는 `HEAD`.
20. **스크립트 문자열에 `\a`·`\b`를 일반 문자열로 넣으면 제어문자(벨·백스페이스)가 된다.** 경로 주석을 코드 생성 스크립트로 쓰다 `android\app...`이 `android<BEL>pp...`로 깨져
    라벨 판정 경로가 틀어졌다. 생성은 raw 문자열로, 끝나면 `[\x00-\x08\x0b\x0c\x0e-\x1f]` 개수가 0인지 확인.

### 실무와의 차이 (정밀 비교, 2026-10-20)

같은 것: ① Android 환경별 앱 분리(Flutter 공식 `flavors` = Gradle productFlavors + `applicationIdSuffix` + 라벨 placeholder). 이 패턴은 `--flavor` 대신 라벨 파일·환경변수로
직접 구현한 것 — 공식 방식이 IDE·`flutter run --flavor` 지원이 낫다. ② 환경별 서버·DB·변수 분리(Railway Environments도 환경마다 변수·네트워킹·DB를 격리). ③ 환경별 소셜 로그인 자격.
④ 스위치가 없으면 운영 제약이 켜지는 안전한 기본값 + 배포 가드.

다른 것:
1. **물리적 폴더 2개 + cherry-pick 승격은 비표준.** 보통은 저장소 하나에서 기능 브랜치 → PR → 병합하고, 개발/staging/운영은 코드 폴더가 아니라 **배포 대상**(같은 코드를 환경 설정만 달리 올린다 —
   build once, deploy many). cherry-pick은 핫픽스를 옛 릴리스에 되옮길 때 주로 쓴다. 폴더 방식의 대가: 커밋 해시가 갈라져 `-x` 출처 꼬리표·patch-id 대조가 필요, 디스크 2배, 충돌 위험.
   얻는 것: 개발 쪽에서 실수로도 GitHub에 못 올림, 서비스와 같은 코드로 로컬 점검. 1인 개발의 사고 방지 장치로는 의미가 있다.
2. **관문이 로컬 스크립트다.** 실무는 서버가 강제한다(GitHub Actions 필수 검사 + 브랜치 보호 + 배포 환경 승인). 로컬 관문은 `git push`를 직접 치면 우회된다. 단 GitHub Free의
   비공개 저장소에서는 보호 브랜치가 적용되지 않을 가능성이 커서(공식 문서가 Pro/Team의 비공개 저장소 기능으로 분류, 규칙셋은 공식 페이지로 확정 못 함 — 요금제 확인 필요)
   로컬 관문이 현실적 대안이다. 보완: 기존 CI(`.github/workflows`)에 "추적 금지 파일 없음" 같은 검사를 얹으면 푸시 뒤에라도 GitHub가 잡는다(사전 차단은 아님).
3. **제약 전환을 git 밖 스위치 파일로 한다.** 표준은 서버 환경변수(`APP_ENV` 등)다 — 같은 코드가 환경변수만 달리 돈다(운영 서버 = 제약 켬, 개발 PC = 풀림). 클라이언트가 제약을 들고 있지 않고
   붙은 서버의 응답을 따르는 점은 같다. 폴더별 `.env`가 이미 git 밖이므로 스위치 파일 대신 `.env` 한 줄로 바꾸는 쪽이 표준에 가깝다(개선 후보).
4. **Railway(또는 유사 PaaS)를 쓰면 상당 부분이 불필요해진다.** staging 환경을 `staging` 브랜치에서 자동 배포하고 운영 환경은 `main`에서 배포하면 로컬 서비스용 폴더·promote·게이트가 하던
   "운영 제약으로 검증"을 그 환경이 대신한다. 이 패턴은 배포 환경이 아직 없거나 1인 개발에서 로컬만으로 안전망을 두고 싶을 때 의미가 있다. 앱 분리·환경별 서버/DB·안전한 기본값은 그 뒤에도 유효.
5. **모바일 릴리스**: 운영 빌드 검증은 Play Console 내부 테스트 트랙, 서명은 릴리스 키(Play App Signing)를 따로 둔다. debug 키 공용은 개발 단계 한정.

### 푸시 브리핑·사용자 승인 (2026-10-20 추가)

검증이 통과해도 GitHub로 나가는 마지막 동작은 **사람이 브리핑을 보고 승인**해야 간다. 푸시 스크립트(`push_verified.ps1`)가 맡는다.

- **브리핑 내용**: 원격 URL·브랜치, 올라갈 커밋 목록(오래된 순, 제목은 110자까지), 변경 규모(`git diff --shortstat`), 검증 결과(표식에 적힌 승격/서비스 전용 개수·시각, 표식 해시 = 지금 브랜치), 승인 코드.
- **승인 코드** = 검증한 커밋 해시 앞 8자리. 브리핑 뒤에 커밋이 생기면 코드가 달라져 거부된다(검증하지 않은 커밋이 같이 나가는 것을 막는다).
- **세 갈래**:
  1. 사람이 터미널에서 직접 실행(대화창 있음) → `y/N` 질문. 아니면 종료 코드 4(취소, 표식은 그대로).
  2. 대화창이 없는 실행(AI 코딩 도구·CI) → 브리핑을 출력하고 **종료 코드 3(승인 대기)**으로 멈춘다. 도구는 브리핑을 사용자에게 요약해 전하고, 사용자가 승인하면 `-Approve <코드>`로 다시 실행한다. 승인 없이 `-Approve`를 붙이지 않는다.
  3. `-Approve <코드>`가 맞으면 푸시. 틀리면 종료 코드 1.
- **종료 코드 전달**: 푸시 스크립트를 부르는 엔진·승격 스크립트는 3(승인 대기)·4(취소)를 "실패"로 보지 않고 그대로 올린다(안 그러면 "검증 실패"로 오해해 표식을 지운다).
- **우회 금지**: `-Push` 플래그가 있어도 승인 단계는 건너뛰지 않는다. "그냥 푸시" 옵션을 두지 않는다.

함정 21~22 (이 단계에서 겪을 것):

21. **한글 출력 깨짐(인코딩)** — Windows PowerShell 5.1의 콘솔 출력과 native 명령 출력 디코딩 기본은 OEM 코드페이지라 한글 커밋 제목이 `?`로 깨진다. ① 스크립트는 BOM 있는 UTF-8로 저장, ② 시작에서 `[Console]::OutputEncoding`과 `$OutputEncoding`을 UTF-8(BOM 없음)로(출력이 파이프로 잡히면 설정이 던질 수 있어 `try`), ③ git은 `-c core.quotepath=false -c i18n.logOutputEncoding=UTF-8`로 커밋 제목을 뽑는다. 만든 뒤 제어문자(`[\x00-\x08\x0b\x0c\x0e-\x1f]`)가 0개인지 확인.
22. **비대화형 실행에서 `Read-Host`는 쓸 수 없다** — 입력이 막혀 있거나 빈 값을 받아 "취소"로 끝난다. 대화창 유무를 `[Environment]::UserInteractive -and -not [Console]::IsInputRedirected -and -not [Console]::IsOutputRedirected`로 판정하고, 아니면 질문하지 말고 종료 코드(3)로 승인을 요청한다.

### 승인 요청 절차 — AI 코딩 도구(Claude Code 등) 사용 규칙과 실제 확인 (2026-10-21 추가)

- **도구가 할 일**: 푸시를 요청받으면 먼저 스크립트를 그대로 실행해 브리핑을 받는다(종료 코드 3). 그 브리핑을 **사용자에게 요약해 전한다** — 올라갈 커밋 수·핵심 변경 한두 줄·변경 규모·검증 결과(표식·테스트)·원격·승인 코드. 사용자가 승인하면 그때만 `.\push_verified.ps1 -Approve <코드>`로 다시 실행한다.
- **하지 않을 것**: 사용자 승인 없이 `-Approve`를 붙이기, 요청 문장에 "푸시"가 들어 있다는 이유로 승인을 갈음하기(요청 ≠ 승인 — 브리핑을 보고 확인받는 단계가 따로 있다), 검증 뒤 커밋이 늘었는데 옛 코드로 재시도하기(코드가 다르면 거부되니 브리핑부터 다시).
- **프로젝트 규칙에 같이 적기**: 프로젝트 `CLAUDE.md`(세션 협업 방식)와 도구의 메모리에 같은 절차를 남긴다 — 세션이 바뀌어도 브리핑·승인 단계를 건너뛰지 않게.
- **실제 확인(poker_app, 2026-10-20)**: 비대화형 실행 → 브리핑 + `승인 필요 — .\push_verified.ps1 -Approve fe3b0801`, 종료 코드 3, 푸시 안 됨 / 틀린 코드(`00000000`) → 거부, 종료 코드 1, 푸시 안 됨 / 한글 커밋 제목·원격·변경 규모가 깨지지 않고 출력. 서비스용 폴더는 그대로 "GitHub보다 N개 앞섬" 상태로 남는다.

### 스크립트가 두 폴더에 똑같이 있는 것 (질문 기록)

개발 폴더와 서비스용 폴더에 승격 스크립트(`promote.ps1`·`gate_engine.ps1`·`service_gate.ps1`·`push_verified.ps1`)가 똑같이 있다. **연결에 필요해서가 아니라 스크립트가 git에 추적되기 때문**이다 — 같은 저장소이고 promote가 추적 파일을 서비스용으로 옮기므로 복사본이 생긴다. 실행은 쓰는 쪽 하나만: 개발 폴더는 `promote.ps1`(그리고 처음 한 번 엔진 Plan), 서비스용 폴더는 `service_gate.ps1`·`gate_engine.ps1`·`push_verified.ps1`. 나머지 복사본은 쓰이지 않고 그대로 놓인다. 연결은 파일 복사가 아니라 **경로**다 — `promote.ps1`이 서비스용 폴더 경로를 `-ServiceRoot`(기본: 폴더 이름의 `_개발` 접미사를 뗀 형제 폴더)로 알아내 그 안의 엔진·게이트를 부른다.
스크립트를 고친 커밋은 이미 서비스용에 올라가 있던 **이전 버전의 엔진으로 먼저 Plan 검증**을 받고 옮겨진 뒤부터 새 버전이 실행된다(처음 한 번만 서비스용에 엔진이 없을 때 개발 복사본으로 Plan).

## 적용 사례 3 — JudgeCal_Athe(Flutter 클라이언트 + FastAPI 서버, 형제 배치, 2026-10-19~21)

원 사례였던 이 프로젝트는 처음에 "promote 하나"만 있었고, 위 poker_app 방식(검증 엔진·제약 모음·라벨·푸시 승인)을 뒤늦게 이식했다. 달라진 점만 적는다.

- **브랜치·remote 이름**: 서비스용 브랜치가 `main`, GitHub remote 이름이 `origin`이 아니라 `judgecal-app`이다. 엔진·푸시 스크립트는 브랜치를 상수로 두고 GitHub 쪽을 "`dev`가 아닌 첫 remote"로 찾는다.
- **제약 모음**: 모은 것은 크레딧제·게스트 발급 한도 2종·힌트 쿨다운·음수 티어 해금(운영 제약 5개). 이미 `.env`로 갈리던 값(`CREDITS_ENFORCED`)은 rules가 그 값을 그대로 읽게 하고 noop은 "끄기"만 맡겨 기존 환경변수 방식과 충돌하지 않게 했다.
  클라이언트에는 모을 운영 제약이 없어(광고·결제·시즌 상한 없음) 클라이언트용 제약 패키지는 만들지 않았다 — 조사해서 "없음"을 확인하는 것도 결과다. 위 "엔진·안정화 로직은 제약이 아니다" 구분은 이 사례의 사용자 지적에서 나왔다.
- **푸시 승인**: poker_app 방식에 더해 미리보기에 **추가된 줄의 비밀값 패턴 스캔**(API 키·개인키·토큰 대입)과 원격 URL을 넣었다. 승인 코드는 해시 앞 7자리(표식은 40자리 전체 비교). 미리보기는 `.git\push_preview.txt`(UTF-8)에도 저장.
  종료 코드 0 성공 / 1 실패 / 3 승인 필요 / 4 취소. `promote.ps1 -Push`는 3·4를 실패가 아니라 "푸시만 대기"로 보고한다. 실제 확인: 서비스용 폴더에서 비대화형 실행 → 한글이 깨지지 않은 미리보기 + 코드 3 / 틀린 코드 → 코드 1 / 두 경우 모두 푸시 안 됨.
- **서비스용 `.env`의 운영 스위치**: 서비스용 폴더 `.env`에 크레딧제가 켜져 있으면 게스트(헤더 없는) 요청의 AI 호출이 막힌다. 서비스용 코드로 실제 AI 호출을 측정할 때는 프로세스 환경변수로만 덮어쓰고(`load_dotenv`는 이미 있는 환경변수를 덮어쓰지 않는다) `.env` 파일은 건드리지 않는다.
- **음성 테스트로 게이트를 확인**: 서비스용 폴더에 스위치 파일·dev 라벨을 일부러 넣어 게이트가 거부하는지 확인하고 되돌렸다. 게이트는 "통과하는 것"보다 "막는 것"을 한 번은 실물로 봐야 믿을 수 있다.

함정 23~25 (이 사례에서 실제로 겪음):

23. **범위 오타로 부분 승격이 났다 — 함정 19의 실제 사고.** `promote.ps1 "HEAD~1..HEAD"`로 두 커밋 중 뒤 커밋만 서비스용에 옮겼더니 게이트가 "서비스용 main이 출처와 다르다"로 막았다(게이트가 제 일을 한 것, 푸시 표식은 지워졌다).
    복구 = 서비스용 폴더에서 **아직 푸시 안 된 로컬 커밋만** `git reset --hard <직전에 푸시한 커밋>`으로 되돌린 뒤 올바른 범위로 다시 승격. 먼저 `git log <remote>/main..main`으로 되돌려도 되는 커밋뿐인지 본다.
    reset은 되돌릴 수 없는 작업이라 AI 코딩 도구의 안전 검사가 막을 수 있다 — 막히면 우회하지 말고 사용자가 `! git reset --hard …`로 직접 실행하게 한다. 예방: 범위의 시작은 "직전에 옮긴 개발 커밋"(그 커밋은 제외됨), 또는 스크립트가 "서비스용에 아직 없는 개발 커밋 전부"로 범위를 자동 계산하게 개선.
24. **개발 폴더 이름에 한글이 있으면 Android Gradle Plugin이 빌드를 거부한다.** "Your project path contains non-ASCII characters" 오류로 첫 개발앱 빌드가 실패했다(서비스용은 영문 경로라 무관). 개발 폴더 `android/gradle.properties`에 `android.overridePathCheck=true`(검사만 끔)를 넣어 해결.
    같은 파일이 승격돼 서비스용에도 가지만 영문 경로에서는 무해. 개발 폴더 이름을 `<프로젝트>_개발`로 하는 이 패턴에서는 프로젝트 이름이 한글이 아니어도 접미사 때문에 걸린다. 개발앱 빌드 후 APK의 앱 ID·이름은 `aapt2 dump badging <apk>`로 확인(`.dev`·`… DEV`·`-dev`).
25. **문서에서도 `\a`·`\b`가 제어문자가 된다(함정 20의 재발).** `client_flutter\android\app_variant` 경로를 파이썬 일반 문자열로 문서에 쓰다 두 번 깨졌다(`\a` = BEL). 스크립트뿐 아니라 문서·README에도 쓴 뒤 `grep -cP "[\x00-\x08\x0b\x0c\x0e-\x1f]"`가 0인지 확인.
26. **브리핑을 본 사용자가 "푸시하자"고 해도 AI 도구의 자동 권한 판별기가 `-Approve` 실행을 막을 수 있다(poker_app, 2026-10-23).** 사용자는 브리핑·승인 코드를 본 뒤
    "테스트 후 푸시하자"라고 했고, 테스트 뒤 `push_verified.ps1 -Approve <코드>`가 "위험" 판정(이유 없음)으로 거부됐다. 스크립트 자체는 일반 푸시 한 줄·강제 없음이었다 —
    판별기는 "사람 승인 단계를 도구가 대신 넘는 동작"과 "조건부 지시(테스트 후)"를 명시적 승인으로 보지 않은 것으로 보인다(추정, 판별기는 이유를 주지 않는다).
    - **우회하지 않는다.** 막혔다고 다른 명령 형태로 같은 푸시를 시도하지 말고, 막힌 사실과 스크립트가 하는 일(푸시 줄 번호)을 보여 준 뒤 사용자가 직접 실행하게 한다.
    - **사용자 직접 실행의 함정**: Windows의 Claude Code에서 `!` 접두 명령은 PowerShell이 아니라 **bash**로 돈다. `! cd ..\poker_app; .\push_verified.ps1 -Approve …`는
      백슬래시가 이스케이프로 먹혀 `cd: ..poker_app: No such file`·`.push_verified.ps1: command not found`로 실패했다(아무것도 실행 안 됨 — 안전).
      안내할 형태: `! cd ../poker_app && powershell -NoProfile -ExecutionPolicy Bypass -File ./push_verified.ps1 -Approve <코드>` — 슬래시 경로, `&&`, PowerShell을 명시 호출.
    - 이 형태는 스크립트의 대화창 판정(함정 22)에서 비대화형이지만 `-Approve`가 있어 바로 푸시한다. 결과 확인은 도구가 `git status -sb`의 `## master...origin/master`로.
    - 도구 메모리에 "막히면 bash 형태 명령을 바로 안내"를 남겨 다음 세션에서 같은 왕복을 줄인다.

## 적용 사례 4 — RVS_App(JudgeCal에서 포크한 두 번째 앱, 2026-10-21~24)

JudgeCal 개발 폴더를 포크해 만든 독립 앱이라 엔진(promote·gate·push_verified·service_gate)·제약 모음·폴더 라벨·푸시 승인을 **그대로 복사**해 시작했다(`RVSU_App/RVS_App_Dev`·`RVS_App_Service`, 서비스용 브랜치 `main`/remote `origin`). 새로 겪은 것:

- **서비스 폴더가 제약 값에서 앞서는 것은 정상 흐름이다.** 실사용자 로그를 바탕으로 한도 숫자를 고치는 일은 서비스 폴더에서 `[service]` 커밋으로 직접 하고(`service_only_paths.txt`에 `server/constraints/rules.py`만 허용), 함수 이름·시그니처를 바꾸는 일은 개발 폴더에서 한다(rules/noop 짝 테스트가 막는다). 개발 쪽으로 되돌려 반영하는 절차는 별도로 두지 않는다 — 두 폴더의 트리가 같은지는 `git diff dev/dev main`(서비스 폴더에서 개발 폴더를 remote `dev`로 fetch)으로 본다. 줄바꿈(CRLF) 때문에 파일 단위 `cmp`는 거짓 차이를 낸다.
- **개발 폴더 전용 무인 작업(콘텐츠 채우기)은 헤드리스 도구를 스크립트로 부르고 푸시는 빼는 것이 안전하다**: 깨끗한 트리에서만 시작, 시작 전 해시 기록, 끝나면 새 커밋이 있는지 확인, 검증기·테스트를 통과해야 커밋, 푸시는 하지 않고 사람이 promote한다. 로테이션 설정이 도메인 카탈로그와 어긋나면(관계 종류 6개 중 4개만 적음) 일관성 테스트가 막아 주지만 그날 실행이 헛수고가 된다.
- **서비스 폴더에 미커밋 변경이 있으면 promote가 멈춘다.** 지우지 말고 `git stash push -m "<무엇이 왜>"`로 보관하고(되돌릴 수 있음) 승격·푸시를 끝낸 뒤 보관본을 사용자와 정한다. 서비스 폴더에서 `stash pop`을 하면 다시 막힌다.

함정 27~30 (이 사례에서 실제로 겪음):

27. **무인 예약 작업이 서비스 폴더에서 돌고 있었다 — 분리를 해 놓고 작업 스케줄러는 옛 경로를 가리킨 채였다.** 분리 이전에 등록한 작업(`JudgeCal-BranchSeedDaily`, 매일 04:00)이 서비스 폴더의 스크립트를 계속 불러 콘텐츠 6,740줄을 미커밋으로 남기고 서비스 폴더의 promote를 막았다. 분리 작업의 체크리스트에 **`Get-ScheduledTask`로 옛 경로를 가리키는 예약 작업 찾기**를 넣는다. 개발/생성 작업은 개발 폴더로 옮기고(새 작업 등록 + 옛 작업은 **삭제가 아니라 Disable**), 운영 작업(백업 등)은 서비스 폴더에 남긴다. 확인은 `schtasks`가 비어 나오는 환경이 있으니 `Get-ScheduledTask | ? { $_.Actions.Execute -match '<프로젝트>' -or $_.Actions.Arguments -match '<프로젝트>' }`로 한다.
28. **테스트 결과가 어느 폴더에서 돌렸는지에 따라 달라졌다.** 서비스 폴더 `.env`의 운영 스위치(`CREDITS_ENFORCED=1`)가 테스트 프로세스에도 적용돼 개발 폴더에서는 통과하는 테스트 3개가 서비스 폴더에서 실패했다(게스트 상태가 "off"). 제약 모음은 conftest가 rules로 고정했지만 `.env`로 갈리는 값은 놓쳤다. conftest에 **폴더별로 갈릴 수 있는 스위치를 기본 꺼짐으로 고정**하는 autouse 픽스처를 두고(켜는 테스트는 직접 켠다) `환경변수=1`로 켠 채 전체 스위트를 한 번 돌려 확인한다. 승격 게이트가 서비스 폴더에서 돌리는 것은 제약 짝 테스트뿐이라 이 결함이 게이트를 통과해 있었다. **같은 부류의 재발(RVS_App 2026-11-11)**: 서비스 폴더 `.env`에 공용 API 토큰(`API_AUTH_TOKEN`)을 넣자 서버 테스트 172개가 토큰 없이 요청해 401로 실패했다 — 개발 폴더엔 토큰이 없어 안 드러났고, 이번엔 게이트가 서비스 폴더에서 서버 테스트 **전체**를 돌려(31번 이후) 잡았다. 대응은 같다: conftest의 autouse 픽스처가 `config.API_AUTH_TOKEN`을 비우고(토큰 게이트를 시험하는 테스트는 직접 켠다), 환경변수 `API_AUTH_TOKEN=값`을 준 채 개발 폴더에서도 전체 스위트를 돌려 재현·확인한다(새 환경 의존 설정이 생길 때마다 같은 식으로).
29. **포크 기준 커밋 기록이 실제와 달랐다.** README는 "`dev@cb25476`을 포크"라 적었지만 실제 코드는 그 다음 커밋(`bdd165e`)까지 들어와 있었다(파일을 대조해 알았다). 포크 직후 `git log` 한 줄을 믿지 말고 "이 파일에 있는 기능이 기준 커밋에 있는가"로 확인해 적는다. 이후 갈라짐은 `포크_앱_공유파일_갈라짐_점검_패턴.md`의 스크립트로 추적한다.
30. **bash 도구에서 한글·따옴표가 많은 `cat > 파일 <<'EOF'` 히어독이 `unexpected EOF while looking for matching`으로 통째로 실패한다(2회; RVS 2026-11-11 세션에서 3회 더).** 파일 내용은 Write 도구로 쓰고, 실행(python/pytest)만 bash로 한다. 같은 명령 안에 히어독 둘 이상을 넣지 않는다. 실패한 히어독은 **아무것도 적용하지 않은 채** 다음 줄의 명령이 그대로 돌아 시험 결과가 엉뚱한 상태를 재게 된다 — 파일로 쓴 스크립트를 실행한 뒤에는 적용 결과(`git diff --stat`·문법 검사)를 먼저 확인하고 시험을 돌린다.
31. **푸시 전 게이트가 테스트 전체를 돌리지 않았다(2026-10-30 발견).** 엔진 Verify는 "넘어올 때의 관문"(제약 짝 테스트 `test_constraints`)만 봤고 `-Full`도 `flutter analyze`까지였다 — GitHub `main`이 곧 배포 대상인데 서버 테스트 실패가 그대로 올라갈 수 있었다. Verify에 서버 pytest 전체(약 2~3분), `-Full`에 `flutter test`를 더했다. GitHub Actions CI도 같은 검사를 하되 **푸시된 뒤라 막지 못하므로 기록용 이중 확인**으로 두고, 막는 곳은 로컬 게이트로 정했다. CI는 개발 폴더(원격 없음)에서는 돌지 않고 승격 뒤에만 돈다 — 먼저 깨끗한 클론(.env·data·스위치 없음)에서 테스트가 도는지 확인해 둔다. 린트는 기존 부채 때문에 버그 규칙만 차단하고, 보관용 `_legacy`는 제외한다(남은 위반이 전부 거기였다).
32. **같은 개발 폴더에서 다른 AI 세션이 동시에 일하면 "내 커밋만 승격"이 안 된다(2026-10-31, RVS_App).** 승격 게이트는 "서비스 == 승격한 마지막 개발 커밋"을 검사하므로 중간 커밋만 골라 올리면 앞선 남의 커밋 내용이 빠져 실패한다. 실제로 내가 승격하려던 커밋을 다른 세션이 뒤의 자기 커밋까지 묶어 먼저 승격해 두어 "이미 옮김"만 나왔다. 승격 전 `git log <마지막 승격>..HEAD`로 남의 커밋이 끼었는지 보고, 섞이면 사용자에게 "함께 올릴지"를 묻는다(서비스 폴더 `git reset`으로 남의 승격을 지우는 건 하지 않는다). 커밋은 내 파일만 add하고, 남이 고치는 중인 파일(미커밋)은 그 세션이 커밋할 때까지 건드리지 않는다 — 기능을 나눠 겹치지 않는 파일부터 한다.
33. **시크릿 파일의 무시 패턴이 이름 변형을 놓치면 게이트도 같이 뚫린다(RVS_App 2026-11-11).** `.gitignore`가 `key.properties`만 막고 있어 `key.properties.txt`(서명 키 항목이 든 복사본)가 untracked로 남아 `git add -A` 한 번이면 커밋될 상태였고, 게이트의 추적 금지 정규식도 정확히 일치만 봐서 **커밋돼도 통과**했다. 루트·플랫폼 폴더 `.gitignore`와 게이트 정규식은 "같은 목록"이므로 함께 `key.properties*`로 넓히고, 이름 변형 몇 개(`.txt`·`.bak`·정상 이름 `keyboard.py`)를 정규식에 직접 넣어 막힘/통과를 확인한다(값은 열어 보지 않는다). 부작용: 같은 접두의 예시 파일(`key.properties.example`)도 막히니 예시 파일은 다른 이름으로 둔다. 발견 경로: 서비스 폴더 `git status`에 계속 untracked로 보이던 파일을 점검에서 짚었다 — **무시되지도 추적되지도 않는 파일은 규칙 누락의 신호**다.
34. **무인 예약 작업은 더러운 개발 폴더에서 조용히 건너뛴다(RVS_App 2026-11-11).** 개발 폴더에 커밋 안 된 변경이 있으면 시드 채우기 스크립트가 시작하지 않고 상태 파일에 `dirty_skip`을 남긴 채 종료 코드 1로 끝난다 — 작업 스케줄러에는 "결과 1"로만 보이고 새 커밋도 알림도 없다. 저녁에 개발 중이면 예약 시각 전에 커밋(또는 정리)해 두고, 예약이 의도대로 돌았는지는 작업 스케줄러 결과 코드가 아니라 스크립트가 남기는 상태 파일(`logs/seed_fill_last.json`)과 `chore: 시드 채우기` 커밋으로 본다. 또 예약 작업의 인자(`-Pack` 같은 선택 플래그)는 등록 때 정한 그대로라, 나중에 생긴 변형 실행은 예약에 **자동으로 들어가지 않는다** — 어떤 일정이 무엇을 채우는지 한 번 읽어 둔다(RVS는 사용자 기억 "12시"와 실제 21:00, 그리고 팩 시드 미포함이 이 점검에서 드러났다).
