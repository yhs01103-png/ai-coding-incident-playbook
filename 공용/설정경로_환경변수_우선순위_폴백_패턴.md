# 설정 경로를 환경변수 우선 + 하드코딩 폴백으로 (범용)

여러 스크립트/프로세스가 같은 설정 파일(레지스트리 JSON, 공용 로그 경로 등)을
공유해서 읽어야 하는데, 그 파일 위치가 사람/기기마다 다를 수 있는 모든 상황에
적용하는 패턴. 특정 프로젝트에 종속되지 않음.

## 핵심 패턴

```python
import os
from pathlib import Path

def resolve_config_path() -> Path:
    return Path(
        os.environ.get("MY_CONFIG_PATH")
        or (Path.home() / ".myapp" / "config.json")  # 범용 기본값
    )
```

- **환경변수가 있으면 그걸 쓰고, 없으면 합리적 기본값으로 폴백한다** — 소스코드에
  특정 사람의 개인 경로(`C:\Users\<사용자이름>\...` 같은)를 직접 박아두지 않는다. 기본값은
  "이 코드를 처음 받은 사람이 아무것도 안 해도 그럴듯하게 동작할 위치"(홈 디렉토리
  기준 등)로 잡는다.
- **같은 설정을 공유하는 소비자가 여럿이면(여러 스크립트, 여러 훅, 하나의 앱), 이
  resolve 함수 자체를 한 곳에만 두고 나머지가 그걸 재사용한다.** 각 소비자가
  독립적으로 `os.environ.get(...) or Path.home()/...` 를 따로 구현하면, 나중에 기본
  경로를 바꿀 때 한 곳만 놓쳐도 그 소비자만 몰래 옛 경로를 계속 보는 드리프트가
  생긴다(실측 사례 아래 참고). 다만 소비자들이 서로 다른 모듈/레포에 흩어져 있어
  import로 공유가 안 되는 경우(예: 독립 실행되는 훅 스크립트)는 예외적으로 각자
  같은 로직을 복제해도 되지만, 그럴 땐 주석에 "원본은 어디" + "복제 이유"를 반드시
  남긴다.

## 실측 함정 1 — 소비자 중 일부만 이 패턴을 적용하면 조용히 드리프트난다

한 프로젝트(앱 본체)가 이 패턴을 먼저 도입했는데, 같은 설정을 읽는 다른 소비자
(전역 훅 스크립트 2개)는 여전히 옛날처럼 경로를 하드코딩하고 있었던 사례(2026-08-19).
나중에 설정 파일을 실제로 이동시켰을 때, 앱은 환경변수를 갱신해서 잘 따라갔지만
훅 2개는 하드코딩된 옛 경로를 계속 봐서 조용히(에러 없이, 그냥 아무 동작도 안 하는
채로) 고장났다. **"이 설정을 읽는 모든 곳"을 한 번에 다 찾아서 같은 패턴으로
맞춰야 한다** — 하나라도 빠지면 그 한 곳만 눈에 안 띄게 stale 상태로 남는다.

## 실측 함정 2 (Windows) — 환경변수를 갱신해도 이미 떠 있는 프로세스엔 반영 안 됨

`[System.Environment]::SetEnvironmentVariable("MY_CONFIG_PATH", "...", "User")`
(PowerShell) 또는 `setx`(cmd)로 Windows 사용자 환경변수를 갱신하면, 그건 **레지스트리에
값을 쓰는 것**이지 이미 실행 중인 프로세스의 메모리 안 환경변수를 바꾸는 게 아니다.
Windows가 `WM_SETTINGCHANGE` 메시지를 브로드캐스트하긴 하지만, 이미 떠 있는
프로세스(셸, 이미 시작된 앱, 이미 열려 있는 에이전트 세션 등)는 대개 이걸 감지해서
재로드하지 않는다 — **새로 시작하는 프로세스부터만** 새 값을 본다.

이 함정은 실제로 이렇게 드러난다: 환경변수를 방금 갱신했는데, "지금 이 세션"에서
`os.environ.get(...)`을 다시 읽어보면 여전히 옛 값이 나온다. 당황하지 않아도 되는
정상 동작이다 — 다음에 그 프로세스(터미널, 앱, 세션)를 새로 켜면 그때 반영된다.
지금 세션에서 즉시 확인하고 싶으면, 그 값을 명시적으로 override해서(`export
MY_CONFIG_PATH=...` 또는 서브프로세스 호출 시 `env=` 인자로 주입) 새 프로세스를
띄우는 방법으로 검증한다 — 이미 떠 있는 프로세스의 환경변수를 코드로 바꿀 방법은
없다.

## 언제 이 패턴이 필요한가

- 설정 파일 위치가 "이 프로젝트를 쓰는 사람마다 다를 수 있는" 경우(개인 컴퓨터 경로,
  회사마다 다른 배포 경로 등) — 특히 코드를 공개 저장소로 옮기거나 여러 사람이
  같이 쓰게 될 가능성이 있으면 처음부터 이 패턴으로 시작하는 게 나중에 "개인 경로
  스크러빙" 작업을 통째로 다시 하는 것보다 싸다.
- 소비자가 2개 이상이고 그중 하나라도 별도 프로세스로 실행되는 경우(훅, CLI,
  스케줄된 작업 등) — 코드 안에서 import로 공유가 안 되는 경계가 있으면 이 패턴이
  아니고서는 위치를 한 곳만 바꿔서 전체가 따라오게 만들 방법이 없다.
