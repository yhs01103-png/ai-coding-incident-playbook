# Qt 앱에 외부(비-Qt) 스레드 라이브러리를 연결할 때 — 릴레이 패턴 (범용)

PySide6/PyQt 앱에 자기 자신의 이벤트루프/스레드를 갖고 있는 외부 라이브러리(트레이
아이콘, 전역 단축키 후킹, 하드웨어/IPC 콜백 등)를 연결하는 모든 상황에 적용되는
패턴. `pystray`(시스템 트레이) 통합 중 실측(2026-08-19 이전, `터미널 단축키 모음집`
프로젝트 D-023, 폴더 터미널_단축키_모음집)으로 발견·검증됨.

## 함정

`pystray`, 전역 핫키 라이브러리, 일부 IPC/하드웨어 콜백 라이브러리는 **자기
자신의 이벤트 루프를 별도 스레드로 돌린다** — Qt의 이벤트 루프와 무관하다. 그
라이브러리의 콜백(트레이 아이콘 클릭, 핫키 눌림 등) 안에서 QWidget을 직접
만들거나 조작하면, Qt의 스레드 안전성 원칙(위젯은 GUI 스레드에서만 건드려야
함)을 위반한다 — 크래시하거나, 더 나쁘게는 가끔씩만(레이스 컨디션) 이상 동작한다.

## 해법 — 콜백은 신호만 emit, 위젯 생성/조작은 슬롯에서

```python
class TrayRelay(QObject):
    show_launcher = Signal()  # 콜백 스레드 → GUI 스레드로 넘기는 유일한 통로


relay = TrayRelay()
relay.show_launcher.connect(create_and_show_launcher_widget)  # GUI 스레드에서 실행됨

def on_hotkey_pressed():  # 이 함수는 외부 라이브러리의 스레드에서 호출됨
    relay.show_launcher.emit()  # 위젯을 직접 안 건드림 — 신호만 던짐

# 외부 라이브러리의 이벤트 루프는 별도 스레드에서
threading.Thread(target=tray_icon.run, daemon=True).start()
```

Qt의 시그널-슬롯은 스레드 간 연결이면 기본적으로 `Qt.QueuedConnection`으로
동작해서, emit이 다른 스레드에서 일어나도 슬롯 실행은 안전하게 GUI 스레드
이벤트 루프로 큐잉된다 — 이 성질을 이용해 "위젯을 만들거나 건드리는 코드는
전부 슬롯 쪽에만" 두면 스레드 위반이 구조적으로 불가능해진다.

## 부수 설정 — 트레이 모드면 창 닫기 ≠ 앱 종료

트레이 아이콘이 있는 앱은 메인 창을 닫아도 앱이 계속 떠 있어야(트레이에 상주)
하는 경우가 많다 — 기본값 `app.setQuitOnLastWindowClosed(False)`를 명시적으로
꺼야 한다(기본값 True면 마지막 창이 닫히자마자 트레이 아이콘까지 같이 죽는다).

## 이미 있는 "QThread 워커" 패턴과의 차이

이 프로젝트 라이브러리에 이미 있는 "무거운 작업은 QThread로 빼고 시그널로 결과
전달"(`서버_워커_분리_로컬디버깅_운영패턴.md`류 문서에서 다루는 것과 인접) 패턴은
**Qt가 자기 자신의 워커를 스스로 만드는** 경우다. 이 문서는 반대 방향 — **Qt가
아닌 외부 라이브러리가 이미 갖고 있는 스레드가 Qt 쪽으로 들어오는** 경우라
헷갈리지 않게 구분한다. 둘 다 "위젯 조작은 GUI 스레드에서만"이라는 같은 규칙을
지키지만, 스레드를 누가 만들었느냐가 다르다.
