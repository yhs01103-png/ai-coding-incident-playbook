# 여러 모듈이 참조하는 공유 계약(contract) 레이어는 한 경유지를 통해서만 (범용)

스택/정책/폴백 설정처럼 여러 레이어가 공통으로 참조하는 "계약" 데이터를 가진
프로젝트에 적용되는 접근 통제 패턴.

## 문제

공유 계약 값(설정, 정책, 스택 선택 등)을 아무 모듈에서나 직접 import해서
쓰게 허용하면, 시간이 지날수록 "어디서 이 값을 쓰고 있는지"를 추적하기
어려워진다 — 계약을 바꿀 때 영향 범위를 사람이 전부 grep해서 찾아야 하고,
빠뜨리면 조용히 어긋난다.

## 해법 — 공유 계약은 오케스트레이션 레이어만 직접 참조하고, 나머지는
오케스트레이션을 거쳐서만 접근

```
전역설정/오케스트레이션 ──(직접 import)──▶ 계약(스택/정책/폴백)
       │
       └─(파이프라인 조립 시 전달)──▶ 로직/파이프라인 (계약을 직접 import 안 함)
```

계약 레이어를 직접 import할 수 있는 곳을 오케스트레이션 하나로 좁히면,
"이 계약이 실제로 어디서 쓰이는지" 확인할 때 오케스트레이션 레이어 하나만
보면 된다 — 계약을 바꿀 때 영향 범위 파악 비용이 "전체 코드베이스 grep"에서
"오케스트레이션 파일 하나 확인"으로 줄어든다.

## 부가 패턴 — 데이터플로우 로그를 에러 로그와 별도로 남긴다

런타임 에러 로그, 오류 지점 등록과는 별개로, **"이 요청이 어느 레이어를
거쳐갔는지"만 기록하는 세 번째 로그**를 두면 레이어 간 의존 관계가 실제로
꼬였는지(예: 로직이 계약을 우회해서 직접 접근했는지) 사후에 진단할 수 있다.
에러가 안 났어도 "설계한 경로대로 흘렀는지"를 확인하고 싶을 때 유용 —
평소엔 안 봐도 되지만, 레이어 위반 의심이 들 때 첫 번째로 열어보는 자료가
된다.
