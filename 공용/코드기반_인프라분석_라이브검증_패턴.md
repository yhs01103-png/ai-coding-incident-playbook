# 코드만 보고 인프라 리스크를 확정하지 않는다 — 라이브 상태로 검증 (범용)

레포 코드(설정 파일, IaC, `.gitignore` 등)를 읽어서 인프라 리스크를 진단할
때 적용하는 원칙. 클라우드 플랫폼(Railway/Vercel/Fly.io 등)은 볼륨 마운트·
환경변수·도메인 연결 같은 상태를 **대시보드/CLI로만 설정하고 레포에는
아무 흔적도 안 남기는 경우**가 흔하다 — 코드에 설정 파일이 없다는 것이
"그 인프라가 안 갖춰져 있다"는 증거가 되지 않는다.

## 함정 — "코드에 없음" = "인프라에 없음"으로 성급히 결론

`railway.toml`/`Dockerfile`/볼륨 마운트 선언이 저장소에 전혀 없는 걸 보고
"재배포 시 영구 스토리지가 없어 데이터가 날아갈 것"이라고 **코드 근거만으로
"High 리스크"를 확정**해 보고했던 실측 사례(2026-08-21). 실제로 플랫폼 CLI
(`railway status`, `railway volume list`)로 확인하니 볼륨이 이미 정확한
마운트 경로에 붙어있었고, 데이터도 이미 그 위에 쌓이고 있었다 — 코드
근거만으로 내린 결론이 완전히 틀렸던 것. 같은 세션에서 "빌드 산출물(`dist/`)이
git에 추적되고 있는지 미확인"이라고 리스크 목록에 올려둔 것도, `git ls-files
-- dist/ build/`로 10초 안에 "이미 gitignore로 안전하게 빠져 있다"를 확정할
수 있었던 걸 확인 없이 열어둔 항목이었다.

## 원칙 — CLI/API로 확인 가능한 건 코드 근거만으로 리스크를 확정하지 않는다

1. **인프라 리스크를 보고하기 전에, 그 플랫폼이 CLI/API를 제공하면 실제
   상태를 먼저 조회한다** — 로그인 여부(`<platform> whoami`), 프로젝트 연결
   상태(`<platform> status`), 리소스 목록(볼륨/도메인/환경변수 목록 명령)
   순으로 짧게 확인하는 것만으로도 "코드에 없어서 리스크"였던 항목의 상당수가
   즉시 해소되거나 반대로 진짜 문제로 확정된다.
2. **`git ls-files`/`git check-ignore` 같은 로컬에서 즉시 확인 가능한
   질문은 "미확인"으로 남겨두지 않는다** — 명령 하나로 끝나는 확인을 안
   하고 리스크 목록에 올리면, 나중에 그 리스크를 근거로 불필요한 작업을
   벌이게 될 수 있다.
3. CLI/API 자체가 없거나 접근 권한이 없어서 확인이 불가능한 항목만
   "코드로는 확인 안 됨(대시보드에서 직접 확인 필요)"로 명시하고, 사용자에게
   그 확인을 요청한다 — 이때도 "리스크가 있다"고 단정하지 않고 "확인이
   필요하다"로 표현을 구분한다.
4. 확인 결과가 코드 근거의 결론을 뒤집으면, 즉시 정정하고 그 자리에서
   사용자에게 알린다 — 이전에 내린 잘못된 판단을 방치한 채로 다음 작업을
   진행하지 않는다.

## 언제 이 패턴이 필요한가

- 클라우드에 배포된 프로젝트의 인프라(스토리지/네트워크/시크릿)를
  코드/설정 파일 리뷰만으로 감사(audit)할 때.
- "설정 파일이 없다"는 관찰을 근거로 심각도(Critical/High 등)를 매기기
  직전 — 특히 그 심각도가 사용자의 다음 행동(추가 작업, 긴급 조치)을
  좌우할 때는 반드시 라이브 검증을 먼저 시도한다.
- 해당 플랫폼의 CLI가 이미 로그인/연결돼 있는 환경(예: `railway whoami`가
  바로 성공하는 상태)이라면, 그 확인 비용은 거의 0에 가까우므로 생략할
  이유가 없다.

## 분석을 직접 실행으로 돌릴 때의 함정 (6개 앱 정밀 분석, 2026-10-11 실측)

테스트·분석 도구를 "다른 사람 저장소"나 "작업 중인 저장소"에서 돌릴 때 결과가 틀어지거나 부작용이 생기는 경우가 반복됐다.

1. **작업 중(미커밋) 코드와 커밋된 코드의 결과를 따로 본다.** 같은 서버 테스트가 작업 트리에서는 661개 중 8개 실패, 커밋된 코드
   (`git archive HEAD`로 임시 폴더에 풀어 실행)에서는 598개 전부 통과였다. 실패가 "배포된 코드의 결함"인지 "작업 중 코드의 미완성"인지는 둘을
   나눠야 알 수 있다. 원본 작업 트리는 건드리지 않고 임시 복사본에서 돌린다.
2. **실제 비밀이 든 설정 파일이 있는 저장소는 더미 환경값을 강제로 넣고 테스트한다.** `.env`에 실제 키·서비스 계정이 있으면 테스트가 실제 외부
   서비스(데이터베이스, 결제, AI)에 닿을 수 있다. CI가 쓰는 더미 값(`GEMINI_API_KEY=ci-dummy`, 서비스 계정 `{}` 등)과 빈 자격 증명 경로를
   명령에 직접 지정한다(dotenv는 이미 설정된 환경변수를 덮어쓰지 않는다).
3. **테스트 격리 누락은 실행해 봐야 보인다.** 서버 테스트를 돌린 뒤 실제 계정 DB 옆에 `-shm`/`-wal` 파일이 새로 생겼다 — 어떤 테스트가
   `conftest.py`에서 임시 경로로 돌리지 않은 실제 DB를 연다는 증거. 실행 전후로 `git status`를 비교해 흔적을 찾고, 흔적이 남았으면 삭제하지 말고
   (사용자 승인 대상) 보고한다.
4. **고정 날짜 픽스처는 분석 날에 처음 터지기도 한다.** 조회 기간 30일 함수에 고정 날짜(`2026-08-16`)를 넣은 테스트가 9월 15일부터 조용히
   실패하고 있었다(CI가 서버 변경 때만 돌아 발견이 늦음) → `실시계_만료판정_테스트_고정날짜_픽스처_시한폭탄_함정.md`.
5. **동기화 폴더(OneDrive) 아래의 `build/`는 잠겨 도구가 실패할 수 있다.** `flutter test`가 build 폴더의 unit_test_assets 삭제 실패로 시작하지
   못했다. `build/`를 지우지 말고 `git archive`로 임시 복사본을 만들어 거기서 `pub get`과 테스트를 돌린다.
6. **분석이 만든 흔적은 정리하지 말고 보고한다.** 생성 파일(gitignore된 코드 생성물)은 다시 만들어도 되지만(`flutter gen-l10n`), 추적 대상
   저장소 옆에 생긴 새 파일은 사용자에게 알린다.
7. **긴 테스트는 백그라운드로 돌리고 진행률만 본다.** 서버 1,900개 테스트는 30분 이상 걸렸다. 완주를 못 기다리면 "약 N% 구간까지 실패 0건"처럼
   확인한 범위를 그대로 적고 통과로 단정하지 않는다.

8. **개발 PC의 `.env`(실제 키)가 테스트에도 로드되면 "모킹 안 된 경로"가 조용히 실제 네트워크를 부른다.** 서버 테스트가 전체 10분(느린
   파일 하나 7분+)이었고, 원인은 알고리즘이 아니라 모듈 레벨로 import된 외부 호출 함수(`from x import call_llm`)를 일부 테스트가 안
   바꿔서 실제 API를 부르고, 실패하면 캐시가 안 쌓여 반복마다 재시도하던 것이었다. 직전 감사의 "실제 호출 테스트 0"은 키가 없는 환경
   기준이라 개발 PC에선 틀렸다. 해법: `conftest.py` autouse 픽스처로 테스트 전체에서 키를 비워 즉시 실패시키고, 실호출이 의도인 테스트만
   자체적으로 다시 설정한다(실측: 602초 -> 252초). 느린 테스트를 찾을 땐 `--durations`보다 먼저 "이 테스트가 네트워크를 타는가"를 본다.
9. **서버 로그에 클라이언트 요청이 0건이면 클라이언트가 다른 곳으로 나간 것이다.** 화면은 "서버에 연결할 수 없습니다"를 그리고 서버는
   멀쩡히 떠 있었다. 원인은 서버 후보 목록이 컴파일타임 값만 읽고 후보가 없으면 프로덕션 주소를 하드코딩해, 문서에 적힌 런타임
   환경변수를 무시하던 것. 확인법: 서버 로그의 요청 수를 본다(요청이 아예 없으면 도달 못한 것). 오류 문구가 주소를 고정 텍스트로
   적고 있으면 실제 접속 대상과 어긋나 오해를 부른다 — 표시하는 주소는 실제로 쓴 값에서 만든다.
10. **앱 창 캡처가 앱 대신 다른 창(전체 화면)을 잡을 수 있다.** 창 제목으로 캡처했는데 사용자의 브라우저가 나왔다 — 대상 창이 가려져
    있었기 때문. 사용자 개인 화면이 찍히므로(1) 그 이미지는 쓰지 않고, (2) 앱 창을 최상단으로 올리고(`SetWindowPos` TOPMOST +
    `SetForegroundWindow`) 그 창의 영역만 캡처한다. 서버 로그의 요청 목록과 프로세스 상태를 보조 근거로 같이 쓴다.
