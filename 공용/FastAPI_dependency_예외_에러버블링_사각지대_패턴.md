# FastAPI dependency 안의 예외는 "파이프라인이 1차로 잡는다" 원칙 밖에 있다 (범용)

`레이어_분리_방침.md`류의 에러 버블링 모델("에러는 파이프라인에서 1차로 전부
잡는다 — 로직·API가 UX로 직접 던지지 않음")을 FastAPI로 구현할 때 생기는
구조적 사각지대. 특정 프로젝트에 종속되지 않음 — FastAPI `Depends()`(또는
동급의 "라우트 본문 실행 전에 먼저 도는" 미들웨어/dependency 메커니즘을 쓰는
프레임워크 전반)에서 재현된다.

원본 사례: poker_app(flutter_App/poker_app/server)의 "앱 정밀 분석" 인프라
감사(2026-09-07) — DB 파일을 읽기전용으로 만들어 쓰기 실패를 강제 유발하는
장애복원력 테스트 중 실측.

## 문제 — dependency는 파이프라인의 try/except보다 먼저 실행된다

FastAPI의 요청 처리 순서는 `Depends(...)` → 라우트 함수 본문(보통 여기서
파이프라인을 호출) 순이다. 그런데 에러 버블링 방침의 "파이프라인이 1차로
전부 잡는다"는 규칙은 **파이프라인 함수 안의 try/except**로 구현되므로, 그
try/except 블록은 라우트 본문(파이프라인 호출부) 안에서만 유효하다 —
`Depends()` 안에서 실행되는 코드는 그 try/except의 바깥에서, 그보다 먼저
실행된다.

**실측 재현**: poker_app 서버의 `get_player_id()` dependency는 헤더 값을
읽어 반환하기 전에 `ensure_player(player_id)`(DB에 처음 보는 player_id면
행 삽입)를 호출한다. 이 DB 쓰기가 실패하면(감사 중 강제로 읽기전용 파일로
만들어 재현) 이 예외를 잡는 코드가 어디에도 없다 — 라우트 본문의 파이프라인
try/except는 아직 실행되지도 않은 시점이라 무의미하고, FastAPI는 처리 안 된
예외를 그대로 raw HTTP 500 + 파이썬 스택트레이스로 응답에 내보낸다. 결과:
계약("장애 시 502로 깔끔히 버블링")과 실제 동작(500 + 정보노출)이 어긋나고,
동시에 스택트레이스가 클라이언트에 노출된다(정보노출).

## 왜 눈에 안 띄는가

- dependency는 보통 "인증/헤더 파싱처럼 절대 안 실패하는 얇은 조회"라고
  가정하고 설계되지만, 실제로는(이 사례처럼) 그 안에서 DB 조회·쓰기·외부
  호출이 슬며시 들어가기 쉽다 — "여기서 플레이어를 처음 본 거면 등록해두자"
  같은 편의 로직이 자연스럽게 dependency 쪽에 얹히기 때문.
- 정상 경로 테스트만으로는 절대 안 드러난다 — dependency의 DB 호출이
  실패하는 경우 자체가 "장애 상황을 강제로 유발"해야만 재현되므로, 일반적인
  단위/통합 테스트 스위트가 이 경로를 우연히 커버할 확률이 낮다.

## 해법 — 둘 중 하나, 섞지 말 것

1. **dependency는 순수 조회만** — DB 등록/쓰기처럼 실패 가능한 부수효과는
   dependency에서 빼서 파이프라인 함수 맨 앞으로 옮긴다(그러면 그 함수의
   기존 try/except가 자연스럽게 커버). dependency는 헤더에서 값을 뽑아
   반환하는 것까지만 — 방침의 "경로 레이어는 아무것도 호출하지 않는다"는
   원칙과 결이 같다.
2. **dependency 자체에 방어적 try/except를 건다** — 부수효과를 dependency
   쪽에 남겨야 하는 구조적 이유가 있다면(예: 모든 라우터가 공통으로 필요해서
   조립 시점 일괄 적용이 더 맞는 경우), dependency 함수 본문에 자체
   try/except를 걸어 502로 변환해 던진다 — 파이프라인의 1차 캐치를
   기대하지 말고 dependency 자신이 그 책임을 진다는 걸 명시적으로
   받아들이는 것.

어느 쪽을 고르든, **"파이프라인이 다 잡아줄 것"이라는 가정을 dependency
코드에 그대로 적용하지 않는다**는 게 핵심 — dependency는 그 가정이 성립하지
않는 유일한 지대라는 걸 설계 시점에 의식적으로 표시해둔다(주석 한 줄로도
충분, 다음에 이 dependency를 확장하는 사람이 같은 함정을 반복하지 않게).

## 언제 이 패턴이 필요한가

- FastAPI(또는 유사 프레임워크)에서 인증/헤더 파싱용 dependency 안에
  DB 조회·쓰기·외부 API 호출 등 실패 가능한 코드가 있는지 감사할 때.
- "장애 복원력" 계층을 실제로 실행 검증할 때(코드만 읽고 "파이프라인이
  잡을 것"이라고 짐작하지 않고, dependency가 관여하는 요청 경로도 반드시
  강제 장애 유발로 재현) — `코드기반_인프라분석_라이브검증_패턴.md`(같은
  폴더)의 "라이브로 확인" 원칙과 정확히 같은 이유.
