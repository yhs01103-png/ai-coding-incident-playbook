# LLM 판단의 자기일관성을 재려면 "진짜 블라인드" 반복 생성이 필요하다

## 언제 이 문서를 참조하는가

"같은 프롬프트를 LLM에 여러 번 넣어서 답이 얼마나 안정적으로 나오는지"를
측정해 신뢰도/일관성 신호로 쓰고 싶을 때 — 콘텐츠 저작 품질 게이트, 프롬프트
튜닝 검증, "이 판단이 우연인지 재현 가능한지" 확인 등. 그리고 그 결과를
자동으로 점수화하려는데 임베딩 API가 없거나(키 미설정) 쓰기 애매할 때.

## 핵심 함정 — "반복 호출"의 대부분은 진짜 독립이 아니다

같은 세션/컨텍스트 안에서 "다시 만들어봐"를 반복하면 모델이 자기가 방금 쓴
답을 대화 이력에서 그대로 보고 있어서, 새로 만드는 게 아니라 살짝 바꿔
베끼는 쪽으로 편향된다(앵커링). `Agent(subagent_type: "fork")`도 마찬가지다
— fork는 호출자의 전체 대화 컨텍스트를 그대로 물려받으므로 "독립 생성"의
전제 자체가 깨진다.

**해법**: 컨텍스트를 전혀 공유하지 않는 fresh 서브에이전트(fork가 아닌 일반
Agent 호출, 매번 완전히 새 세션)를 N개(보통 5개) 병렬로 띄워, 각각에 완전히
자기완결적인 동일 프롬프트만 준다("다른 자료나 이전 시도는 전혀 없다 — 이
프롬프트만 보고 처음부터 새로 만들어라"를 프롬프트에 명시). 이래야 N개의
결과가 진짜 서로 독립적인 표본이 된다.

## 측정한 값이 의미하는 것 — 정확도가 아니라 결정공간의 안정성

**자기일관성 ≠ 정답 여부.** N개가 전부 똑같이 수렴해도 그건 "모델이 이
프롬프트에서 일관되게 같은 편향을 재생산한다"는 뜻일 수 있지, 그 답이 실제로
맞다는 보증이 아니다(온도가 낮으면 사소한 이유로도 트리비얼하게 수렴한다).
반대로 낮은 수렴률은 "이 상황이 실제로 여러 타당한 접근이 갈리는 애매한
영역"이라는 신호일 수도, 프롬프트 설계가 부실해서 노이즈가 큰 것일 수도
있다 — 둘을 코드만으로는 구분 못 한다.

그래서 이 점수를 **승격/차단 게이트로 쓰지 않는다**. 실사용(실제 사람의
선택·결과)과 대조해 불일치가 나는 것만 신뢰 가능한 신호로 삼고, 자기일관성
점수는 "참고용 배지"나 "검수 우선순위 정렬" 용도로만 쓴다 — 실측 사례(아래)
에서 사용자가 먼저 이 구분을 요구했다: "승격보다 사용자가 감안하고 보는
방향으로."

## 자동 점수화의 함정 — 임베딩 없이 키워드/자카드로 대체하면 값이 왜곡된다

N개의 결과를 자동으로 클러스터링해서 점수(예: "5개 중 몇 개 클러스터로
나뉘는가")를 내고 싶을 때, 임베딩(의미 기반 유사도) 없이 표면 단어 겹침
(자카드)만으로 대체하면 — 특히 한국어처럼 조사/어미가 붙는 언어에서는 —
의미가 완전히 같은 문장도 겹치는 단어가 거의 없어서 클러스터가 실제보다
훨씬 잘게 쪼개진다(`한국어_조사_결합_토큰화_누락_함정.md` 참고). 실측:
자카드 기반 클러스터링이 "일관성 0.3"으로 낸 상황을 사람이 직접 읽어보니
5번 중 4번이 사실상 같은 전략("휴식/잠시 손 떼기")이었다 — 표현만 달랐을
뿐. 임베딩 API 키가 없는 환경에서는 자동화를 억지로 밀어붙이지 말고, N개
(보통 25개 안팎)를 사람(또는 LLM 자신)이 직접 읽고 의미 단위로 묶어 수동
산정하는 편이 더 정확하다 — 다만 그 값은 재현 불가능한 주관적 추정이므로
출처 필드(예: `consistency_score_method: "manual_llm_estimate"`)로 반드시
표시해서, 나중에 진짜 임베딩이 생기면 구분해서 재계산할 수 있게 해둔다.

## 실측 사례 (JudgeCal_Athe, D-122, 2026-09-11)

역산 시뮬레이터(내러티브 판단 게임)의 사전 저작 콘텐츠(상황당 행동선택
5개)가 "AI가 한 번 생성한 것"이라 얼마나 안정적인 판단인지 알 길이 없다는
문제에서 출발. 상황 하나당 fresh 서브에이전트 5개를 블라인드로 띄워 행동
목록을 독립 생성시킨 뒤, 직접 읽고 의미 클러스터로 묶어 "행동목록 겹침률"을
0.0~1.0로 수동 산정 — `consistency_score` 필드로 콘텐츠에 저장하고, 실제
매칭된 상황에서 사용자에게 참고용 배지로만 노출(승격/차단에는 안 씀). 두
카테고리(daily 1개, job 1개, 총 20개 상황×5=100회 독립 생성)에 반복 적용해
기법 자체가 카테고리 무관하게 재현됨을 확인 — 점수 분포가 실제 판단 난이도
차이(업계 표준 대응이 있는 상황은 0.9대, 재량 판단이 필요한 애매한 상황은
0.8 이하)를 잡아내는 것도 확인했다(순수 노이즈였다면 이런 분포 차이가 안
나왔을 것).

## 비용 감

상황 1개당 5회 호출(각 호출 3~4만 토큰 안팎, 5~15초) — 실사용 요청 경로에
넣기엔 비싸다. **콘텐츠 저작/큐레이션 시점(1회성)**에만 쓰고, 그 결과값을
저장해 실제 서비스 요청에서는 저장된 값을 그대로 재사용하는 구조로 짜야
한다. 상황 10개 분량이면 50회 호출 — 한 번에 다 띄우면(병렬) 실제 대기
시간은 각 호출의 지연시간 수준(수십 초)으로 끝난다.
