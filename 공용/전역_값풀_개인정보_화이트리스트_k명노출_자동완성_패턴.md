# 사용자들이 적은 값을 서로 자동완성으로 쓰게 할 때 — 항목은 고정, 값만 풀, 개인정보는 화이트리스트와 k명 노출로 막는다

## 문제

프로필처럼 항목이 많은 입력은 사용자가 직접 치기 힘들다. 다른 사람들이 이미 쓴 값("INTJ", "신중함", "파이썬")을 후보로 보여 주면
"검색해서 고르기"로 바뀐다. 그런데 사용자 입력을 남에게 보여 주는 순간 **이름·지역·병명·연락처가 새어 나갈 수 있다**.

**실측(RVS_App, 2026-11-03·06)**: 프로필 값 전역 풀을 서버에 두고 웹·앱 입력칸에 자동완성을 붙였다.
사용자 요구는 "항목(스키마)은 내가 미리 세팅해 고정, 그 안의 값만 풀로, 개인정보 항목은 스키마로 막고, 나중엔 직접 안 치고 골라서".

## 패턴

1. **두 가지 검색을 나눈다**
   - 항목 검색(맨 위 검색창): 항목 이름·분야 이름만 찾는다. 고르면 그 섹션을 펼치고 칸으로 이동. 풀과 무관.
   - 값 자동완성(각 칸): 그 칸에 치면 바로 아래 후보. 이것만 전역 풀을 쓴다.
2. **풀 칸은 화이트리스트**: 짧고 범용적인 칸만(성향 키워드, 가치, 강점·약점, 기술 이름, 우선순위 이름, 루틴 이름, 관계 이름표 "팀장").
   이름·지역·건강·메모·목표·일정·자유 서술은 **기본 제외**. 새 항목을 만들 때 "풀 허용"을 명시적으로 켜야 들어간다.
3. **값 검증**: 그 칸의 최대 길이 안, 연락처처럼 보이는 값 거절(`@`, URL, 4자리 이상 숫자, 전화번호 꼴). 저장은 막지 않고 풀에만 안 넣는다.
4. **k명 노출**: 다른 사용자에게는 서로 다른 사용자 k명(예: 3명) 이상이 쓴 값만 보인다. 한 사람만 쓴 값은 그 사람에게만 보인다("내가 쓴 값" 표시).
5. **기여는 현재 프로필과 같게**: 프로필 저장 때마다 그 사용자의 풀 행을 지우고 지금 값으로 다시 넣는다 → 지운 값은 빠진다. 계정 삭제 때 그 사용자 행을 지운다(삭제 훅을 풀 모듈이 스스로 등록).
6. **표 하나**: `(field, value, owner, created_at)` 기본키 `(field, value, owner)`. 조회는 `GROUP BY value HAVING COUNT(DISTINCT owner) >= k OR mine` + 부분 일치(대소문자 무시), 많이 쓴 순.
7. **클라이언트는 명세로 안다**: 프로필 명세 응답에 `pool_fields` 목록을 실어 보내고, 그 칸에만 자동완성을 붙인다. 풀을 안 쓰는 칸으로 조회하면 404.

## 함정

- **목록 칸(한 줄에 하나)**: 자동완성은 "지금 커서가 있는 줄"로 찾고, 고르면 그 줄만 바꾼다. 칩 입력이면 고르는 즉시 칩으로 추가.
- **시험 픽스처**: 명세 응답에 새 키(`pool_fields`)를 붙였으면, 명세를 대조하는 서버 시험과 픽스처 생성 스크립트도 같은 모양(응답 그대로)으로 맞춘다. 한쪽만 고치면 다른 쪽 시험이 깨진다(RVS 11-06).
- **조회 칸 이름은 서버가 정한다**: 클라이언트 입력칸 이름 = 풀 경로(`section.field`, 목록 항목은 `list.subfield`)로 맞추면 연결이 단순하다.
- **풀이 비어 있을 때의 첫 경험**: 처음엔 후보가 거의 없다(k명 조건). 내가 쓴 값은 바로 보이게 해야 "기능이 동작한다"가 느껴진다.

## 체크리스트

- [ ] 풀 칸 목록이 코드 한 곳(화이트리스트)에 있고 개인정보 칸이 없다
- [ ] 연락처 꼴 거절과 길이 제한이 있다
- [ ] k명 이상만 남에게 보인다(시험으로 확인)
- [ ] 값을 지우거나 계정을 지우면 기여가 빠진다(시험으로 확인)
- [ ] 명세 응답에 풀 칸 목록이 있고, 픽스처·대조 시험이 같은 모양이다
