# 개인용 로컬도구 → 상용화/팀배포 전환 패턴

## 상황

1인 로컬 데스크톱 도구(설정파일·정책파일을 로컬에 평문으로 자유롭게 쓰고
읽는 구조)를 상용 제품이나 팀 배포로 전환할 때. "코드는 이미 잘 짜여
있으니 그대로 팔면 된다"는 착각이 흔한 함정 — 1인 로컬 도구는 "이 파일을
아무도 안 본다"와 "이 파일을 아무도 안 고친다"라는 암묵적 신뢰 위에서
설계돼 있어서, 전제가 깨지는 순간 지금까지 안 보이던 두 종류 구멍이
드러난다.

## 핵심 원칙

상용화/팀배포는 "제작자 = 유일한 사용자 = 유일한 신뢰주체"라는 전제 중
최소 하나가 깨지는 사건이다. 어느 게 깨지는지에 따라 손봐야 할 지점이
갈린다 — 아래 2가지가 실제로 제일 먼저, 제일 조용히 걸린다(코드 리뷰로는
안 잡히고 git/파일 감사로만 잡힘).

## 체크리스트 (7가지 — 실제로 걸리는 지점)

1. **앱이 실행 중 자동으로 만들어내는 파일에 개인 경로/사용자명이 실리는가**
   (설정파일, 사용기록, 프리셋, 최근 작업 목록 등) → `.gitignore`는 보통
   `.env`처럼 "알려진 시크릿 파일"만 잡지, 앱이 알아서 채워나가는 상태
   파일은 안 잡는다. 최초 커밋 시점엔 그 파일이 비어있거나 아예
   없어서 아무도 gitignore에 안 넣고 넘어가고, 나중에 실사용하며 실제
   경로/사용자명이 채워진 뒤에야 `git status`/`git log -- <파일>`로
   뒤늦게 드러난다. 원격 저장소가 아직 없으면 히스토리 재작성은 나중으로
   미뤄도 안전하지만(로컬에만 존재), `.gitignore` 추가는 "지금부터"만
   막을 뿐 과거 커밋 속 내용은 그대로라는 점을 놓치기 쉽다 — 첫 공개
   push 전엔 반드시 `git filter-repo` 등으로 과거 커밋까지 정리해야 함.
2. **정책/설정 파일이 "이 사람이 이 명령을 실행해도 되는가"를 가르는
   로직의 근거인가**(실행 허용/차단 규칙, 자동승인 조건 등) → 개인용일
   땐 평문 JSON 직접 편집이 편의지만, "팀원이 몰래 못 고친다"는 게 제품의
   판매 근거가 되는 순간 그 편의가 그대로 취약점이 된다. 서버 인프라 없이
   로컬에서 완결되는 해법은 비대칭키 서명(관리자 개인키로 서명, 공개키로
   검증) + 검증 실패 시 "기존 관대한 설정 유지"가 아니라 엄격한 폴백
   (fail-closed, 전부 확인 필요 모드)으로 떨어뜨리는 것. 배포 시 흔한
   실수 2개: (a) 공개키를 팀원마다 다르게 주는 게 아니라 전원 동일 파일
   1개를 그대로 복사해야 함 — 개인키만 관리자가 보관, (b) 공개키만
   배포하면 안 되고 "서명된 정책파일 + 서명파일" 세트까지 통째로 같이
   배포해야 함(공개키만 넣고 팀원의 기존 정책파일을 안 바꾸면 서명
   불일치로 즉시 폴백당해 오작동처럼 보임). 관리자가 정책을 고칠 때마다
   재서명 + 재배포도 필요.

3. **개별 데이터 항목마다 "리터럴 경로"를 직접 들고 있는가** (프리셋/명령어별
   저장 경로, 즐겨찾기별 폴더 등) → 1인 사용 땐 "이 프리셋은 항상 이
   폴더에서" 식으로 항목마다 경로를 박아둬도 문제가 안 드러난다. 여러
   프로젝트를 오가며 쓰는 실사용 패턴, 또는 다른 사용자에게 배포하는
   순간 이 방식은 깨진다 — 항목마다 제각각 경로가 박혀 있으면 "지금
   내가 작업 중인 프로젝트"라는 개념 자체가 없어서 매번 수동으로
   맞춰줘야 한다. 해법은 데이터 항목에서 리터럴 경로를 완전히 제거하고,
   "지금 활성화된 컨텍스트(활성 루트)" 하나만 두는 세션형 모델로
   전환하는 것 — 클로드 코드가 디렉터리별 세션을 관리하는 것과 같은
   패턴. 실행 시 항목이 뭘 들고 있든 무시하고 항상 활성 컨텍스트로
   해석하면, 배포 후에도 각 사용자가 자기 활성 루트만 바꾸면 모든
   항목이 자동으로 맞게 동작한다. 부가로 "자주/최근 사용" 랭킹까지
   붙이면(기존 사용량 카운트 모듈이 있다면 그 패턴 그대로 재사용 가능)
   컨텍스트 전환 자체가 하나의 기능이 된다.
4. **데모/마케팅용으로 캡처하는 화면에 실제 개인정보가 그대로 찍히는가**
   → 1~2번을 다 조치해서 git에는 개인정보가 없어져도, 앱을 실제로
   켜서 스크린샷을 찍는 순간 화면 자체(상태줄, 최근 목록, 프리셋 이름
   등)에 실경로·실사용자명·다른 프로젝트명이 그대로 나온다. 이건
   git 감사로는 절대 안 잡히고 캡처 직후 육안으로만 잡힌다 — 데모
   자료 준비를 "코드/데이터 정리가 끝난 뒤"의 완전히 별개 단계로
   취급하고, 캡처 직전에 예시용 더미 값(`C:\projects\demo-app` 같은)으로
   바꾼 뒤 찍거나, 찍은 뒤 해당 부분만 잘라내는 후처리를 반드시 거친다.
5. **판매/배포 채널 자체에 "신규 계정 콜드스타트" 장벽이 있는가** → 결제
   플랫폼(스토어 생성이 계정 단위로 레이트리밋 걸릴 수 있음 — IP를
   바꿔도 안 풀리면 계정 자체가 걸린 것이므로 네트워크 문제로 오판하지
   말고 지원팀에 바로 문의) + 홍보 채널(Hacker News, Indie Hackers 등
   커뮤니티형 플랫폼은 신규 계정이 계정 나이/댓글 활동 이력을 어느 정도
   쌓기 전엔 글 작성 자체가 막힘, 스팸성 무의미한 댓글로 억지로 채우면
   오히려 역효과) 양쪽 다 "코드 다 준비되면 바로 노출 가능"이 아니라
   최소 며칠의 준비 기간이 별도로 필요하다는 걸 일정에 넣어야 한다.
6. **가격을 감으로 정하고 있는가** → "이 정도면 팔리겠지" 대신, 비슷한
   카테고리(예: 인디 개발자용 SaaS 보일러플레이트/소스코드 템플릿)의
   실제 거래 시세를 먼저 조사한 뒤, 그 구간의 중하단에서 시작해서
   반응 보고 올리는 순서가 안전하다. 판매 채널(예: Lemon Squeezy vs
   Gumroad)도 수수료 구조·세금 처리 방식·개발자 도구 카테고리 적합성
   기준으로 비교해서 고른다.

7. **로컬 전용이라 인증을 생략한 컴포넌트가 있는가**(관리자 콘솔, 디버그
   서버, 내부 API 등) → 1인용일 땐 "같은 기기(127.0.0.1) 또는 같은
   Wi-Fi에서만 접근 가능하니 토큰 인증까지는 과하다"는 판단이 실제로
   합리적이다 — 위협 모델 자체가 "공인 도메인에 여러 기기/사용자가
   접속하는 서버"와 다르기 때문. 문제는 이 판단이 **원저자 본인의
   배포 환경을 전제로 한 것**이라는 점 — 그 코드가 판매용 소스로
   나가는 순간 전제가 깨진다: 구매자가 어떤 네트워크 토폴로지에
   배포할지, `0.0.0.0`으로 LAN에 열지, 공유 서버에 올릴지를 원저자는
   알 수 없다. "로컬 전용이라 무인증"이라는 원래 결정 자체가 틀린 게
   아니라, **그 결정이 유효한 전제(배포 환경을 안다)가 판매 순간
   사라진다**는 게 핵심 — 코드 리뷰로는 안 잡히고, "이 코드를 산 사람이
   내가 모르는 환경에 배포한다"는 질문을 스스로 던져야만 드러난다. 해법은
   무인증을 완전히 없애는 게 아니라 **기본값을 뒤집되 탈출구를
   남기는 것** — 토큰 인증을 기본값으로 켜고(자동생성 토큰, 시작 시
   출력), 원저자 본인처럼 순수 로컬 전용 용도인 걸 아는 사람만 명시적
   플래그로 원래(무인증) 동작으로 되돌릴 수 있게 한다.

8. **"코드 틀만 먼저, 검증은 나중에 몰아서"로 전환 작업을 쪼갤 때 — 축마다
   위험도가 다르다는 걸 구분하는가** → 상용화/팀배포 전환은 손댈 지점이
   많아 "일단 파라미터 배선(코드 틀)만 해두고, 실제 검증 로직은 서비스화
   착수 직전에 한 번에 몰아서 채운다"는 접근이 합리적일 때가 많다(1인
   사용 중이라 그 시점까지 미뤄도 실사용 리스크가 없다는 전제 위에서).
   문제는 이 "스캐폴드 후 나중에 검증"이 **모든 축에 똑같이 안전하지
   않다**는 것 — 축을 헷갈리면 "나중에 잠그면 되는 줄 알았던 것"이 아니라
   "선언하는 순간 이미 위험한 것"을 방치하게 된다.
   - **안전한 축(지금 열어놔도 됨, 나중에 잠그면 됨)**: 인증/소유권 검증—
     함수가 `owner_user_id` 같은 파라미터를 받기만 하고 아직 `if` 검증을
     안 걸면, 기본 동작은 "누구나 통과"라 스캐폴드 자체가 아무 동작도
     안 바꾼다. `게이트_실패시_열림_패턴.md`(같은 폴더)의 fail-open
     철학과 같은 축 — "지금 당장 방어를 안 걸어도 기존 동작과 동일"이
     성립하는 종류.
   - **위험한 축(선언하는 순간 즉시 위험해짐)**: 응답 스키마 강제(FastAPI
     `response_model=`, 엄격한 JSON Schema validate, DB `NOT NULL`/`CHECK`
     제약 등)는 "선언 = 즉시 런타임에서 필터링/검증이 활성화"라서, 필드가
     하나라도 빠진 채로 걸면 **그 순간부터 실제 응답이 조용히 잘려나가거나
     저장이 거부된다** — "나중에 완성하면 되지"가 성립하지 않는다. 이
     축은 (a) 스키마/모델 정의 자체는 미리 작성해두되 (b) 실제로
     "부착"(response_model= 지정, validate 활성화, 제약 추가)하는 단계는
     완전히 분리해서, 부착 직전에 실제 반환값/데이터와 전수 대조부터
     한다.
   - **판단 기준**: "이 스캐폴드 커밋이 지금 당장 실제 동작을 하나라도
     바꾸는가?"를 먼저 확인한다 — 안 바뀌면 안전한 축(그대로 진행), 이미
     바뀐다면(선언만 했는데 필터링이 걸림) 위험한 축이니 정의와 부착을
     반드시 분리한다.
   - 부가 팁: 대량의 스키마/모델을 한 번에 만들어야 할 때(엔드포인트
     50개 이상 등) 초안 작성을 서브에이전트에 위임하더라도, 전부를
     맹신하지 말고 트래픽이 크거나 로직이 복잡한 핵심 엔드포인트 몇 개는
     반드시 원본 코드와 직접 대조 검증한다 — "조건부로만 붙는 필드"
     (예: 특정 분기에서만 응답 dict에 새 키가 생기는 경우)를 초안이
     놓치는 게 실제로 발생하는 실패 유형이다.

## 실측 사례

`Local_APP\터미널 단축키 모음집`(dev_shortcuts, 자연어→명령어 패키징
데스크톱 앱)을 상용화 검토하며 위 2개 조건이 전부 실제로 걸림돌로
확인됨(2026-08-24). 1번은 `config.json`/`presets.json`/`usage_history.json`이
실제 Windows 사용자명 + 여러 프로젝트의 절대경로를 담은 채 git에 커밋돼
있었음(원격 저장소가 없어 아직 외부 유출은 없었음 — `git rm --cached` +
`.gitignore`로 조치, 히스토리 재작성은 첫 공개 push 전 필수 항목으로
별도 기록). 2번은 `execution_policy.json`(명령어별 허용/확인/차단 규칙)이
평문이라 "팀 정책을 개인이 몰래 못 바꾼다"는 주장이 성립하지 않는 문제 —
`backend/policy_signing.py`(Ed25519 서명 검증 + 폴백) + `sign_policy.py`
(관리자 전용 키생성/서명 CLI) 신설로 해결. 상세는 그 프로젝트 설계도의
D-033/D-034, H-020/H-021 참고(일반화된 버전은 이 문서에만 남기고 프로젝트
세부사항은 그쪽에만 둠 — 중복 기록 안 함).

같은 프로젝트에서 3~6번도 전부 실제로 확인됨(2026-08-25~26). 3번은 프리셋/
명령어마다 저장돼 있던 리터럴 경로를 전부 제거하고 `db/project_roots.py`
(사용량 카운트+세션형 활성 루트, 클로드 코드 세션 전환과 동일한 발상)로
전환 — `backend/runner.resolve_path()`가 저장된 값과 무관하게 항상 활성
루트로 수렴하도록 변경. 4번은 스크린샷 캡처 중 런처 상태줄에 실경로가
찍힌 걸 2번(액션바, 위험명령 확인) 발견해서 캡처 후 크롭으로 조치. 5번은
Lemon Squeezy가 계정 단위로 보이는 429(모바일 등 다른 네트워크에서도

않았다** — 2026-09-07·09-08 두 세션에 걸쳐 grep(`require_auth`/
`token_urlsafe`/`Bearer` 전부 매치 없음)과 실제 서버 실행+무인증 curl
요청(200 OK로 레지스트리 데이터 그대로 반환)으로 재현 확인. **이 문서가
"완료"로 기록한 게 실제 배포 코드에 반영됐다는 보장이 아니라는 뜻** —
사본/포크에 적용한 수정을 이 문서에 "완료"로 적을 땐 어느 경로(원본인지
사본인지)에 적용했는지까지 명시해야 하고, 원본 코드가 여전히 취약한 채로
2세션·11커밋 동안 방치됐다는 사실 자체가 "문서상 완료 = 실제 반영"이
아니라는 걸 보여주는 실측 사례다.

**같은 조사 중 발견된 인접 함정(2026-09-08, 별개 취약점)**: 같은
"로컬 전용이라 안전하다"는 전제가 걸린 또 다른 지점 — `corePath`(MCP
무인 세션 스케줄러가 여는 앱 경로)를 `cmd.exe /K "cd /d {core_path} &&
..."`처럼 f-string으로 셸 명령 문자열에 직접 끼워넣고 있었다.
`core_path`에 `"` 한 글자만 섞여도(`C:\proj" & calc.exe & "`) 뒤에
임의 명령을 이어붙이는 명령 인젝션 — 무인 실행(사람이 매번 확인 안 함)
이라 더 위험한 유형. 인증 누락과 달리 이건 **알려진 위험문자를 걸러내는
게 아니라 벡터 자체를 구조적으로 없애는 해법**이 있었다: 경로를
문자열에 끼워넣지 말고 `subprocess.Popen([...], cwd=core_path)`처럼
OS가 셸 파싱 없이 처리하는 파라미터로 넘기면 된다(Windows
CreateProcess의 `lpCurrentDirectory`). 교훈: "로컬 전용/원저자만 씀"
전제가 깨지는 시나리오는 인증 누락 하나가 아니라, 그 전제 위에서 안전
검증 없이 짜여진 문자열 조합(셸 명령, SQL, 경로) 전부를 의심 대상으로
넓혀야 한다.
