# Claude Code 다중 프로젝트 워크스페이스 — 규칙 인덱싱 패턴 (범용)

여러 프로젝트가 한 워크스페이스(상위 폴더) 밑에 모여 있고, 그 프로젝트들이 공통
작업규칙을 공유해야 하는 모든 상황에 적용하는 패턴. 특정 워크스페이스 하나에
종속된 문서가 아니다 — 새 워크스페이스를 만들거나 새 PC로 옮길 때 이 패턴을
그대로 재현한다. (`flutter_App` 워크스페이스가 실제 적용 예시로 곳곳에 등장하지만,
그건 예시일 뿐 이 문서의 대상이 아니다.)

## 핵심 원칙 3가지

1. **하드코딩 대상은 "위치"지 "내용"이 아니다.** 어떤 파일을 다른 파일이 참조할 때,
   그 경로를 고정으로 적어두는 건 안전하다 — 위치는 거의 안 바뀌고, 내용은 참조하는
   쪽이 매번 다시 읽으므로(또는 `@import`로 자동으로) 최신 상태가 반영된다. 진짜
   위험한 건 **내용을 복붙**하는 것 — 참조 대신 전체 텍스트를 그대로 옮겨 담으면
   원본이 바뀔 때마다 사본도 일일이 갱신해야 하는 이중 관리가 시작된다.
2. **"항상 필요한 것"과 "가끔 필요한 것"을 구분해서 로드 방식을 다르게 한다.** 항상
   필요한 것(예: 코딩 작업 컨벤션)은 세션 시작 시 무조건 자동으로 있어야 하고, 가끔만
   필요한 것(예: 특정 프로젝트 세부 규칙, 설계 문서 프로토콜)은 인덱스에 경로만
   기록해두고 필요할 때 찾아서 연다.
3. **"자동 로드 안 함"과 "경로를 모름"은 다르다.** 어떤 항목을 항상 로드 대상에서
   뺐다고 그 항목이 어디 있는지까지 인덱스에서 지우면 안 된다 — 인덱스의 존재 이유
   자체가 "가끔 필요한 것의 경로를 항상 기록해두고, 여는 건 필요할 때만 하는 것"이다.

## 계층 구조 (3단)

1. **사용자 레벨(`~/.claude/CLAUDE.md`, Claude Code 공식 기능)** — 이 PC의 어느
   프로젝트에서 세션을 열든 예외 없이 항상 로드되는 유일한 자리. `@import`로
   "항상 필요한 것"만 최소한으로 하드코딩한다(원칙 2). 보통 2가지 정도로 충분:
   - 워크스페이스 공통 작업규칙 마스터본(선커밋/커밋규칙/테스트/빌드 등 코딩
     컨벤션 — 프로젝트 세부사항이나 설계 문서 프로토콜은 여기 안 넣는다, 아래
     "무엇을 항상 로드할지" 참고)
   - 워크스페이스 밖에서도 항상 알아야 하는 것이 있다면 그것도(예: PC 환경설정
     스크립트 위치 인덱스)

2. **워크스페이스 루트의 분류기(`<workspace>/.claude/CLAUDE.md`)** — 워크스페이스
   루트에서 세션을 열었을 때만 로드됨(개별 프로젝트 폴더 안에서 열면 안 보임 —
   그래도 무관, 1번이 이미 항상 부르고 있으므로). **실제 내용을 담지 않는다** —
   "항상 필요한 것"이 어디 있는지(1번이 이미 불렀으니 참고용) + "가끔 필요한 것"
   (다른 프로젝트 찾기, 워크스페이스 공용 참고 문서 등)의 경로만 안내하는 순수
   인덱스. 여기서 `@import`를 또 쓰면 1번과 중복 로드되니 안 쓴다.

3. **각 프로젝트 루트의 `.claude/CLAUDE.md`** — `@import` 안 쓴다. "작업규칙
   마스터본은 이미 자동 로드돼 있다"는 한 문단 + (있다면) 그 프로젝트만의 전용
   규칙만 프로즈로 담는다. 1번이 이미 어디서 세션을 열든 보장해주므로, 프로젝트
   마다 또 `@import`할 필요가 없다.

**3.5. (선택 확장) 이 위에 레지스트리 계층을 하나 더 얹을 수 있다.** 프로젝트
수가 많아지면 3번 파일 하나하나에 프로즈로 참조조건을 써넣는 대신, 별도 레지스트리
파일(JSON 등, 프로젝트 label→경로→참조조건 매핑)을 하나 두고 각 3번 파일은 그
레지스트리를 가리키는 순수 포인터로만 남길 수 있다("실제 참조조건은 항상 레지스트리
파일에서 확인, 여기 내용을 복붙하지 않는다" 같은 문구). 이러면 참조조건이 바뀔 때
프로젝트마다 CLAUDE.md를 손대는 대신 레지스트리 한 곳만 고치면 된다 — 원칙 1
("하드코딩 대상은 위치지 내용이 아니다")을 3번 계층에도 한 단계 더 적용한 것.
프로젝트 수가 적으면 오버엔지니어링이니, 3번만으로 부족하다고 느껴질 때만 도입한다.

**3.5-a. 레지스트리를 도입했으면 물리 CLAUDE.md는 "산출물"이지 관리 대상이
아니다.** 레지스트리의 참조조건 텍스트가 실질적 규칙 SSOT가 되는 순간, 각
프로젝트의 물리 `CLAUDE.md`는 그 텍스트로부터 그때그때 재생성 가능한 결과물일
뿐이다(둘 데이터가 어긋날 위험은 "손편집 vs 재생성"의 이중관리처럼 보이지만,
재생성이 항상 레지스트리와 100% 일치하게 만들면 애초에 발생하지 않는다). 이
상태에서 물리 CLAUDE.md가 남아있는 유일한 이유는 **레지스트리/훅을 못 읽는 다른
AI 툴(Cursor/Windsurf 등, `.cursorrules`/`.windsurfrules`류 관례)과의 호환**뿐 —
그런 툴을 안 쓰기로 했다면 물리 파일 자체를 완전히 없애도 지금 작업 중인 AI
에이전트 입장에서는 기능 손실이 없다(레지스트리를 직접 읽으면 되므로).

**3.5-b. 공유 컨트롤플레인(레지스트리+상시로드 규칙)은 자식 프로젝트가 아니라
공통 조상 위치에 둔다.** 여러 프로젝트(워크스페이스)가 하나의 레지스트리를
같이 참조하는 구조에서, 그 레지스트리 파일을 그 여러 프로젝트 중 "가장 자주
여는" 프로젝트 하나 안에 물리적으로 두면 당장은 편해도 구조적으로 어색하다 —
그 프로젝트가 여러 소비자 중 하나일 뿐인데 소유자처럼 보이게 되고, 나중에 그
프로젝트만 통째로 옮기거나 삭제하면 다른 모든 프로젝트가 같이 끊긴다. 여러
소비자가 공유하는 설정/레지스트리/컨트롤플레인은 **그 소비자들의 공통
부모(워크스페이스) 밑에 전용 폴더**를 두고 거기 둔다(예: `<여러 프로젝트의
부모>/Plug_In_Global/.claude/` 같은 형태) — 특정 자식 프로젝트에 얹혀사는 대신.

**3.5-c. 레지스트리 하나당 하위 문서는 "README 체인"으로 뻗는다, JSON을 매번
안 고친다.** 레지스트리의 각 항목(루트)은 그 루트의 **최상위(진입점) README** 딱
하나만 가리키면 된다(예: `readmeReferenceCondition` 필드 하나). 그 밑에 하위
프로젝트/폴더가 늘어나서 README가 여러 개 생겨도 레지스트리는 절대 안
건드린다 — 대신 새 README가 생길 때마다 그 **바로 위(부모) README**에 "경로 +
언제 여는지 한 줄"을 표로 추가한다. 즉 인덱싱은 "레지스트리→최상위 README"
한 번만 구조화 데이터로 하고, 그 아래는 전부 README가 README를 가리키는
자연어 체인으로 내려간다. 이러면 하위 문서가 아무리 늘어나도 레지스트리는
등록 시점 이후로 사실상 안정 상태를 유지한다 — 레지스트리를 고쳐야 하는 경우는
"완전히 새로운 최상위 루트를 등록할 때"뿐이다.

**3.5-d. referenceCondition(또는 그에 준하는 프로즈 필드)을 새로 쓰거나 고칠 때
따르는 공통 골격**: `# {루트명} — {한 줄 역할}` 헤더로 시작 → "사용자 레벨 규칙은
이미 자동 로드됨" 한 문단(2번 계층과의 중복 로드 방지 확인) → 본문(인덱스
표 또는 산문, 하위 항목 3개 이상이면 표로) → (하위 프로젝트가 여럿이면) "다른
루트와의 관계" 절, 양방향 역참조 명시 → "세션이 이 루트 자체에서 열렸을 때만"
절(하위에 여러 프로젝트가 있을 때만 필요, 완결형 단일 프로젝트면 생략). 안 쓰는
섹션은 억지로 채우지 말고 뺀다 — 짧아도 되는 루트를 길게 쓰는 것보다, 그 루트
성격에 맞는 섹션만 남기는 쪽이 다른 루트들과의 패턴 일관성을 지킨다.

**3.5-e. README 체인만으로는 "정말 열리는지"가 프로즈 판단에 의존한다 —
자동 체크가 필요한 하위 항목엔 경량 레지스트리 티어를 하나 더 둔다.**
3.5-c의 README 체인은 그 문서가 지금 작업과 "관련있다"고 AI가 판단해야만
실제로 열린다는 약점이 있다 — 새로 생긴 미등록 하위 폴더에서 그냥 작업을
시작하면 그 판단 자체가 안 걸릴 수 있다는 게 실측으로 확인됨(README가
있는데도 한 번도 안 열리는 경우). 그 폴더를 완전한 루트로 승격(3.5의
레지스트리 계층 전체, referenceCondition 동기화·actions 같은 무거운
기계장치 포함)하는 건 과하다. 그 중간에 **경량 레지스트리 배열**(무거운
루트 배열과 완전히 분리, 최소 필드 `{label, path, parentLabel, 마지막
점검일}`만)을 하나 더 둘 수 있다 — 프로즈가 아니라 "구조화된 목록"이라,
세션 시작 훅 같은 자동 체크가 AI 판단 없이도 전체를 순회할 수 있게 된다.

**3.5-f. 폴더가 이동해도 재탐색 가능하게, 그 폴더의 README 자신에 라벨을
자기선언시킨다.** 경량 레지스트리가 경로를 들고 있어도 폴더가 옮겨지면
경로가 끊긴다. 그 폴더의 README.md 맨 위에 `<!-- SSOT-LABEL: 이름 -->`
같은 자기선언 마커 한 줄을 두면, 경로가 끊겼을 때 이 라벨로 다시 찾아낼
수 있는 앵커가 된다. 표기는 값 하나만 담을 거면 프론트매터보다 주석
마커가 낫다 — 구조화된 값(부모 라벨, 마지막 점검일 등)은 어차피 레지스트리
JSON이 이미 들고 있으므로 README 쪽엔 재탐색용 앵커 하나만 있으면 충분하고,
주석은 렌더링 시 안 보여서 기존 문서 스타일을 안 깬다(프론트매터는 여러
필드를 담기엔 좋지만 렌더링 시 그대로 텍스트 블록으로 노출되고, 이미
프론트매터 관례가 없는 프로젝트라면 스타일이 붕 뜬다).

**3.5-g. "정기 점검이 필요한 항목"의 알림은 시계가 아니라 날짜 문턱값으로
잡고, 평소엔 카운트다운 → 문턱값 도달 시 승인 요청으로 전환한다.** AI
에이전트는 세션이 열려 있을 때만 존재하므로 "N시간마다"/"매일 자정에" 같은
시계 기반 알림은 실제 무인 백그라운드 실행(cron 등)이 있어야만 의미가
있다 — 이건 "사람이 세션 중 직접 승인"이라는 전제 자체를 벗어나는 훨씬 큰
결정(사람 없이 파일을 만들고 고치는 자율 에이전트가 된다는 뜻)이라, 정기
점검엔 안 맞는 경우가 많다. 대신 "마지막 점검일 대비 오늘 며칠 지났나"를
**세션이 열릴 때마다(그 항목과 무관한 세션 포함, 3.5-e처럼 cwd 매치 여부와
무관하게 전체 순회)** 재계산하는 문턱값 방식을 쓰면, 세션 사이 공백을
자연스럽게 흡수하면서도 무인 실행 없이 같은 효과를 낸다. 새 문턱값 숫자를
발명하지 말고 그 프로젝트에 이미 있는 비슷한 성격의 문턱값을 재사용한다
(근거 없는 임의의 새 숫자보다 낫다). 알림 방식도 "문턱값 넘기 전엔 조용,
넘으면 갑자기 경고"보다 낫게 — 문턱값 전엔 매 세션 "점검까지 D-N일" 같은
카운트다운을 항상 보여줘서 사람이 원하면 언제든 앞당겨 수동으로 트리거할
수 있게 열어두고, 문턱값에 도달하면 그제서야 "지금 진행할까요?" 승인형
프롬프트로 바꾼다. 어느 쪽이든 신호만 낼 뿐 실제 점검(파일 생성/수정 등)은
사람 승인 뒤 에이전트가 그 세션 안에서 직접 수행 — 신호를 내는 쪽과
실행하는 쪽을 분리하는 원칙은 그대로 유지된다.

**3.5-h. 범용규칙 문서가 다른 프로젝트를 마이닝해 신설될 때, 원본 프로젝트
README에도 역참조를 표준 절차로 남긴다.** 코드_프로젝트_범용규칙(또는 이에 준하는
범용 패턴 저장소)에 새 패턴 문서가 어떤 프로젝트의 실측 사례를 근거로 신설되면,
그 근거가 된 원본 프로젝트의 README(또는 그 프로젝트 인덱싱 계층의 진입점
README — 3.5-c의 README 체인 규칙을 따름)에도 "일반화된 버전은 `<경로>`에 있다"는
역참조 한 줄을 매번 남기는 걸 표준으로 삼는다(임기응변이 아니라 절차). 이 역참조는
**참조조건(어떤 상황에 여는지) 한 줄만** 담는다 — 범용규칙 문서 쪽에 원본 프로젝트의
세부 내용을 복붙하지 않듯, 반대 방향(세부 내용을 원본 README에 길게 인라인으로
늘어놓는 것)도 하지 않는다. 세부 내용은 그 프로젝트 안 별도 파일로 분리하고,
README에는 그 파일을 가리키는 참조조건 한 줄만 남긴다 — 이 폴더의 "문서 인덱스"
표(참조조건 한 줄 + 실제 내용은 별도 .md) 자체가 이미 이 원칙을 코드_프로젝트_
범용규칙 자신에게 적용하고 있는 사례다.

**3.5-i. 세션 밖(무인 스케줄러 등)에서 도는 감지원이 있으면, 그 결과를
다음 세션에 넘기는 통로도 같은 레지스트리 파일에 "구조화된 요청 큐"로
둔다.** 3.5-g가 정리한 "세션이 열릴 때만 존재하는 AI 에이전트" 전제는
감지 자체가 세션 밖(작업 스케줄러/cron 등)에서 일어나는 경우에도 안
바뀐다 — 무인 스케줄러가 문제를 찾아도 그 자리에서 파일을 고칠 순 없고
(3.5-g와 동일한 "신호와 실행 분리" 원칙), 사람이 다음 세션을 열 때까지
그 발견을 어딘가에 들고 있어야 한다. 이때 GUI 버튼 같은 별도 입력
경로를 새로 만들 필요는 보통 없다 — 구조적으로 감지 가능한 문제
(경로 소실/문서 부재/신선도 등)는 애초에 사람이 먼저 알아채야 하는
케이스가 실질적으로 없기 때문(설계 중 실제로 이 결론에 도달해 GUI
버튼 안을 스스로 기각한 사례 있음). 대신 `{requestId, targetType,
targetLabel, actionType, requestedAt, note}` 형태의 최소 필드짜리
배열을 레지스트리에 하나 더 둔다 — 처리 완료되면 그 항목을 지우고
이력은 안 남긴다(경량 레지스트리의 `마지막 점검일`을 덮어쓰기만 하는
것과 같은 원칙, 이력이 필요하면 3.5-j 참고). 이 큐 하나로 GUI/CLI/
무인 스케줄러처럼 서로 프로세스가 다른 여러 감지원이 전부 같은 레지스트리
파일을 통해서만 접점을 갖는다 — 서로 직접 호출하지 않는다.

**3.5-j. 감지 로그는 "최근 이력"이 아니라 "나중에 알고리즘 투자 여부를
판단할 데이터"로 설계한다.** 3.5-g의 큐(3.5-i)는 처리되면 이력을 안
남기므로, "이 종류의 문제가 실제로 얼마나 자주 발생하는가"를 시간을
두고 판단하려면 별도의 축적형 로그가 필요하다 — 단순 디버그용 최근
20건 뷰가 아니라, 각 발견마다 **근거(evidence)**까지 구조화해서 담아야
나중에 "이 패턴이 반복되니 전용 처리 로직에 투자할 가치가 있다/없다"를
데이터로 판단할 수 있다(예: 경로가 사라진 걸 감지할 때 "이동했는지
삭제됐는지 재탐색하는 알고리즘"을 만들지 말지는, 그 사라짐이 실제로
몇 번이나 발생했는지가 쌓여야 판단 가능하다 — 감지만 하고 재탐색은
사람이 매번 판단하게 미뤄둔 스켈레톤 단계에서 특히 중요). 상한(보관
개수)도 "최근 로그"류 진단 로그보다 넉넉하게 잡는다 — 목적이 다르면
같은 숫자를 재사용하지 않는다.

**3.5-k. SessionStart 훅이 주입하는 양은 "상시/조건부"로 나눠 줄인다 — 훅은 입구(인덱스)만
주고 상세는 참조 조건으로 돌린다.** 훅이 주입한 파일은 곧 상시 로드이므로 파일 크기가 곧 모든
세션의 비용이다. 실측 예: 한 워크스페이스에서 훅 3개가 매 세션 약 17.6k자를 넣고 있었다(작업규칙
전문 10,373자 + 프로젝트 인수인계 전문 5,797자 + 레지스트리 요약 약 1.5k자). 이 중 인수인계를
"다음 시작점 + 최근 세션 요약(3개) + 참조 조건 표"로 줄였더니 5,797자 → 1,780자(훅 출력 측정
2,253자)가 됐고, 긴 내용(사용자 프로필·미결·이전 진행)은 **원문 그대로** 별도 문서로 옮겨 표로만
연결했다. 판단 기준: (1) 상시 주입 파일 자체를 인덱스형으로 설계한다(훅 코드는 거의 안 바꿔도
파일이 작아지면 자동 절감). (2) "읽지 않으면 적용 안 되는" 규칙 전문은 포인터로만 돌리면 `@import`
미전개와 같은 조용한 누락 위험이 있다 — 줄이려면 핵심 요약 상시 + 전문 포인터(이중 관리 비용)가
한계선이고, 줄일지는 사용자가 정한다. (3) 이동은 삭제가 아니다: 줄 범위를 스크립트로 추출해 원문을
보존하고, 분리 전 원본은 백업 폴더에 두며, 이동 후 문서 안 경로가 실제 파일을 가리키는지 스크립트로
전수 확인한다. 함정: 스크립트 안 한 글자 함수명 `R`은 PowerShell 별칭 `r`(Invoke-History)과
충돌해 쓰기가 전부 실패했다(원본은 무사) — 함수명은 2글자 이상으로 짓는다.

**3.5-l. 폴더마다 "위·아래 포인터만" 가진 CLAUDE.md + README 참조 조건 체인 + 부모 등록
게이트.** 3.5-a는 레지스트리가 있으면 물리 CLAUDE.md가 군더더기라고 했지만, Claude Code가 조상
CLAUDE.md는 자동으로 전부 불러오고 하위 CLAUDE.md는 그 폴더 파일을 건드릴 때 지연 로드한다는 점을
이용하면 "어느 폴더에서 열든 그 폴더의 입구가 자동으로 보장"된다(레지스트리 계층이 없는 하위 폴더에
특히 유효). 규칙: (1) CLAUDE.md는 포인터만 — 최상위 CLAUDE.md 경로, 바로 위 CLAUDE.md, "항상 먼저
이 폴더 README를 읽을 것", 하위 목록과 여는 조건(내용 복붙 금지). (2) README는 그 폴더 문서의
참조 조건 전문(경로 + 언제 여는지 표) + 하위 README를 여는 조건. (3) **게이트**: 새 문서·하위
폴더·기록 파일은 부모 README 표(와 부모 CLAUDE.md 하위 목록)에 먼저 한 줄을 추가한다 — 표에 없는
문서는 기록·참조 대상이 아니다(읽기 인덱스 = 기록 인덱스). 이러면 최상위에서 하위 README의 조건만
갱신하면 아래로 자연스럽게 내려간다. 절충: 앱이 생성하는 이웃 블록이 닿지 않는 하위 폴더에서는 포인터
CLAUDE.md가 수동 관리라 새 폴더를 만들 때 3곳(새 CLAUDE.md, 부모 하위 목록, 부모 README 표)을
사람이 맞춰야 하고 어긋남을 알려주는 자동 검증이 없다. 새 세션에서 실제로 자동 로드되는지는 첫
세션에 확인 항목으로 두고 검증한다.
## 무엇을 "항상 로드"에 넣을지 판단 기준

항상 로드 대상은 최소한으로 유지한다 — 넣을 때마다 모든 세션(그 워크스페이스와
전혀 무관한 세션 포함)이 그 컨텍스트 비용을 상시로 문다. 판단 기준:

- **넣어야 하는 것**: 코딩 작업 자체의 컨벤션(커밋 규칙, 테스트 규칙 등) — 거의
  매 세션 실제로 쓰인다.
- **빼야 하는 것**: 특정 작업 유형에서만 쓰이는 프로토콜(예: 설계 문서 작성
  프로토콜, 아키텍처 레이어 방침) — 그 문서 자신이 "일반 작업규칙과 분리 유지,
  합치면 컨텍스트 부담 상시 발생"이라고 명시하는 경우가 특히 그렇다. 이런 건
  분량이 크면 클수록 항상 로드 대가가 커지므로 인덱스로 돌린다.
- **분류기 자체는 `@import`를 쓰지 않는다** — 워크스페이스 루트에서 열 때만 로드되는
  파일이 1번(사용자 레벨)과 같은 내용을 또 `@import`하면, 루트에서 여는 그 순간만
  같은 내용이 두 번 로드되는 낭비가 생긴다.

## 새 프로젝트를 워크스페이스에 추가할 때

1. `<프로젝트>/.claude/CLAUDE.md`를 아래 템플릿으로 생성(`@import` 안 씀):
   ```
   # <프로젝트명> — 프로젝트 규칙

   작업규칙 마스터본은 이미 자동 로드돼 있다 — `~/.claude/CLAUDE.md`(사용자 레벨)가
   `@import`로 세션마다 무조건 주입하므로 따로 찾아가서 읽을 필요 없다.
   `<워크스페이스 루트>/.claude/CLAUDE.md`는 프로젝트별 양방향 인덱스(다른 프로젝트
   경로 목록) 용도 — 이 프로젝트 안에서만 작업할 땐 안 봐도 되고, 다른 프로젝트를
   찾아야 할 때만 연다.
   ```
2. 워크스페이스 루트 분류기의 프로젝트 인덱스 표에 새 행(프로젝트명 + **루트 폴더
   경로**, `.md` 파일까지는 안 적음 — 아래 "인덱스 표는 md 파일이 아니라 폴더
   경로로" 참고)을 추가한다(양방향 — 새 프로젝트 CLAUDE.md에도 위 템플릿으로 이미
   역참조가 남는다).
3. 이 프로젝트만의 전용 규칙(빌드 명령, 커밋 정책, 고정 SSOT 문서 등)이 생기면 위
   템플릿 아래에 이어서 프로즈로 적는다.

## 인덱스 표는 md 파일이 아니라 폴더 경로로

프로젝트별 인덱스 표에 각 프로젝트의 `CLAUDE.md` 파일 경로를 직접 적지 않는다 —
파일 경로를 그대로 적어두면 인덱스를 열자마자 나열된 걸 전부 열어보게 되기 쉽다.
대신 **프로젝트 루트 폴더**까지만 적어서, 필요한 프로젝트를 찾은 다음에도 "그 안
`.claude/CLAUDE.md`를 찾아서 연다"는 판단을 한 단계 더 거치게 한다.

## 새 워크스페이스에 이 패턴을 처음 적용할 때 — 폴더 구조 예시

작은 항목(프로젝트 인덱스 표, 짧은 참고 경로 등)은 분류기 파일 안에 섹션으로 직접
담고, 크거나 항상 로드 대상인 것만 별도 파일로 분리한다 — 폴더/파일을 필요 이상
쪼개지 않는다. `flutter_App` 워크스페이스의 실제 구조:

```
<workspace>/.claude/
├── CLAUDE.md      ← 분류기. 프로젝트 인덱스 표, 스캐폴딩 킷 경로, 가끔 필요한
│                     참고문서 경로 등 작은 항목은 여기 섹션으로 직접 담음.
│                     @import 안 씀.
└── .claude/       ← 작업규칙 마스터본(항상 로드) — 크거나 상시 필요한 것만
    └── CLAUDE.md     여기 별도 파일로 분리.
```

## Claude Code 공식 import 문법(`@경로`)

CLAUDE.md 안에 `@경로/파일` 한 줄만 적으면 그 파일 내용을 **세션 시작 시 그 자리에
그대로 펼쳐 넣는** 공식 import 문법(상대/절대/`~/` 경로 전부 지원, 재귀 최대 4단계,
코드블록 안 `@`는 무시, `.md` 아닌 파일도 가능 — `.txt`도 확인됨).

| | 프로즈 안내문 | `@경로` import |
|---|---|---|
| 로드 여부 | AI가 "가서 읽어야지"라고 판단해야 함(안 읽을 수도 있음) | 세션 시작 시 무조건 자동 로드 |
| 작업 폴더 밖 참조 | 제약 없음 | 최초 1회 승인 팝업 뜸(그 뒤론 안 뜸) |
| 토큰 비용 | 참고 시에만 | 매 세션 항상(안 읽을 수도 있는 대신 확실히 읽음) |
| 언제 쓰나 | "가끔 필요" 성격 | "항상 있어야" 성격 — 최소 개수만 |

**주의**: import 대상 파일을 나중에 이동/리네임하면, 그 파일을 가리키던 `@import`
줄을 같이 고쳐야 한다 — 프로즈 포인터와 달리 깨져도 에러 없이 조용히 무시될 수
있어 더 위험하다. 하드코딩 지점을 최소화할수록 이 유지보수 리스크도 줄어든다.
